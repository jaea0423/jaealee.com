## 1. 결정 — 테이블 구조: **예약은 행(row) 단위로 분리, 설정은 jsonb 한 덩어리**

한 덩어리(JSON 통째)는 기기 두 대가 각자 저장하면 **서로 덮어써서** 예약이 사라집니다. 예약만 분리하면 충돌 검사·TV 공개 뷰·백업이 전부 행 단위로 됩니다. 설정은 한 사람(사장)이 가끔 고치니 덩어리로 둡니다.

**칼럼으로 뽑는 기준: 조회 조건·정렬·뷰·색인에 필요한 것만.** 나머지는 전부 `data jsonb`. 화면 코드가 보는 예약 객체 모양은 **지금과 100% 같게** 유지합니다 — 행 ↔ 객체 변환은 `rowToRes(row)` / `resToRow(rec)` 두 함수에서만 합니다.

```sql
-- v4/supabase/schema.sql  (Supabase SQL Editor 에서 한 번 실행)
create table stores (
  key        text primary key,                 -- 'hanok' | 'anjip'
  name       text not null,
  settings   jsonb not null default '{}',      -- 지금의 s.settings 통째 (좌석·영업시간·코스·문자·tvType…)
  snapshots  jsonb not null default '{}',      -- 6차의 s.snapshots (날짜별 좌석 수)
  updated_at timestamptz not null default now()
);
create table reservations (
  id         uuid primary key,                 -- 클라이언트 newId() 가 만든 UUID 그대로
  store      text not null references stores(key),
  date       text not null,                    -- 'YYYY-MM-DD' 문자열 (시차 문제 없음)
  time       text not null,                    -- 'HH:MM'
  status     text not null,                    -- 확정/방문/노쇼/취소 (지금 값 그대로)
  name       text not null default '',
  phone      text not null default '',         -- 숫자만 (하이픈 제거해서 저장, 화면에서 phoneFmt)
  people     int  not null default 0,          -- pplOf(r) 결과. 성인/유아 세부는 data 에
  room_id    text,                             -- r.roomId (잠정 배정 tentativeRoomId 는 data 에)
  data       jsonb not null default '{}',      -- 나머지 전부: adults, infants, courses, source, memo, request, changes, sms, tentativeRoomId …
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  deleted_at timestamptz                       -- soft delete. null 이면 살아 있음
);
create index reservations_store_date on reservations(store, date);
create index reservations_store_phone on reservations(store, phone);
create table logs (
  id     bigserial primary key,
  store  text not null,
  at     timestamptz not null default now(),
  action text not null,
  detail text not null default '',
  who    text not null default '',             -- 'staff' | 'admin' | 'screen'
  ua     text not null default ''
);
-- updated_at 은 서버가 찍습니다. 태블릿·TV 시계는 믿지 않습니다.
create or replace function set_updated_at() returns trigger language plpgsql as $$
begin new.updated_at = now(); return new; end $$;
create trigger t_res_upd   before update on reservations for each row execute function set_updated_at();
create trigger t_store_upd before update on stores       for each row execute function set_updated_at();
```

- `trash` 는 별 테이블이 아니라 `deleted_at is not null` 인 행입니다. 불러올 때 최근 30일 지운 것을 `s.trash` 로 채웁니다.
- 안집(`anjip`) 행도 만들어 둡니다(비활성). `store` 칼럼은 처음부터.
- `changes` 이력은 `data.changes` 안에. 감사 로그로 뺄 양이 아닙니다.

## 2. 결정 — 동시 수정 충돌: **`updated_at` 조건부 저장 → 충돌이면 확인창(두 선택지), 자동으로 이기는 쪽 없음**

- 저장은 `PATCH /rest/v1/reservations?id=eq.{id}&updated_at=eq.{내가 마지막으로 본 값}` + `Prefer: return=representation`. **응답 행이 0개면 충돌**(누가 먼저 고쳤음).
- 충돌이면 그 행을 다시 읽어 확인창: 제목 `다른 기기에서 먼저 수정됐습니다`, 본문에 **상대 버전 요약**(시각·인원·좌석·상태 중 다른 것만 `18:00 → 18:30` 식으로), 버튼 두 개 — **`상대 내용으로 보기`(기본, 내 변경 버림)** / `내 변경으로 덮어쓰기`(조건 없이 PATCH). 막지 않고 선택을 줍니다.
- 삭제도 `deleted_at` PATCH 라 같은 규칙. 등록(INSERT)은 UUID 라 충돌이 없습니다. 삭제된 행을 다른 기기가 고치면 0행 → 같은 확인창에 `이미 삭제된 예약입니다` 문구.
- 저장 성공 응답의 `updated_at` 을 `rec.updatedAt` 에 넣습니다(문자열 그대로 비교. 파싱 금지 — 마이크로초가 잘립니다).
- **`saveData()` 호출부는 건드리지 않습니다.** `saveData()` 를 '바뀐 것만 보내는 flush' 로 바꿉니다: 마지막 동기화 때의 각 예약 JSON 문자열(`SYNC.res[id]`)과 지금 `JSON.stringify(rec)` 가 다르면 PATCH, `SYNC` 에 없으면 POST, 설정은 `JSON.stringify(settings)` 비교 후 PATCH. 예약 200~500건 stringify 는 밀리초 단위입니다. 호출부 40여 곳을 고치는 것보다 이게 안전합니다.
- flush 실패(네트워크): 화면 위에 빨간 띠 `저장 안 됨 · 다시 시도` 버튼. dirty 상태는 메모리에 남아 있으니 다시 시도하면 됩니다. **탭을 닫으면 사라진다**는 문구를 띠에 씁니다. 오프라인 쓰기 큐는 만들지 않습니다(결정).
- 1분 자동 갱신(`refreshData` → 아래 `reloadFromStore`)이 **dirty 인 로컬 예약은 덮지 않습니다.** 서버 버전은 옆에 두고 다음 flush 때 충돌 절차로 갑니다.

## 3. 결정 — 권한: **anon 키 파일에 내장 + 계정 2개(PIN 이 비밀번호) + RLS 전부 켜기 + TV 는 공개 뷰만**

- 이메일 링크 로그인은 **안 합니다.** 카운터 태블릿에 메일함이 없습니다. 지금 PIN 화면 그대로, 뒤에서 `POST /auth/v1/token?grant_type=password` 로 `staff@jaealee.com` 로그인. 관리자 비밀번호는 `admin@jaealee.com`. 두 계정은 대시보드에서 손으로 만들고(Auto Confirm), **가입은 막습니다.**
- **PIN 은 6자리로 확정.** Supabase 비밀번호 최소 길이가 6 이라 4자리는 아예 안 됩니다. PIN 화면 점 4개 → 6개(`.pdot` 한옥반점 네 글자 → `한옥반점예약` 여섯 글자, 글꼴 f1~f6 순환).
- RLS: 세 테이블 모두 켜고 `authenticated` 에게 전체 허용, `anon` 에게는 정책 없음(= 전부 차단). 두 계정이 같은 권한을 갖는 건 의도된 것입니다 — 어드민 구분은 **화면에서** `SESSION.who === "admin"` 으로만 합니다(설정 변경·PIN 변경). DB 수준 구분은 미룹니다.
- 세션: 로그인 응답의 `access_token`(1시간) + `refresh_token` 을 **메모리와 sessionStorage** 에만. 만료 5분 전 `grant_type=refresh_token` 으로 갱신. 새로고침·재시작 시 PIN 다시 입력(지금 규칙 유지). `localStorage` 에 토큰을 두지 않습니다.
- PIN 틀림 5회 → 60초 잠금(클라이언트). Supabase 자체 로그인 제한도 있지만 화면에서 먼저 막아 둡니다.
- PIN 변경 = `PUT /auth/v1/user` `{password}` 를 **admin 토큰으로 staff 계정에** 할 수 없으므로: PIN 변경 화면에서 관리자 비밀번호로 admin 로그인 → 그 뒤 **staff 로 다시 로그인해서 staff 토큰으로 `PUT /auth/v1/user`**. 즉 PIN 변경 화면은 (관리자 비밀번호, 현재 PIN, 새 PIN) 세 칸. 관리자 비밀번호 변경은 admin 토큰으로 같은 API.
- `PIN_ANY` 삭제. `DATA._auth` · `DEFAULT_AUTH` 삭제(PIN 이 파일 안에 평문으로 있던 것이 이걸로 끝). `migrate` 에서 `_auth` 가 있으면 지웁니다.

```sql
alter table stores       enable row level security;
alter table reservations enable row level security;
alter table logs         enable row level security;
create policy staff_all on stores       for all to authenticated using (true) with check (true);
create policy staff_all on reservations for all to authenticated using (true) with check (true);
create policy staff_all on logs         for all to authenticated using (true) with check (true);
revoke all on stores, reservations, logs from anon;

-- 손님용 TV: 로그인 없이 보는 두 뷰. 이름은 서버에서 가립니다(JS maskName 과 같은 모양: "조 * 결", "김 *").
create or replace function mask_name(n text) returns text language sql immutable as $$
  select case when length(trim(n)) <= 1 then trim(n)
              when length(trim(n)) = 2 then left(trim(n),1) || ' *'
              else left(trim(n),1) || ' ' || array_to_string(array_fill('*'::text, array[length(trim(n))-2]), ' ') || ' ' || right(trim(n),1) end
$$;
create or replace view public_today as
  select store, time, mask_name(name) as name, people, room_id, status
  from reservations
  where deleted_at is null and status in ('확정','방문')
    and date = to_char(now() at time zone 'Asia/Seoul', 'YYYY-MM-DD');
create or replace view public_screen as
  select key as store, name,
         jsonb_build_object('rooms', settings->'rooms', 'displayRows', settings->'displayRows',
                            'tvAd', settings->'tvAd', 'tvType', settings->'tvType') as settings
  from stores;
grant select on public_today, public_screen to anon;
```
- `public_screen` 에 넣는 설정 키는 **TV 코드(`renderTvList/renderTvGrid/displayRows/seatLabel`)가 실제로 읽는 키**를 grep 으로 확인해 맞춥니다. 전화·요청사항·메모·문자는 뷰에 **절대** 넣지 않습니다.
- 확인: `curl -H "apikey: ANON" URL/rest/v1/reservations` → 빈 배열 또는 401 이어야 하고, `/rest/v1/public_today` → 오늘 행. 이 두 줄 결과를 보고에 붙입니다.

## 4. 결정 — 오프라인·읽기 실패: **마지막 성공본을 브라우저에 저장해 읽기 전용으로 보여줌 + 띠**

- 불러오기 성공마다 `localStorage["hanok.cache.v1"] = {at, stores, reservations}` (로그 제외, 1~2MB).
- 불러오기 실패 → 캐시가 있으면 그것으로 화면을 그리고 `DATA._readonly = true`, 띠: `오프라인 · 마지막 갱신 12:30 · 지금은 볼 수만 있습니다` + `다시 연결` 버튼. 30초마다 자동 재시도, 성공하면 띠 내리고 정상 모드. 캐시도 없으면 지금 5차의 빈 화면 + 빨간 띠(`.loaderr`) 그대로.
- 읽기 전용일 때 등록·수정 버튼은 **숨기지 않고** 누르면 `지금은 저장할 수 없습니다 — 종이에 적어 두세요` 안내(막되 이유를 말함. 이 경우는 진짜로 저장이 불가능하므로 예외).
- 사장님 폰 데이터 끊김도 같은 경로입니다. 별도 처리 없음.
- TV: `public_today/public_screen` 결과를 `localStorage["hanok.screen.v1"]` 에 같은 방식으로. 실패 3회 띠(`.tvl-off`)는 5차에 있음.

## 6. 결정 — 클라이언트: **supabase-js CDN 안 씀. `fetch` 로 REST·Auth 직접 호출**

"외부 요청 0" 원칙 유지, 파일 크기 그대로, 구형 TV 에서도 `fetch` 는 됩니다(Chrome 42+; 이 코드는 이미 async/await 로 55+ 를 요구). 필요한 호출은 여섯 개뿐입니다:

| 용도 | 호출 |
|---|---|
| 로그인 | `POST {url}/auth/v1/token?grant_type=password` `{email,password}` |
| 갱신 | `POST …?grant_type=refresh_token` `{refresh_token}` |
| 비밀번호 변경 | `PUT {url}/auth/v1/user` `{password}` |
| 읽기 | `GET {url}/rest/v1/reservations?store=eq.hanok&date=gte.{오늘-365}&select=*&order=date,time` (`deleted_at` 포함해서 받고 클라이언트가 trash 로 분류. 1년 넘은 노쇼 이력은 안 보이는 것을 감수 — 보고에 명시) |
| 델타 갱신 | `GET …&updated_at=gt.{마지막 최대 updated_at}` — 1분 폴링은 **전체가 아니라 바뀐 행만** |
| 쓰기 | `POST` / `PATCH …?id=eq.X&updated_at=eq.Y` (`Prefer: return=representation`) |

모든 요청 헤더: `apikey: anon`, `Authorization: Bearer {access_token 또는 anon}`, `Content-Type: application/json`. 헬퍼 하나 `sb(path, opts)` 로 묶습니다. Realtime(웹소켓)은 쓰지 않습니다 — 1분 폴링이 이미 있고 TV 에서 소켓은 불안합니다.

`loadData()` 순서: 로그인 → `stores` → `reservations`(365일) → `logs`(최근 300) → 지금의 `DATA` 모양으로 조립(`DATA.hanok.reservations / .settings / .trash / .snapshots`, `DATA._logs`) → `migrate()` 그대로 → 캐시 저장. `reloadFromStore()` = 델타 GET → 병합(dirty 제외) → `LAST_REFRESH`. `logEvent()` 는 메모리 push + `logs` INSERT(실패해도 무시, 로그 때문에 화면이 죽지 않게). `saveData()` = 2번의 flush.

TV(`view.fromRoute`): 로그인 없이 `public_screen` + `public_today` 만 읽어 `DATA.hanok` 의 **최소 모양**(settings 일부, reservations = 뷰 행을 `{date:오늘, time, name, people, roomId, status}` 로)을 만듭니다. `renderTvList/Grid` 가 그 이상을 읽으면 그 지점만 고칩니다. 1분 갱신은 뷰를 다시 읽습니다.

## 7. 백업 — GitHub Actions 가 매일 새벽 JSON 으로 받아 **비공개 저장소**에 커밋

- **`jaealee.com` 저장소에 넣지 않습니다.** 그 저장소는 공개이고 백업에는 이름·전화가 있습니다. 새 비공개 저장소 `hanok-backup` 을 만들고 그 안에 워크플로를 둡니다.
- `v4/backup/hanok-backup.yml` 을 작성해 두면 재아가 그 저장소 `.github/workflows/` 로 옮깁니다. 내용: 매일 19:30 UTC(04:30 KST) `curl` 로 `reservations`(전체, 삭제 포함)·`stores`·`logs`(30일) 를 받아 `data/*.json` 으로 저장, 바뀐 것이 있으면 커밋. `SUPABASE_URL`·`SUPABASE_SERVICE_KEY` 는 **GitHub Secrets**. 실패하면 Actions 가 메일을 보내니 별도 알림 없음.
- 복구 절차 한 단락을 `v4/supabase/checklist.md` 끝에: "백업 JSON 을 SQL Editor 의 `insert … select from jsonb_populate_recordset` 로 되돌린다" 정도. 실제 복구 스크립트까지는 이번에 안 만듭니다.

## 9. 묶음과 멈춤 지점

- **묶음 A — 파일만**: `schema.sql`, `checklist.md`, `build.py`(dev/prod 분기 + `__SUPA_CFG__`), `supabase.dev.json.example`. 코드 수정 없음. → 보고 후 **재아가 8번 1~5 를 함**. 끝나면 "다음".
- **묶음 B — 읽기**: `sb()` 헬퍼, 로그인(PIN 6자리 화면), `loadData` 서버판, `rowToRes/resToRow`, 캐시·읽기 전용 띠. 쓰기는 아직 막아 둠(`_readonly`). 확인: dev 에서 로그인 → 빈 화면 정상, 키 틀리게 빌드 → 빨간 띠, 네트워크 차단(Playwright `route.abort`) → 캐시 띠.
- **묶음 C — 쓰기**: flush 방식 `saveData`, 충돌 확인창, `logEvent` INSERT, `reloadFromStore` 델타, 저장 실패 띠. 확인: **탭 두 개**를 열어 같은 예약을 각각 고쳐 두 번째 저장에서 충돌창이 뜨는지; 탭 A 등록 → 탭 B 1분 갱신에 나타나는지; 새로고침 후 남아 있는지; 삭제 → trash → 다른 탭에서 사라지는지.
- **묶음 D — TV**: 공개 뷰 읽기, 로그인 없는 `screen/`, 캐시. 확인: 로그아웃 상태 `dev/screen/` 에서 오늘 예약이 가린 이름으로 보이고, 개발자도구 Network 응답에 **전화번호가 한 글자도 없는지**.
- **묶음 E — 계정**: PIN 변경(3칸)·관리자 비밀번호 변경, 5회 잠금, `PIN_ANY`·`_auth` 삭제, `demo` 플래그. 확인: 틀린 PIN 5회 → 60초, 바꾼 PIN 으로 재로그인.
- **묶음 F — 백업**: `hanok-backup.yml` + checklist 복구 단락. 재아가 저장소·Secrets 만든 뒤 `workflow_dispatch` 로 한 번 수동 실행해 JSON 이 생기는지 확인.
- 전부 끝나면 `supabase.prod.json` 으로 `python build.py` → 실서비스. 그 전까지 **prod 프로젝트에는 아무것도 쓰지 않습니다.**

## 10. 하지 않을 것

- supabase-js · Realtime · Edge Function · 오프라인 쓰기 큐 · 권한 세분화(RLS 로 staff/admin 구분) · 문자 실발송 · 안집 활성화.
