# Supabase 붙이기 전에 정리할 것

작성일: 2026-09-13
결론: **화면이 아니라 "데이터 모양" 다섯 가지를 먼저 고칩니다.** 한 번 DB 에 들어가면 되돌리기 어렵습니다.

---

## 1부. 반드시 먼저 (코드 수정 · v4)

### ① 코스 키가 '순서 번호' 입니다 — 제일 위험합니다

지금 예약의 코스는 이렇게 저장됩니다.

```js
courses: { "0|촉": 2, "1|동한": 4 }     // 0, 1 = 설정에 있는 코스 묶음의 '순서 번호'
```

`courseSummary()` 는 `k.split("|")[1]` 로 이름을 꺼내고,
`courseGroupFits()` 는 `+k.split("|")[0]` 을 **설정 배열의 인덱스로** 씁니다.

> 사장님이 설정에서 코스 묶음 순서를 바꾸거나 하나 지우면,
> **이미 저장된 예약의 코스가 전부 다른 묶음을 가리킵니다.**

지금은 예약이 화면에만 있으니 새로고침하면 사라집니다. DB 에 쌓이기 시작하면 **과거 기록이 조용히 틀어지고, 되돌릴 방법이 없습니다.**

→ 코스 묶음마다 고정 id(`cg_xxx`)를 주고 키를 `cg_a1b2|촉` 으로. 옛 데이터는 `migrate()` 에서 옮깁니다.

### ② 예약 id 가 밀리초 시각입니다

```js
id: "res_" + Date.now()
```

지금은 한 사람이 한 기기에서 쓰니 괜찮습니다. **여러 기기가 같은 DB 를 쓰면** 두 사람이 같은 밀리초에 저장할 때 같은 id 가 나옵니다. 기본 키라 한쪽이 덮어써집니다.

→ UUID 로. (`crypto.randomUUID` 는 구형 TV 에 없으므로 직접 만듭니다)

### ③ 삭제가 진짜 삭제입니다

```js
s.reservations = s.reservations.filter(r => r.id !== id);
```

기기 A 가 지우고, 기기 B 가 아직 옛 목록을 들고 있다가 저장하면 **지운 예약이 되살아납니다.**

→ `deletedAt` 을 찍고 화면에서만 뺍니다. 화면 동작은 지금과 똑같습니다.

### ④ `updatedAt` 이 아예 없습니다 (0곳)

두 사람이 같은 예약을 동시에 고쳤는지 **판단할 수단 자체가 없습니다.**
거창한 잠금은 필요 없습니다(직원 두세 명 · 하루 20건). `updatedAt` 한 칸이면
"내가 본 뒤에 누가 고쳤네" 를 알 수 있습니다.

→ 저장할 때마다 찍고, 나중에 `if updatedAt = 내가본값` 조건으로 씁니다.

### ⑤ 예시 데이터가 자동으로 들어옵니다 — 사고 위험

```js
try { ... } catch(e) { DATA = seedDemo(deepClone(DEFAULT_DATA)); }
```

불러오기가 **어떤 이유로든** 실패하면 가짜 예약 1,300건을 만듭니다.
지금은 저장이 안 되니 무해합니다. Supabase 를 붙이면 —

> 카운터에서 인터넷이 한 번 끊긴다 → 불러오기 실패 → 가짜 1,300건 생성
> → 직원이 예약 하나 수정 → **저장 → 진짜 DB 에 가짜 예약이 들어갑니다.**

→ 실패했을 때는 **비우지도 채우지도 말고 "불러오지 못했습니다" 를 띄우고 멈춥니다.**
예시 데이터는 설정에서 사람이 직접 누를 때만.

## 2부. 접속 키 — 걱정하신 것과 실제

> "접속 키가 들어가면 안 되고"

Supabase 키는 두 종류입니다. **이걸 구분하는 게 핵심입니다.**

| 키 | 공개해도 되나 |
|---|---|
| `anon` (공개용 키) | **원래 공개하는 키입니다.** 브라우저에 넣으라고 만든 것입니다 |
| `service_role` | **절대 안 됩니다.** 모든 규칙을 무시합니다. 서버에만 |

`anon` 키는 그 자체로 아무 권한이 없습니다. **RLS(행 수준 보안)** 를 켜 두면
로그인하지 않은 사람은 아무것도 못 읽고 못 씁니다. 키를 봐도 소용이 없습니다.

그래서 **`anon` 키는 파일에 넣는 게 맞습니다.** 대신 세 가지를 반드시 해야 합니다.

1. **모든 테이블에 RLS 켜기** — 기본이 꺼져 있습니다. 안 켜면 키만으로 다 뚫립니다
2. **회원가입 막기** (Supabase 대시보드 → Authentication → 가입 비활성화)
3. **`anon` 에게는 손님 화면용 읽기 뷰 하나만** 열기

### PIN 은 그대로 쓰되, 검증을 서버로

말씀하신 대로 **계정 두 개**를 만들고 PIN 을 그 계정의 비밀번호로 씁니다.

| 계정 | 비밀번호 | 쓰는 곳 |
|---|---|---|
| `staff@…` | 지금의 PIN | 평소 예약 접수·수정 |
| `admin@…` | 지금의 관리자 비밀번호 | 설정 변경, PIN 변경 |

화면은 **지금과 똑같습니다.** PIN 네 자리를 누르면 뒤에서 `staff` 계정으로 로그인할 뿐입니다.
직원은 이메일이 있는지도 모릅니다.

이렇게 하면 지금보다 나아지는 점:

- PIN 이 **더 이상 파일 안에 평문으로 있지 않습니다** (지금은 `DATA._auth` 에 그대로 있어 개발자도구로 보입니다)
- 검증이 서버에서 일어납니다
- `PIN_ANY = true` (아무 번호나 통과)를 그때 끄면 됩니다

### 짚고 갈 것 — 네 자리는 약합니다

공개 주소에 붙는 **유일한 자물쇠**가 네 자리 숫자면 경우의 수가 1만 개입니다.
안에 손님 이름과 전화번호가 들어 있으니 개인정보이기도 합니다.

식당 예약이 표적이 될 가능성은 낮지만, **여섯 자리로 늘리는 것**을 권합니다.
직원이 외우는 부담은 거의 같고, 경우의 수는 100배가 됩니다.

## 3부. 손님용 TV — 로그인 없이 봐야 합니다

TV 에는 키보드가 없습니다. `/screen/hanok` 주소로 열면 바로 떠야 합니다.

→ **읽기 전용 공개 뷰**를 하나 만듭니다. 오늘 것만, 그리고 **이름은 서버에서 가려서** 내보냅니다.

```sql
-- 손님 화면이 보는 것: 시각 · 가린 이름 · 인원 · 좌석. 그게 전부입니다.
create view public_today as
  select time, mask_name(name) as name, people, room_id
  from reservations
  where date = current_date and deleted_at is null and status in ('확정','방문');
```

지금은 **브라우저에서** 이름을 가립니다(`maskName`). 즉 **진짜 이름이 페이지 안에 다 들어 있고 개발자도구로 보입니다.** 공개 주소인 손님 화면에서는 서버에서 가려 보내는 편이 맞습니다.

전화번호·요청사항·메모는 이 뷰에 **아예 넣지 않습니다.**

## 4부. 스키마 — 지금 정할 것과 미룰 것

### 테이블로 쪼갤 것

| 테이블 | 비고 |
|---|---|
| `reservations` | `store`(hanok/anjip) 칼럼 **처음부터** 넣기. 안집이 나중에 들어옵니다 |
| `settings` | 매장별 한 줄. 내용은 **jsonb 한 덩어리** (아래 참고) |
| `logs` | 지금 배열 3,000건 제한 → 테이블로 |

### settings 는 jsonb 로 두세요 — 쪼개지 마세요

좌석·zone 구조를 테이블로 정규화하고 싶어질 텐데, **아직 누님 답을 못 받았습니다.**
"1·2·3 은 붙는데 1·3 은 안 됨" 같은 게 나오면 지금 모델(같은 존 안에서만 붙음)로는 표현이 안 됩니다.
테이블로 쪼개 놓고 나중에 바꾸면 **두 번 짜게 됩니다.** jsonb 는 모양이 바뀌어도 그냥 담깁니다.

### 그대로 둘 것

- **날짜·시간은 문자열로** (`"2026-09-13"`, `"18:30"`). `timestamptz` 로 바꾸면 시차 문제만 생깁니다.
  이 시스템에 UTC 가 필요한 곳은 한 군데도 없습니다
- `changes` 이력은 예약 안에 jsonb 로. 감사 로그로 따로 뺄 만큼 양이 많지 않습니다

|---|---|
