📘 Lecture 8 — Shell II & Process(입문)

자료: 09 lec8 - shell II and process.pdf (28쪽)

🧭 한눈에 보기 (Overview)

  • 전반부: Shell Script 문법 마무리 — case, for, while, function, read, here-string/here-document
  • 후반부: 프로세스(Process) 입문 — 메모리 구조, 상태(State), 전경/배경(foreground/background) 실행, ps·top·htop, fork() & execve()

① Case 문 (Multiway Branch)

🍰 비유: if-else if-else를 길게 쓰는 대신, “값에 딱 맞는 가지(case)”를 골라 들어가는 분기문입니다. 마치 자판기에서 버튼을 누르면 그 줄만 떨어지는 느낌이에요.

개념: case 변수 in 패턴) 명령 ;; 로 다중 분기를 구현합니다. 오직 한 패턴만 선택되며 패턴에는 와일드카드 *, ?, | (또는), [] (집합)을 쓸 수 있습니다. 자바의 switch와 유사하다고 생각하면 됩니다.

#!/bin/bash
# 사용자가 입력한 글자에 따라 분기
read ch
case $ch in
  [aeiou])  echo "모음(vowel)" ;;       # 한 글자 모음
  [a-z])    echo "소문자 자음" ;;       # 위에서 안 걸린 소문자
  q|Q)      echo "종료"; exit 0 ;;  # q 또는 Q
  *)        echo "기타" ;;              # 와일드카드 = 그 외 전부
esac
⚠️ 각 줄 끝의 ;; 가 break 역할입니다. 빼먹으면 문법 오류가 납니다.

② For Loop

🍡 비유: 꼬치에 꿰어진 재료를 하나씩 꺼내 굽는 것과 같아요. 미리 정한 단어 목록(word-list)을 처음부터 끝까지 한 번씩 돌립니다.

for 변수 in 단어목록
do
  # 반복할 명령
done

단어 목록에 올 수 있는 것:

  • 위치 매개변수(parameters): $1 $2 ... $@ — 스크립트를 호출할 때 준 인자들
  • 문자열(strings): "hello" "world" "1"
  • 파일명 패턴(filename glob): *.c, file?.txt
  • 쉘 변수(shell variables): $VAR1 $VAR2
  • 명령 치환(command substitution): $(ls) 또는 `ls` — 명령의 출력 결과를 그대로 끼워 넣기
# 예시 1: 인자 전부 출력
for a in "$@"; do echo $a; done

# 예시 2: 명령 치환 — 현재 폴더의 .c 파일들에 대해 반복
for f in $(ls *.c); do
  echo "컴파일: $f"
  gcc -c $f
done

③ While Loop

🚦 비유: 신호등이 초록일 동안만 계속 걷는 것과 같아요. 조건이 참(TRUE)인 동안 반복합니다.

while 조건
do
  # 반복할 명령
done

# 예: 1부터 5까지 출력
i=1
while [ $i -le 5 ]
do
  echo $i
  i=$((i+1))      # 산술 연산은 $(( ))
done

④ Loop 제어 — break / continue

  • break: 현재 감싸고 있는(enclosing) 반복문을 즉시 빠져나감. 자바의 break와 동일.
  • continue: 이번 반복은 건너뛰고 다음 조건/항목으로 점프.

⑤ Shell Function (함수)

🧰 비유: 자주 쓰는 도구를 도구함에 넣어두고 이름만 부르면 꺼내 쓰는 것. C/Java 함수와 비슷하지만 문법이 조금 다릅니다.

# 정의 (definition)
greet() {
  echo "Hello, $1 and $2"   # 함수 안에서 $1, $2 = 함수 인자
  return 0                    # 0 = 성공
}

# 호출 (call)
greet Alice Bob

# 반환값 확인 — $? 에는 직전 명령의 종료 상태
echo $?

# 환경 변수처럼 자식 쉘에도 함수 노출
export -f greet
💡 함수 내부의 $1, $2는 스크립트의 인자가 아니라 함수의 인자입니다. 변수 이름이 같아 보여도 스코프가 다르다는 것이 시험에 자주 나옵니다.

⑥ read — 표준 입력 한 줄 받기

키보드(표준 입력 stdin)에서 한 줄을 읽어 변수에 저장합니다.

# 변수 한 개
read name
echo "hi, $name"

# 변수 여러 개 — 공백으로 자동 분리
read a b c
# 입력: 1 2 3   →  $a=1 $b=2 $c=3

read + 파이프(|)의 함정

echo "hello world" | read arg1 arg2
echo $arg1 $arg2     # 결과는?

예상 결과: 빈 줄(아무것도 안 나옴).
왜? 파이프 오른쪽 read는 서브쉘(subshell)에서 실행됩니다. 거기서 만든 변수는 부모 쉘로 돌아오지 않으므로, 다음 줄 echo가 보는 $arg1은 비어 있어요. (이게 PDF의 “Why?” 슬라이드 정답입니다.)

해결법: brace 그룹 또는 here-string

# 방법 A: { ... } 그룹 — 같은 서브쉘 안에서 사용
echo "hello world" | {
  read arg1 arg2
  echo $arg1 $arg2  # 여기서는 보임
}
echo $arg1 $arg2    # 밖으로 나오면 다시 비어 있음

# 방법 B: here-string <<<  → 부모 쉘에서 직접 읽기
read arg1 arg2 <<< "hello world"
echo $arg1 $arg2    # 정상 출력

⑦ Here-document (<<)

🧾 비유: 한 줄짜리 인자가 아니라 “여러 줄짜리 종이쪽지”를 명령에 통째로 건네주는 방식.

cat << EOF > script.sh
#!/bin/bash
if test -f /bin/bash ; then
  echo "exist"
else
  echo "not exist"
fi
EOF

<< EOF ... EOF 사이의 모든 줄이 cat의 입력으로 들어가고, > script.sh 로 파일로 저장됩니다. 쉘 스크립트가 다른 스크립트 파일을 만들 때 자주 사용합니다.

⑧ Process — 정의와 메모리 구조

📦 비유: 프로그램(program)이 레시피라면, 프로세스(process)는 그 레시피로 실제로 요리하는 중인 행위입니다.

구분설명
Program정적(static) 객체 — 디스크에 저장된 실행 파일
Process능동(active) 객체 — 메모리에 올라가 실행 중인 인스턴스

프로세스를 구성하는 부분:

  • Text section: 실행할 코드(machine instructions)가 있는 영역
  • Data section: 전역 변수(global variable)가 있는 영역
  • Heap: 실행 중에 malloc 등으로 동적 할당(dynamically allocated)되는 메모리
  • Stack: 함수 호출 정보(매개변수, 지역변수, return address)가 쌓이는 영역
  • 현재 상태: program counter(PC), 레지스터(register) 값들
🔍 자료구조 수업과 연결: Stack은 마지막에 들어간 게 먼저 나오는(LIFO) 자료구조죠? 함수 호출이 끝날 때 가장 최근 호출의 지역변수가 먼저 사라지는 이유가 바로 이것입니다. Heap은 자료구조의 “힙(heap tree)”과 이름이 같지만 전혀 다른 개념이니 헷갈리지 마세요. 
# 실행 파일의 섹션 정보 확인
$ readelf -S /usr/bin/ls

⑨ Process State (프로세스 상태)

상태의미
New프로세스가 생성되는 중
RunningCPU가 현재 명령어를 실행 중
WaitingI/O 완료 같은 이벤트를 기다리는 중
ReadyCPU만 할당되면 바로 실행 가능 (큐에서 대기)
Terminated실행이 끝남

🧠 핵심: 한 CPU 코어에는 정확히 한 프로세스만 동시에 Running 상태일 수 있습니다. 여러 개가 동시에 도는 것처럼 보이는 건 시분할(time-sharing) 덕분이에요.

⑩ Foreground vs Background

🍔 비유: Foreground는 “주문하고 음식 받을 때까지 카운터에 서 있는 손님”, Background는 “주문 후 진동벨 받고 자리 가서 다른 일 하는 손님”입니다.

  • Foreground (interactive): 명령을 실행하면 끝날 때까지 쉘이 사용자 입력을 받지 않음.
  • Background (batch): 명령 끝에 & 를 붙이면 쉘이 즉시 다음 입력을 받음. 오래 걸리는 작업에 유용.
$ sleep 100 # foreground — 100초간 묶임
$ sleep 100 &        # background — 즉시 프롬프트 복귀, [1] 12345 같이 PID 표시
$ jobs             # 백그라운드 작업 목록 보기
$ fg %1            # 1번 작업을 foreground 로 가져오기

⑫ Process Creation — fork() & execve()

🧬 비유: fork()는 자신을 복사하는 분열, execve()는 복사된 몸의 껍데기는 두고 알맹이만 다른 프로그램으로 바꿔치기 하는 변신입니다.

  /bin/bash (PID:70253)
        |
        v  fork()
  /bin/bash (PID:88402)   # 똑같은 bash가 복사되어 새 PID 부여
        |
        v  execve("/usr/bin/bc")
  /usr/bin/bc (PID:88402) # 같은 PID지만 내용물이 bc로 바뀜
  • PID(process identifier): 0 이상의 유일한 정수. 자료구조에서 unique key 같은 역할.
  • 한 부모(parent)는 여러 자식(child)을 가질 수 있지만, 자식은 부모가 단 하나입니다 → 자료구조의 트리(tree) 모양이죠.
  • pstree 명령으로 프로세스 트리를 확인할 수 있습니다.

Q1. (쉬움) Shell의 case 문에서 각 패턴 줄을 종료할 때 반드시 붙여야 하는 기호는?
정답: ②. ;; 가 break 역할을 하며, 안 붙이면 문법 오류 또는 다음 case로 떨어집니다.
Q2. (쉬움) for f in *.c; do echo $f; done 가 활용한 “단어 목록 생성 방식”은?
정답: ③. *.c는 쉘이 매칭되는 파일명 목록으로 펼쳐줍니다(파일명 globbing).
Q3. (쉬움) 함수에서 직전 명령의 종료 상태를 보관하는 변수는?
정답: ③. $? 는 마지막으로 종료된 명령(또는 함수)의 exit status입니다. 참고로 $#=인자 개수, $@=인자 전체, $!=마지막 백그라운드 PID.
Q4. (중) 아래 코드의 출력 결과는? 
echo "hello world" | read a b
echo "[$a][$b]"
정답: ②. 파이프 오른쪽의 read는 서브쉘(subshell)에서 동작하므로 변수가 부모 쉘로 전달되지 않습니다. echo 시점에는 빈 값.
Q5. (중) 위 Q4 문제를 “부모 쉘에서 그대로” 변수에 담고 싶을 때 가장 깔끔한 방법은?
정답: ②. <<< 는 here-string으로, 좌변 문자열을 우변 명령의 stdin으로 직접 넣어줍니다. 서브쉘이 끼지 않아 변수가 살아남습니다.
Q6. (중) 프로세스 메모리 영역 중 malloc()으로 할당된 데이터가 머무는 곳은?
정답: ④. 동적 할당 = Heap. Stack은 함수 호출 프레임, Data는 전역/static 변수, Text는 코드(읽기 전용)입니다.

📝 Homework 08 — 관계 연산 쉘 스크립트

자료: 2026 HW08.pdf (3쪽) · 본문 제목은 “Homework #7”이지만 파일명 HW08 기준으로 정리합니다.

🇬🇧 English (원문 요약)

Please write a shell script relationop_studentID.sh for relational operations.

  • The script supports only the operators == and !=.
  • The operands are integer values.
  • The script takes exactly 3 command-line arguments: operand1 operator operand2.
    e.g., $ bash ./relationop_2019012345.sh 10 == 22
  • Use IF / ELIF / ELSE statements.
  • If the number of arguments is not 3 → print an error and exit.
  • For an invalid operator → print an error and exit.
  • Output must be either TRUE or FALSE.
🇰🇷 한국어로 보기

관계 연산용 쉘 스크립트 relationop_학번.sh 를 작성하세요.

  • 지원 연산자: == 와 != 두 가지만.
  • 피연산자는 모두 정수로 가정합니다.
  • 커맨드라인 인자(argument) 정확히 3개를 받습니다 — 순서: 피연산자1 연산자 피연산자2.
    예: $ bash ./relationop_2019012345.sh 10 == 22
  • if / elif / else 사용.
  • 인자 개수가 3개가 아니면 → 에러 메시지 출력 후 종료.
  • 지원하지 않는 연산자가 들어오면 → 에러 메시지 출력 후 종료.
  • 결과는 반드시 TRUE 또는 FALSE 로 출력.
✅ 모범 풀이 (한국어 해설)

🧠 설계 순서 (먼저 머리로 정리해보기):

  1. 인자 개수 검증 → $# 이 3이 아니면 에러 출력 + exit 1.
  2. 인자 3개를 의미 있는 이름 변수에 담기 (가독성 ↑) — op1=$1 op=$2 op2=$3.
  3. 연산자 분기: if/elif/else 로 ==, !=, 그 외 처리.
  4. 비교는 정수 비교이므로 산술 비교 연산자 -eq, -ne 사용. (주의: 쉘에서 == 는 문자열 비교용입니다. 입력 토큰이 == 라는 것과, 실제로 비교할 때 쓸 연산자는 다른 문제예요.)
  5. 결과는 TRUE / FALSE 둘 중 하나만 echo.

💻 정답 코드 (주석 포함):

#!/bin/bash
# relationop_2019012345.sh
# 인자 형식: $1 = 피연산자1, $2 = 연산자(== 또는 !=), $3 = 피연산자2

# 1) 인자 개수가 정확히 3개인지 검사
if [ "$#" -ne 3 ]; then
  echo "Error: exactly 3 arguments are required (operand1 operator operand2)"
  exit 1
fi

# 2) 의미 있는 이름으로 인자 받기
op1="$1"
op="$2"
op2="$3"

# 3) 연산자에 따라 분기 — IF/ELIF/ELSE
if [ "$op" = "==" ]; then
  # 정수 동등 비교 → -eq
  if [ "$op1" -eq "$op2" ]; then
    echo "TRUE"
  else
    echo "FALSE"
  fi
elif [ "$op" = "!=" ]; then
  # 정수 비동등 비교 → -ne
  if [ "$op1" -ne "$op2" ]; then
    echo "TRUE"
  else
    echo "FALSE"
  fi
else
  # 4) 지원하지 않는 연산자
  echo "Error: invalid operator '$op' (only == and != are supported)"
  exit 1
fi

  • [ $op1 == $op2 ] 도 동작하지만 이건 문자열 비교입니다. 과제는 정수 가정이므로 -eq, -ne 가 더 의도에 맞습니다.

📘 Lecture 9 — Process II & Compile (gcc)

자료: 10_lec9 - process and compiler.pdf (28쪽)

🧭 한눈에 보기

  • Process II: fork/execve 복습, 종료(termination)와 시그널, kill / sleep / uptime / time.
  • Compile: gcc 가 사실은 여러 도구의 묶음이라는 사실 — 전처리(pre-processor) → 컴파일(compile) → 어셈블(assemble) → 링크(link) 4단계.
  • 핵심 옵션: -o, -E, -S, -c, -v --save-temps, -l, -L, -I.

① Process Termination — 종료의 의미

🔚 비유: 영화가 끝나면 엔딩 크레딧을 부모(영화관)에게 보여주고 자리를 정리하는 것과 비슷합니다.

프로세스는 마지막 명령을 실행한 뒤 OS에 종료를 알립니다. 자식 프로세스가 종료되면 부모 프로세스에게 시그널(signal) 메커니즘으로 통지됩니다.

부모가 자식을 강제 종료하는 사유:

  • 자식이 허가된 자원을 초과해서 사용할 때
  • 부모가 더 이상 자식이 필요 없을 때

사용자가 강제로 죽이는 대표 명령은 kill -9 PID.

② kill 명령

$ kill [-signal] PID
$ kill -9   PID    # SIGKILL — 무조건 즉시 종료
$ kill -15  PID    # SIGTERM — 정중한 종료 요청(프로세스가 정리할 시간 줌, 기본값)
$ kill -l          # 사용 가능한 시그널 목록
$ man kill        # 매뉴얼
📌 중요: kill 은 “죽이는” 명령처럼 들리지만 정확히는 “시그널을 보내는” 명령입니다. 무슨 시그널이냐에 따라 종료, 일시정지, 무시 등 다양한 동작을 합니다.

③ sleep 명령

$ sleep seconds     # 지정한 초만큼 멈춤
$ sleep 3 && echo done   # 3초 뒤 done 출력

배치 처리 스크립트에서 의도적으로 시간 간격을 줄 때 자주 씁니다 (예: 서버 켜지길 기다린 뒤 클라이언트 시작).

④ uptime, time

  • uptime : 시스템이 얼마나 오래 켜져 있었는지 + 평균 부하(load average)
  • time 명령 : 명령 실행에 걸린 시간 측정 (real / user / sys)
$ time gcc -O2 hello.c
real    0m0.123s   # 실제 경과 시간 (wall-clock)
user    0m0.090s   # CPU 가 사용자 모드에서 쓴 시간
sys     0m0.020s   # CPU 가 커널 모드(시스템 콜)에서 쓴 시간

⑤ gcc 란? — “컴파일러”가 아니라 “드라이버”

🚗 비유: gcc 는 자동차 자체가 아니라, 여러 부품(전처리기, 컴파일러, 어셈블러, 링커)을 순서대로 운전하는 운전기사(driver)입니다.

GCC (GNU Compiler Collection) 는 처음엔 C 전용이었지만, 이후 C++, Objective-C, Fortran, Java, Go 같은 언어로 확장됐고 ARM·x86·SPARC 등 수많은 CPU 아키텍처를 지원합니다.

$ sudo apt install gcc
$ gcc [options] C-files

⑥ 컴파일 4단계 (Compilation Pipeline)

단계도구입력출력
① 전처리(Pre-processing)cpp0 / cc -Ehello.chello.i
② 컴파일(Compile)cc1hello.ihello.s
③ 어셈블(Assemble)ashello.shello.o
④ 링크(Link)ld / collect2hello.o + 라이브러리실행 파일 hello

4단계가 한 줄 명령(gcc hello.c)에 다 묻혀있는 것이지, 내부에서는 위 순서대로 실행됩니다. 시험에 단골입니다 ⭐

⑦ 단계별 옵션

$ gcc hello.c                        # 4단계 다 → a.out 생성
$ gcc -o hello hello.c               # 결과 파일명 hello

# 중간 산출물도 모두 보고 싶을 때
$ gcc -v --save-temps -o hello hello.c
# → hello.i (전처리), hello.s (어셈블리), hello.o (오브젝트), hello (실행) 모두 남김

# 단계별로 멈추기
$ gcc -E hello.c -o hello.i          # 전처리만 (#include, #define 펼침)
$ gcc -S hello.c -o hello.s          # 어셈블리까지
$ gcc -c hello.c -o hello.o          # 오브젝트까지 (링크 X)

⑧ 라이브러리 옵션 — -l / -L / -I

옵션의미예시
-lnamelibname.a 또는 libname.so 와 링크-lm → libm (수학 라이브러리), -lcurses
-Ldir라이브러리 탐색 경로 추가-L/home/me/mylib
-Idir헤더 파일 탐색 경로 추가-I/usr/local/include
$ gcc -o hello_box hello_box.c -lcurses          # ncurses(텍스트 UI) 와 링크
$ gcc -o app main.c -L/opt/mylib -lmymath -I/opt/include

관련 환경변수

  • LIBRARY_PATH: 컴파일/링크 시점에 정적 라이브러리 탐색 경로
  • LD_LIBRARY_PATH: 실행 시점에 공유 라이브러리(.so) 탐색 경로
$ export LD_LIBRARY_PATH=/opt/mylib:$LD_LIBRARY_PATH
$ source myenv          # myenv 파일 안의 export 들을 현재 쉘에 적용

⑨ ncurses — 참고용 메모

ncurses 는 터미널에서 텍스트 기반 UI(메뉴, 박스, 색상)를 그릴 수 있게 해주는 라이브러리입니다. 헤더 <curses.h> 를 포함하고 빌드할 때 -lcurses 또는 -lncurses 를 붙입니다. (시험에 깊게는 안 나와요. “이런 게 있구나” 수준.)

Practice #3 — hello 컴파일 + ELF 분석 + hex 패치(nop)

🇬🇧 English
  • Write hello.c in VIM, compile with gcc -o hello hello.c.
  • Inspect where “hello” and “world” strings live (use readelf / objdump).
  • Find the assembly location that calls printf (e.g., address 117a).
  • Open the executable with VIM in hex-edit mode (:%!xxd), replace e8 d1 fe ff ff → 90 90 90 90 90, then save with :%!xxd -r, :wq!.
  • Run the executable again and observe the result.
🇰🇷 한국어
  • VIM 으로 hello.c 작성 후 gcc -o hello hello.c 로 컴파일.
  • “hello” 와 “world” 문자열이 어느 섹션에 들어가 있는지 확인 (readelf, objdump).
  • 디스어셈블 결과에서 printf 를 호출하는 어셈블리의 위치를 찾기 (예: 117a).
  • VIM 16진 편집 모드(:%!xxd)로 실행파일 열어 e8 d1 fe ff ff 를 90 90 90 90 90 으로 치환. (:%!xxd -r 로 되돌린 뒤 :wq! 로 저장)
  • 실행 결과가 어떻게 달라지는지 확인.
✅ 풀이

1) hello.c 작성 후 컴파일

// hello.c
#include <stdio.h>
int main(void) {
  printf("hello\n");
  printf("world\n");
  return 0;
}
$ gcc -o hello hello.c
$ ./hello
hello
world

2) 문자열이 어느 섹션에 있는지 확인

$ readelf -S hello | grep -E "rodata|text|data"
  [n] .text       PROGBITS  ... # 실행 코드
  [n] .rodata     PROGBITS  ... # 읽기 전용 데이터 (대부분 여기에 문자열 리터럴이 들어감)

$ strings -t x hello | grep -E "hello|world"
  2004 hello
  200a world
# 위 오프셋은 보통 .rodata 영역에 속합니다.

3) printf 호출 위치(call instruction) 찾기

$ objdump -d hello | grep -A 30 "<main>:"
0000000000001169 <main>:
   ...
   117a:  e8 d1 fe ff ff   call   1050 <puts@plt>   # printf("hello\n") 호출
   ...
   주소:  e8 .. .. .. ..  call   ... <puts@plt>   # printf("world\n") 호출

e8 은 x86-64에서 상대 호출(call rel32) 명령의 opcode 입니다. 뒤 4바이트는 점프할 상대 오프셋이에요.

4) VIM 으로 hex 편집 → nop 으로 덮기

$ vim hello
:%!xxd                        # 화면을 hex 보기로 전환
# e8 d1 fe ff ff 위치를 찾아 (예: /e8 d1)
# 90 90 90 90 90 로 직접 수정. 90 은 NOP(아무 일도 안 하는 명령)
:%!xxd -r                     # 다시 바이너리로 되돌림 (필수!)
:wq!                          # 강제 저장

$ ./hello
world

첫 번째 printf("hello\n") 호출 명령(call)을 NOP 5개로 덮어버렸기 때문에 “hello”는 출력되지 않고 “world” 만 나옵니다.

🔑 핵심 용어:
  • NOP(No Operation, 0x90): 1바이트짜리 “아무 일 안 함” 명령. 이런 코드 변조에서 단골 손님.
  • opcode: 어셈블리 명령에 대응하는 기계어 바이트. e8 .. = call.
  • .rodata: read-only data 섹션. 문자열 상수는 거의 여기.

Practice #4 — secret_code 의 jle 패치로 “비밀번호” 우회

🇬🇧 English

  • Disassemble main and find the jle (jump if less or equal) instruction(s).

🇰🇷 한국어

  • main 함수를 디스어셈블해서 jle (작거나 같으면 점프) 명령을 찾는다.

✅ 풀이

아이디어: 프로그램은 보통 “입력값을 검사해서 틀리면 jle/je/jne 같은 조건 점프로 정답 출력을 건너뛰는” 구조입니다. 그 점프 명령을 NOP 으로 무력화하면 조건과 무관하게 “정답 경로”를 그대로 진행하게 됩니다.

$ objdump -d secret_code | grep -E "jle|<main>" -A 0
<main>:
  ....:  7e XX            jle    ....    # 8비트 상대 jle (총 2바이트)
  ....:  0f 8e XX XX XX XX jle    ....   # 32비트 상대 jle (총 6바이트)

주의: jle 은 두 가지 형태가 있습니다.

  • 짧은 형(short form): 7e XX (2바이트) → 90 90 으로 교체
  • 긴 형(near form): 0f 8e XX XX XX XX (6바이트) → 90 90 90 90 90 90 으로 교체

“길이를 그대로 유지” 라는 지시가 핵심 — 길이를 바꾸면 그 뒤 모든 명령 주소가 어긋나 프로그램이 망가집니다.

# 7e XX 를 90 90 로, 0f 8e XX XX XX XX 를 90 90 90 90 90 90 로 모두 치환
:%!xxd -r
:wq!

$ ./secret_code

Practice #5 — execvp 로 “ls -altr” 실행

🇬🇧 English

Fill in the blanks so the program executes ls -altr. Refer to man execvp.

#include <unistd.h>
int main(void) {
    char *args[] = { _____ , _____ , _____ };
    execvp( _____ , _____ );
    return 0;
}
🇰🇷 한국어

ls -altr 가 실행되도록 빈칸을 채우세요. man execvp 참고.

✅ 풀이

먼저 함수 시그니처부터 정확히 외우기:

int execvp(const char *file, char *const argv[]);
  • file : 실행할 프로그램 이름 (PATH 에서 검색). 여기선 "ls".
  • argv[] : argv[0] 부터 시작해서 마지막은 반드시 NULL. argv[0] 은 관례적으로 프로그램 이름.

완성 코드:

#include <unistd.h>     // execvp 선언이 들어 있는 헤더

int main(void) {
    // args[0] = 프로그램 이름, args[1] = 옵션, 마지막은 반드시 NULL
    char *args[] = { "ls", "-altr", NULL };

    // 첫 인자 = 실행할 파일 (PATH 검색), 둘째 인자 = argv 배열
    execvp("ls", args);

    // execvp 가 성공하면 여기로 절대 안 옴 (현재 프로세스 이미지가 ls 로 교체됨)
    // 실패했을 때만 아래 코드가 실행됨
    return 0;
}
🧠 왜 NULL 이 꼭 필요할까? C 의 배열은 길이 정보를 함께 갖지 않습니다. execvp 는 “NULL 을 만나기 전까지가 인자”라고 약속해서 길이를 알아냅니다. NULL 안 넣으면 메모리 쓰레기까지 인자로 해석해 SIGSEGV 가 납니다. 자료구조 수업에서 배운 sentinel(보초 값) 패턴과 같은 아이디어예요.

fork 와 함께 쓰는 표준 패턴 (실전):

#include <unistd.h>
#include <sys/wait.h>

int main(void) {
  pid_t pid = fork();
  if (pid == 0) {              // 자식 프로세스
    char *args[] = { "ls", "-altr", NULL };
    execvp("ls", args);    // 자식만 ls 로 교체됨
    perror("execvp");          // 여기 오면 execvp 가 실패한 것
  } else {                     // 부모 프로세스
    wait(NULL);              // 자식이 끝날 때까지 기다림
  }
  return 0;
}

⑤ Single-module → Multi-module Programming

단일 파일에 모든 함수를 다 적으면:

  • 재사용 어려움: operation_plus 함수가 다른 프로그램에서도 필요하면 매번 복사?
  • 협업 어려움: 함수 수백 개를 여러 사람이 한 파일에 작업하면 충돌 천국.

그래서 모듈화(modularity):

  • 기능별로 .c 파일을 나누고, 외부에 공개할 인터페이스만 .h 헤더에 적습니다.
  • 각 .c 를 gcc -c 로 따로 컴파일 → .o (오브젝트 파일).
  • 마지막에 gcc 로 .o 들을 링크해 실행 파일을 만듦.

헤더 파일에 들어가는 것

  • 함수 프로토타입(prototype): int operation_plus(int, int);
  • 상수 정의: #define MY_PI 3.141592
  • 매크로 함수: #define MIN(X,Y) ((X)<(Y)?(X):(Y))
  • extern 으로 다른 파일의 전역 변수를 참조

예시 빌드 흐름

# 1) 모듈별로 컴파일 (-c → .o 만 만들고 링크 안 함)
$ gcc -c operation_main.c   # → operation_main.o
$ gcc -c operation_plus.c   # → operation_plus.o
$ gcc -c operation_minus.c  # → operation_minus.o

# 2) 링크 — 실행 파일 생성

Practice #2 — strings · nm 으로 바이너리 분석

🇬🇧 English

Use strings and nm to figure out what a program is doing.

🇰🇷 한국어

실행파일 안에 박혀 있는 “읽을 수 있는 문자열”과 “심볼 이름” 만으로 프로그램의 정체를 추측해 보세요.

✅ 풀이 — 두 명령의 의미
명령의미
strings 실행파일파일 안의 출력 가능한 문자열 시퀀스를 추출. 보통 .rodata 의 리터럴이 보임 — 프로그램이 어떤 메시지를 출력할 지, 어떤 magic string 이 박혀 있는지 한눈에 파악.
nm 실행파일오브젝트 파일의 심볼(symbol) 목록을 출력. 함수·전역변수의 이름과 타입(코드 분류 문자)을 보여줌. 디버깅 정보가 없어도 동작.

nm 결과의 분류 문자(앞 알파벳)

문자의미
T심볼이 text(코드) 섹션에 있음 → 함수
D심볼이 초기화된 data 섹션에 있음 → 초기값 있는 전역/static 변수
B심볼이 BSS(초기화 안 된 data) 섹션에 있음 → 0으로 초기화되는 전역/static
대문자/소문자대문자=외부 공개(global), 소문자=파일 내부(local)
$ strings stack | head
$ nm stack | grep -E " T | D | B "
$ man nm
$ man strings

  • 아래 명령들을 실행: 
    $ chmod ou+x ./stack         # owner+others 에 실행 권한 추가
$ sudo chown root.root stack # 소유자/그룹을 root 로
$ sudo chmod u+s stack       # SUID 비트 설정 (root 권한으로 실행되게)
  • ./stack 실행해 보고, 이 프로그램이 받아들이는 정답 문자열을 찾아내는 것이 목표.
  • strings, nm, GDB 를 조합해 분석합니다.
✅ 풀이 — 단계별 분석 흐름

0단계: SUID 비트가 왜 중요한가

🔑 SUID (Set-UID) 비트가 설정된 실행파일은 실행하는 사람과 무관하게 파일 소유자(root)의 권한으로 동작합니다. 그래서 해킹 실습에서 “비밀번호 맞추면 root shell 이 떨어진다” 같은 시나리오가 의미가 있는 거예요.

1단계: strings 로 단서 수집

$ strings stack
...
Input a string:                # 사용자에게 입력 받는 메시지
Failed to hack. Try again?     # 실패 메시지
getPasswd                      # 함수 이름?
!@#$!@#%H                      # 이상한 문자열 (encrypted?)
correct_answer                 # 변수 이름?
Processing_Passwd              # 함수 이름?
modified                       # 변수 이름?

📌 입력 → 정답 비교 → 성공/실패 분기 구조라는 게 보입니다. 단순히 !@#$!@#%H 를 입력해도 통과 안 됩니다 — 추가 분석 필요.

2단계: nm 으로 심볼의 종류 확인

$ nm stack
... T Processing_Passwd        # T → text 섹션 → 함수
... D passwd_encrypted         # D → 초기화된 data → 전역 변수
... U getPasswd                # U → undefined (외부에서 들어옴, extern)
  • passwd_encrypted 은 전역 변수 — 미리 박혀 있는 “암호화된 비밀번호”일 가능성.
  • Processing_Passwd 는 함수 — 비밀번호 처리 로직.
  • getPasswd 는 extern (다른 곳에서 가져옴) — 정의가 안 보임.

3단계: GDB 로 정적 분석

$ gdb ./stack
(gdb) b main
(gdb) r
(gdb) p (char*)passwd_encrypted   # 그냥 보면 깨진 문자열(encrypted)
(gdb) disassemble Processing_Passwd
# 13번째 줄 즈음에서 correct_answer 가 초기화되는 걸 관찰
(gdb) b Processing_Passwd
(gdb) c
(gdb) n  n  n ...                 # correct_answer 초기화 직후까지 진행
(gdb) p correct_answer
$1 = 0x... "AZSXDCFVG"     # 정답 후보 발견!

그런데 입력에 AZSXDCFVG 를 그대로 넣어도 통과가 안 됩니다. 왜냐하면 비교 대상은 modified 변수이고, modified 는 별도로 !@#$!@#% 같은 값으로 초기화되어 있기 때문이에요.

4단계: 스택 메모리 배치 확인 — buffer overflow 의 무대

(gdb) p &buffer
$2 = 0x7fff9f28ee1c
(gdb) p &modified
$3 = 0x7fff9f28ee26

두 주소의 차이: 0x7fff9f28ee26 - 0x7fff9f28ee1c = 0xA = 10 bytes.
즉, 스택에 두 변수가 나란히 잡혀 있고 buffer[0..9] 바로 다음에 modified[0..9] 가 위치합니다.

높은 주소  ┌──────────────┐
          │ char modified[10] │  ← 0x7fff9f28ee26
          ├──────────────┤
          │ char buffer[9]    │
          │ char buffer[8]    │
          │ ...               │
          │ char buffer[0]    │  ← 0x7fff9f28ee1c
낮은 주소  └──────────────┘

5단계: 익스플로잇 (Exploit) — 입력 한 줄로 modified 덮어쓰기

입력으로 받은 데이터가 buffer 에 “경계 검사 없이” 복사된다는 점을 이용해서, buffer 크기(10바이트) 를 넘는 데이터를 입력하면 그 초과분이 옆 변수 modified 를 덮어씁니다 — 이게 바로 buffer overflow.

입력해야 할 19바이트:
   [0..9]  : 아무 dummy 10바이트 (예: 0123456789)
   [10..18]: AZSXDCFVG       # 정답이 들어가야 할 자리

총 입력 = "0123456789AZSXDCFVG"
$ ./stack
Input a string: 0123456789AZSXDCFVG
# 성공 → "AZSXDCFVG" == "AZSXDCFVG" 이 되어 분기 통과
# SUID 가 걸려 있으면 root 권한 셸이 떨어짐
⚠️ 주의: 이런 식의 “인접 변수 덮어쓰기” 가 가능한 이유는 gets()·strcpy() 처럼 길이 검사를 안 하는 함수를 썼기 때문입니다. 실제 코드에서는 fgets()·strncpy() 처럼 길이를 제한하는 함수를 쓰거나, 컴파일 옵션 -fstack-protector 같은 보호 장치를 켜는 것이 정석.

6단계: 실제 사례 — CVE-2021-27363

커널의 iSCSI 모듈에서 경계 검사 누락으로 발생한 buffer overflow. 슬라이드 마지막 페이지에서 보여준 사례입니다. CVE-2021-27363 참고. 우리가 한 실습이 “장난감” 이지만 패턴은 실제 커널 취약점과 동일합니다.

Q1. (쉬움) 실행 파일에 박힌 “출력 가능한 문자열” 들을 한꺼번에 보고 싶을 때 쓰는 명령은?

Q2. (쉬움) nm 출력의 분류 문자 중 함수 를 나타내는 것은?
정답: ①. T = text(code) 섹션 = 함수. D = 초기화된 data(전역), B = BSS(0 초기화 전역), U = undefined(외부).
Q3. (쉬움) sudo chmod u+s stack 의 효과는?
정답: ②. SUID = Set-UID. owner 가 root 면 누가 실행해도 root 권한으로 돈다(보안적으로 매우 민감).
Q4. (중) 두 주소 0x7fff9f28ee26 와 0x7fff9f28ee1c 의 차이는 몇 바이트?
정답: ③. 0x26 - 0x1c = 0xA = 10. 그래서 buffer[10] 다음 자리가 modified 임을 알 수 있음.
Q5. (중) stack 프로그램을 통과시키기 위해 입력해야 할 문자열의 총 길이는?
정답: ③. buffer 의 10바이트는 아무거나 채워 넘기고, 그 뒤 9바이트가 modified 자리로 흘러들어가 정답 문자열이 되어야 함.
Q6. (중) 단답형: 본 실습에서 사용한 “경계 검사 없이 입력을 받아 인접 변수까지 덮어버리는” 버그의 일반 명칭은?
정답: buffer overflow (스택 영역에서 일어나면 stack buffer overflow). Lec10 의 런타임 버그 분류에서 “out-of-bound memory access” 의 한 종류.
Q7. (중상) nm 결과에서 U getPasswd 의 U 가 의미하는 것은?
정답: ②. U = undefined. 링커가 다른 오브젝트에서 정의를 찾아 채워주어야 합니다.
Q8. (중상) GDB 에서 가장 깊은 함수에서 bt 를 친 결과의 frame#0 은 무엇을 가리키나요?
정답: ②. frame#0 = 현재 실행 지점. 숫자가 커질수록 호출자(caller) 쪽. frame N 으로 점프해서 그 시점의 지역변수를 살펴볼 수 있어요.

  • 의존성 트리(dependency tree)가 어떻게 만들어지고, make 가 “바뀐 것만 다시 빌드”하는 원리.
  • 오픈소스 프로젝트의 일반적인 구조와 ./configure && make && sudo make install 파이프라인.
  • 자주 만나는 빌드 에러 4가지와 해결법.

① make 가 뭐길래?

🍳 비유: 라면 끓일 때 “물 끓이기 → 면 넣기 → 스프 넣기 → 계란” 순서를 외워두는 메모지가 Makefile 이고, 그 메모지대로 실행해주는 요리사가 make 입니다.

  • build automation tool — 여러 소스 파일을 어떤 순서로, 어떤 명령으로 빌드할지 자동화.
  • “어느 파일이 바뀌었는가”를 수정 시간(modification time)으로 판별해, 바뀐 것만 다시 컴파일. 큰 프로젝트일수록 시간 절약.

② Makefile 기본 문법

targetList: dependencyList
<TAB>commandList
  • targetList: 만들고 싶은 결과물(.o, 실행파일 등). 보통 한 줄에 한 개.
  • dependencyList: 그 target 을 만들기 위해 필요한 파일들. 이 파일들 중 하나라도 target 보다 최근에 바뀌었으면 다시 만든다.
  • commandList: 실제로 실행할 명령들. 반드시 줄 맨 앞이 탭(TAB) 문자여야 합니다. 스페이스 8칸으로 들여쓰면 “missing separator” 에러가 나요.
$ make                # 현재 폴더의 Makefile (또는 makefile) 사용
$ make -f mymakefile  # 특정 이름의 makefile 사용

③ 예시 — operation 프로젝트

아래 트리는 다중 모듈(main, plus, minus)로 구성된 “operation” 프로그램입니다.

                 operation (executable)
               /            |            \
   main.o              plus.o              minus.o
    /  \              /  \                /  \
 main.c main.h     plus.c plus.h    minus.c minus.h
# Makefile
operation: operation_main.o operation_plus.o operation_minus.o
	gcc -o operation operation_main.o operation_plus.o operation_minus.o

operation_main.o: operation_main.c operation_main.h
	gcc -c operation_main.c

operation_plus.o: operation_plus.c operation_plus.h
	gcc -c operation_plus.c

operation_minus.o: operation_minus.c operation_minus.h
	gcc -c operation_minus.c

# 청소용 가짜 target
clean:
	rm -f *.o operation
💡 첫 번째 target이 트리의 root(최종 결과물)여야 합니다. make 만 쳤을 때 기본으로 이 첫 번째 target 을 만들기 때문.

④ make 가 “바뀐 것만” 다시 빌드하는 원리

make 는 의존성 트리를 리프(leaf)부터 루트(root)로 거슬러 올라가며 각 노드의 수정 시간을 비교합니다. 자식 노드가 부모 노드보다 새로 수정되었다면 → 부모를 다시 만듭니다.

케이스동작
plus.c 만 수정plus.o 다시 만듦 → 그것이 operation 보다 새로워졌으므로 링크도 다시 수행
아무 것도 안 바뀜"Nothing to be done" 출력하고 끝
main.h 수정main.o 를 새로 컴파일 → 링크 다시 수행
🔍 이산수학 수업과 연결: 의존성 트리는 사실 DAG(Directed Acyclic Graph) 이며, make 가 빌드 순서를 정하는 건 위상 정렬(topological sort) 의 일종이라고 생각해도 좋습니다.

⑥ 자주 만나는 빌드 에러 4가지

Error #1 — “package not found”

configure: error: Package requirements (openssl >= 1.1) were not met:
No package 'openssl' found

해결: 의존 패키지 설치. apt-cache search openssl 로 이름 찾고 sudo apt install libssl-dev pkg-config 처럼 dev 패키지를 설치. (보통 -dev 접미사가 붙은 게 헤더/링크 정보 포함)

Error #2 — ./configure 가 없거나 실행 권한이 없음

bash: ./configure: No such file or directory
bash: ./configure: Permission denied

해결: configure.ac 가 있다면

$ autoreconf -ivf && chmod +x ./configure

autoreconf -ivf = autoconf/automake/libtool 을 자동 실행해서 configure 를 생성합니다.

Error #3 — “undefined reference to ___”

main.o: undefined reference to `sqrt'

해결: 링커 에러(linker error) — 라이브러리 누락. -lm 처럼 필요한 -l라이브러리 를 추가.

Error #4 — “fatal error: ___.h: No such file or directory”

fatal error: zlib.h: No such file or directory

해결:

  • 헤더 경로 추가: -I/path/to/include
  • 또는 dev 패키지 설치: sudo apt install zlib1g-dev

⑦ 빌드 에러 디버깅 일반 순서

  1. 스크롤 위로 올려서 가장 처음 나온 에러 메시지를 찾는다. (뒤쪽 에러는 보통 첫 에러의 “2차 피해”)
  2. 파일명과 줄 번호를 확인. Makefile / configure / 헤더 / 소스 어디서 났는가?
  3. 에러 메시지를 그대로 검색하거나 의미를 해석. 위 4가지 패턴이면 위 해결책 적용.
  4. 더 자세히 보고 싶으면 make V=1 또는 make VERBOSE=1 로 실행. configure 실패면 config.log 확인.

🧭 개념 다지기 — Host vs Target (시험에도 자주 나옴)

용어의미HW09 상황
Host (machine)컴파일러가 실행되는 컴퓨터여러분의 x86-64 Linux PC
Target (machine)컴파일 결과 실행 파일이 돌아갈 컴퓨터RISC-V 보드

🧭 한눈에 보기

  • APUE 의 목적: UNIX 표준 (ISO C, IEEE POSIX) 위에서의 시스템 프로그래밍(System Programming) 이란?
  • Linux 구조: Hardware → Kernel → System Call → Library/App.
  • System Call vs Library Function: 누가 누구를 부르는가? strace·ltrace 로 직접 확인.
  • C I/O Library: printf/scanf/fopen/fclose 같은 표준 함수가 내부적으로 read()/write() 시스템 콜로 변환됨.
  • File / File Descriptor: 파일은 “바이트의 연속”, fd 는 정수 핸들. 표준 fd 0/1/2.
  • System call: open() · close() · read() · write() · lseek() + 플래그(O_RDONLY, O_CREAT, ...).

① APUE 의 목적과 UNIX 표준

📖 APUE(Advanced Programming in the UNIX Environment) = 이 수업의 공식 교재. “UNIX 환경에서 시스템 프로그래밍을 한다는 것” 자체를 다루는 책입니다.

UNIX 의 변종(System V, BSD, Solaris, Linux, macOS 등)이 너무 많아서 “표준” 이 필요했고, 두 축이 만들어집니다.

표준역할
ISO C (= ANSI C)C 언어 자체의 표준. 우리가 작성한 C 코드가 UNIX 뿐 아니라 다양한 OS에서도 컴파일·동작하도록 이식성(portability)을 제공.
IEEE POSIX“POSIX 호환” OS 라면 반드시 제공해야 할 시스템 서비스(파일·프로세스·시그널 API 등)를 규정. Linux, macOS, BSD 가 모두 POSIX 호환.

② 시스템 프로그래밍이란?

🛠 비유: 일반 앱이 “손님” 이라면, 시스템 프로그래밍은 “주방장이 쓰는 도구를 만들거나, 주방 그 자체를 운영하는 일”입니다.

  • 성능에 민감한(performance-constrained) 소프트웨어, 다른 프로그램을 도와주는 인프라성 소프트웨어.
  • OS 자원과 시스템 콜을 직접 사용.
  • 대상: 파일·프로세스·시그널·IPC(프로세스 간 통신)·네트워크 프로그래밍.
  • 실제 예: DBMS, 컴파일러, 디버거, OS 자체, 펌웨어, 게임 엔진, 산업 자동화.

③ Linux 계층 구조

┌─────────────────────────────────────────────┐
│  Commands · Utilities · Application programs │  ← bash, vim, gcc, ./hello
├─────────────────────────────────────────────┤
│        System Call interface                 │  ← read(), write(), open(), ...
├─────────────────────────────────────────────┤
│  Kernel                                      │  ← Process / File / Memory / Device 관리
├─────────────────────────────────────────────┤
│  Hardware (CPU, Memory, Disk, Peripherals)   │
└─────────────────────────────────────────────┘
  • Kernel: OS의 핵심. 프로세스/파일/메모리/장치 관리.
  • System Call: 프로그래머가 커널에 “일 해줘” 라고 부탁할 수 있는 유일한 공식 통로.
  • Commands/Utilities/Apps: 시스템 콜을 직접 부르거나, 라이브러리 함수를 거쳐 부른다.

④ System Call vs Library Function

🔬 strace vs ltrace — 자기 눈으로 확인하기
  • strace ./prog : 프로그램이 호출한 시스템 콜을 추적해서 보여줌.
  • ltrace ./prog : 프로그램이 호출한 라이브러리 함수를 추적해서 보여줌.
같은 printf("hi") 프로그램이라도, ltrace 로는 printf 가 보이고 strace 로는 그 안에서 일어난 write(1, "hi", 2) 가 보입니다. “라이브러리 함수가 결국 시스템 콜로 변환된다”는 사실을 눈으로 확인할 수 있어요.

⑤ User Mode vs Kernel Mode

🚪 비유: 일반 시민(User Mode)이 정부 청사(Kernel)에 들어가려면 “접수창구(system call interface)”를 거쳐야만 합니다. 직접 사무실에 난입할 수는 없어요.

  • User Mode: 일반 응용 프로그램이 실행되는 모드. 권한 제한.
  • Kernel Mode: 커널 코드가 실행되는 모드. 모든 하드웨어/메모리 접근 가능.
  • System Call 호출 시 CPU 가 user → kernel 로 모드 전환(mode switching) 을 수행. 끝나면 다시 user 로.

⑦ File I/O — 표준 라이브러리 방식 (FILE*)

파일 입출력의 큰 흐름은 항상 똑같습니다: open → read/write → close.

🔹 fopen — 파일 열기

#include <stdio.h>
FILE *fp;
fp = fopen(pathname, mode);   // 실패 시 NULL 반환 → 반드시 체크!

🔹 fgets.c 예제 (한 줄씩 읽기)

#include <stdio.h>

int main(int argc, char *argv[]) {
  FILE *fp = fopen(argv[1], "r");     // 1) 열기
  if (!fp) { perror("fopen"); return 1; }

  char buf[256];
  while (fgets(buf, sizeof buf, fp)) {  // 2) 한 줄씩 (개행 포함, 마지막 NUL)
    fputs(buf, stdout);                  // 표준출력에 그대로
  }

  fclose(fp);                              // 3) 닫기 — 안 닫으면 누수
  return 0;
}

🔹 fcopy.c 예제 (파일 복사 골격)

// usage: ./fcopy src dst
FILE *src = fopen(argv[1], "r");
FILE *dst = fopen(argv[2], "w");     // "w" = 덮어쓰기 주의!

char buf[4096];
size_t n;
while ((n = fread(buf, 1, sizeof buf, src)) > 0) {
  fwrite(buf, 1, n, dst);
}
fclose(src);
fclose(dst);
💡 VIM Tip (슬라이드에 나옴): 함수 이름 위에 커서를 두고 Shift+K 를 누르면 그 함수의 man 페이지가 바로 열립니다. 시스템 콜·라이브러리 함수 시그니처 빨리 확인하기 좋아요.

⑧ 파일이란? & File Descriptor

📂 File(파일): "바이트의 연속(contiguous sequence of bytes)". OS 가 강요하는 포맷은 없고, 응용 프로그램이 그 바이트를 어떻게 해석할지 결정합니다 (txt? jpg? mp3?).

🔢 File Descriptor (fd): 정수형 핸들. open() 이 fd 를 반환하고, 이후 read/write/close 등에서 "어느 파일이냐"를 fd 로 가리킵니다. 프로세스가 종료되면 모든 fd 가 자동 close.

🔹 표준 file descriptor 세 개

fd이름매크로 (unistd.h)
0표준 입력 (stdin)STDIN_FILENO
1표준 출력 (stdout)STDOUT_FILENO
2표준 오류 (stderr)STDERR_FILENO
3 ~ N사용자가 open 한 파일들—

📊 N의 값? 슬라이드의 자체 실험: 본인 Linux 에서는 1024. 이건 시스템마다 다르고 ulimit -n 또는 getrlimit(RLIMIT_NOFILE) 로 확인 가능.

🧰 lsof (list open file): 시스템 전체에서 "현재 열려 있는 파일" 을 보여주는 명령. 어떤 프로세스가 어떤 fd 로 무엇을 열고 있는지 진단할 때 유용. $ lsof 또는 $ lsof -p PID.

🔹 open() 의 flags — 시험에 잘 나옴

접근 모드(반드시 하나 포함):

  • O_RDONLY — 읽기 전용
  • O_WRONLY — 쓰기 전용
  • O_RDWR — 읽기/쓰기

옵션 플래그 (필요 시 비트 OR):

플래그의미
O_APPEND쓰기를 항상 파일의 끝에 추가
O_CREAT파일이 없으면 새로 생성 (이때 세 번째 인자 mode 로 권한 지정 필요)

O_TRUNC이미 있는 파일이면 길이를 0으로 잘라 비움

#include <fcntl.h>
#include <unistd.h>

int fd = open("afile", O_RDWR | O_CREAT, 0644);
//    O_RDWR | O_CREAT → 읽고 쓸 수 있게, 없으면 생성
//    0644 → owner=rw, group=r, others=r  (8진수)
if (fd == -1) { perror("open"); return 1; }

char buf[100];
ssize_t n = read(fd, buf, sizeof buf);   // 실제 읽힌 바이트 수 반환
write(fd, "hi\n", 3);                      // 3바이트 쓰기
close(fd);

⑩ [ASIDE] write() — wrapper 와 실제 커널 코드

왜 반환형이 ssize_t (signed) 인가?

📐 size_t 는 unsigned 라 음수가 없습니다(0 ~ 0xFFFFFFFF...). 하지만 write() 는 실패 시 -1 을 반환해야 하므로, "-1 을 표현 가능한" signed 타입(ssize_t) 이 필요합니다.

또한 unsigned 와 signed 를 섞은 산술/비교에서 overflow / 부호 오류가 일어나기 쉬워서, 보안 취약점의 단골 원인이 됩니다.

3단계 구조

유저 프로그램
   │
   │ write(fd, buf, n)            ← 우리가 호출
   ▼
glibc write() wrapper             ← 시스템 콜 번호와 함께 trap 발생
   │
   │ syscall instruction (모드 전환)
   ▼
커널 write() 구현 (fs/read_write.c)  ← 실제 디스크 I/O 등 수행

CVE-2021-3491: Linux 커널 io_uring 의 write() 관련 부호/길이 검사 미스로 인한 권한 상승 취약점. 교재에 "이런 게 실제로 일어난다" 는 예시로 등장합니다. 굳이 외울 필요는 없지만, "unsigned 와 signed 의 경계가 보안에 큰 영향을 준다" 는 교훈은 기억해 두세요.

Q1. (쉬움) 다음 중 "POSIX 표준" 의 역할로 가장 정확한 것은?
정답: ②. C 언어 자체는 ISO C 가, OS 서비스 API 는 IEEE POSIX 가 표준화.
Q2. (쉬움) 다음 중 시스템 콜은?
정답: ③. read()·write()·open()·close() 등이 시스템 콜. 나머지는 라이브러리 함수.
Q3. (쉬움) 표준 fd 의 매핑이 옳은 것은?
정답: ②. 영원히 외울 것: 0/1/2 = stdin/stdout/stderr.
Q4. (쉬움) 단답형: 프로그램이 호출한 "시스템 콜만" 추적해서 보여주는 명령은?
정답: strace. (라이브러리 함수 추적은 ltrace.)
Q5. (중) fopen("a.txt", "w") 후 a.txt 가 이미 있던 경우 결과는?
정답: ③. "w" 는 truncate. 보존하고 싶다면 "a" 또는 "r+".
Q6. (중) open() 의 flags 에 반드시 하나는 포함되어야 하는 것은?
정답: ④. 접근 모드는 반드시 하나. 나머지는 선택적인 옵션이고 비트 OR 로 결합.
Q7. (중) open("a.txt", O_WRONLY | O_CREAT | O_EXCL, 0644) 가 "a.txt 가 이미 있을 때" 보이는 동작은?
정답: ②. O_EXCL + O_CREAT = "이미 있으면 절대 안 만들고 에러". race condition 없이 "새로 만들기" 를 보장.
Q8. (중) read()/write() 의 반환형 ssize_t 가 unsigned 가 아니라 signed 인 이유는?
정답: ②. unsigned 는 음수가 없어 "에러 표시" 불가능. -1 표현하려면 signed 필요.
Q9. (중) fopen/fread 같은 표준 라이브러리 방식과 비교한 open/read 시스템 콜 직접 사용의 특징은?
정답: ②. 라이브러리는 보통 유저 공간 버퍼링이 있어 작은 read/write 가 합쳐져 한 번에 커널로 갑니다.
Q10. (중상) 단답형: 시스템 전체에서 "지금 누가 무슨 파일을 열고 있는지" 를 보여주는 명령은?
정답: lsof (list open files). 특정 프로세스만 보고 싶다면 lsof -p PID.
Q11. (중상) 같은 printf("hi") 프로그램에 대해 strace 출력에서 가장 핵심적으로 보이는 호출은?
정답: ③. printf 는 라이브러리 함수라 strace 에는 안 보이고, 그 안에서 호출된 write() system call 이 보입니다. fd=1 이 stdout.
Q12. (중상) fd = open("log", O_WRONLY | O_CREAT | O_APPEND, 0644); 의 의미로 옳은 것은?
정답: ②. 로그 파일에 가장 적합한 조합. O_APPEND 가 멀티프로세스 환경에서도 안전한 "끝에 이어쓰기" 를 보장.
Q13. (중상) 단답형: 파일 안에서 현재 읽기/쓰기 위치(offset)를 옮기는 system call 의 이름은?
정답: lseek. 세 번째 인자 whence 는 SEEK_SET(파일 시작), SEEK_CUR(현재 위치), SEEK_END(끝) 중 하나.
Q14. (중상) 프로세스가 정상적으로 종료될 때 열려 있던 fd 들은 어떻게 되나요?
정답: ②. 프로세스 종료 시 모든 fd 가 자동 정리. 그래도 "명시적 close()" 를 코드로 적는 것이 좋은 습관.

① creat() — 파일 생성 전용

#include <sys/types.h>
#include <sys/stat.h>
#include <fcntl.h>

int creat(const char *pathname, mode_t mode);

새 파일을 만들 때 쓰는 시스템 콜. 사실 open() 의 단축형이에요:

fd = creat(pathname, mode);
// ↑ 위와 아래는 정확히 같은 동작
fd = open(pathname, O_WRONLY | O_CREAT | O_TRUNC, mode);

mode (8진수 권한):

mode의미권한 표시
0644소유자 rw, 나머지 r-rw-r--r--
0755소유자 rwx, 나머지 rx-rwxr-xr-x
0444모두 읽기만-r--r--r--

반환: 성공 시 새 file descriptor, 실패 시 -1.

💡 creat() 의 약점: 쓰기 전용으로만 열림. 읽기+쓰기 둘 다 하려면 open() 직접 쓰는 게 유연해요. 그래서 요즘 실무에서는 open() 위주.

② close() 복습

int close(int fd);
  • 명시적으로 안 닫아도 프로그램 종료 시 OS 가 모든 fd 자동 정리
  • 그래도 명시적 close 가 좋은 습관 — 자원 누수 방지, 에러 처리 명확
  • 반환: 성공 0, 실패 -1

③ read() 깊게 보기

ssize_t read(int fd, void *buf, size_t count);
인자의미
fd읽을 파일의 디스크립터
buf읽은 데이터를 저장할 메모리(버퍼)
count읽고 싶은 바이트 수

반환값의 3가지 의미:

반환의미
> 0 (count 이하)실제로 읽은 바이트 수. count 보다 작을 수도 있음 (파일 끝 가까이 / 네트워크 I/O 등)
0EOF (end of file) — 더 읽을 게 없음
-1에러 발생. errno 확인
⚠️ size_t vs ssize_t — 시험 단골 (학습서 Lec12 ⑩ 와 같은 맥락)
타입부호이유
size_tunsigned크기는 음수가 없음 (count, sizeof 결과 등)
ssize_tsignedread/write 반환값. -1 (에러) 을 표현해야 하므로 signed 필요

④ write() 복습

ssize_t write(int fd, const void *buf, size_t count);
  • 반환: 실제로 쓴 바이트 수 (count 이하), -1 에러
  • “쓴 바이트 수가 count 보다 작을 수 있다” 는 사실 → 그래서 진짜 안전한 쓰기는 루프로 처리하기도 함

⑤ lseek() — 파일 오프셋 이동

off_t lseek(int fd, off_t offset, int whence);

🍳 비유: 파일 안에서 “읽기/쓰기 커서” 의 위치를 옮기는 것. 책에서 책갈피를 다른 페이지로 옮기는 느낌.

whence의미
SEEK_SET파일 시작 기준 offset 바이트로
SEEK_CUR현재 위치 기준 offset 바이트 이동 (음수 가능)
SEEK_END파일 끝 기준 offset 바이트 (음수 가능)

오프셋의 동작:

  • 파일을 처음 열면 offset = 0 (파일 시작)
  • read/write 후엔 그만큼 자동으로 이동
  • lseek() 로 임의 위치로 점프 가능

⑥ lseek() 의 신기한 트릭 — File Hole

fd = open("file.hole", O_RDWR | O_CREAT, 0644);
write(fd, "abcdefghij", 10);         // 0~9 위치에 알파벳 소문자
lseek(fd, 40, SEEK_END);             // 끝에서 40 byte 점프 → 50 위치
write(fd, "ABCDEFGHIJ", 10);         // 50~59 위치에 대문자

결과:

오프셋    내용
 0-9      a b c d e f g h i j
10-49     \0 \0 \0 ... \0 \0      ← 빈 공간 (전부 0). 이게 "hole"
50-59     A B C D E F G H I J
🤔 File hole 의 매력: 중간이 비어 있는 큰 파일을 만들 수 있는데, 실제 디스크 공간은 거의 안 차지함 (희소 파일, sparse file). DB 나 가상 디스크 이미지가 이 트릭을 자주 씁니다.

⑦ fcntl() — 열린 파일 속성 바꾸기

int fcntl(int fd, int cmd, ...);    // 세 번째 인자는 cmd 에 따라 다름

주요 cmd:

cmd역할
F_GETFL현재 파일 상태 플래그(file status flags) 반환
F_SETFL플래그 설정 (변경 가능한 건 O_APPEND, O_ASYNC, O_NONBLOCK 만)
F_GETFDfd 플래그 가져오기
F_SETFDfd 플래그 설정 (예: close-on-exec)
F_DUPFDfd 복제

파일 상태 플래그들:

플래그의미
O_RDONLY/WRONLY/RDWR접근 모드
O_APPEND매 쓰기마다 끝에 추가
O_NONBLOCK비차단(non-blocking) 모드 — read 가 데이터 없으면 -1+EAGAIN 즉시 반환
O_SYNC쓰기가 디스크에 동기화될 때까지 대기
O_ASYNC비동기 I/O
// 현재 플래그 가져와서 O_APPEND 추가 (기존 플래그 유지)
int flags = fcntl(fd, F_GETFL);
fcntl(fd, F_SETFL, flags | O_APPEND);

⑧ 에러 처리 — errno · strerror · perror

🧭 큰 원리: 시스템 콜이 실패하면 -1 반환 + 전역 변수 errno 에 “에러 번호” 가 저장됨. 우리는 그 번호로 진짜 사유를 알아낼 수 있어요.

#include <errno.h>
#include <string.h>
#include <stdio.h>

int fd = open("no_such_file.txt", O_RDONLY);
if (fd == -1) {
    // 방법 1: errno 번호 직접 보기
    printf("errno = %d\n", errno);

    // 방법 2: strerror() 로 사람이 읽을 수 있는 메시지
    printf("%s\n", strerror(errno));

    // 방법 3: perror() — 가장 간단. 메시지 + 콜론 + errno 문자열
    perror("open");
    // 출력 예: open: No such file or directory
}
도구특징
errno (변수)마지막 에러 번호. <errno.h> 인클루드 필요
strerror(num)번호 → 메시지 문자열. <string.h>
perror("어디서")"어디서: 메시지" 형식으로 stderr 에 출력. 가장 손쉬움
⚠️ errno 의 함정: errno 는 다음 시스템 콜이 성공해도 안 지워짐. 그러므로 시스템 콜 실패 직후 곧바로 검사해야 합니다.
또 errno 검사 전에 다른 시스템 콜을 부르면 그 콜이 errno 를 덮어쓸 수 있음.

⑨ 종합 예제 — write_num.c + read_num.c

write_num.c — 난수 정수를 파일에 쓰기

#include <stdio.h>
#include <stdlib.h>     // rand, srand
#include <time.h>       // time
#include <fcntl.h>
#include <unistd.h>

int main(void) {
    srand(time(NULL));           // 시간으로 난수 시드 (매번 다른 결과)
    int num = rand();              // 0 ~ RAND_MAX 의 의사 난수

    int fd = open("num.bin", O_WRONLY | O_CREAT | O_TRUNC, 0644);
    if (fd == -1) { perror("open"); return 1; }

    write(fd, &num, sizeof(num));   // 4바이트 통째로 쓰기
    close(fd);
    printf("wrote: %d\n", num);
    return 0;
}

read_num.c — 그 파일에서 정수 읽기

int fd = open("num.bin", O_RDONLY);
if (fd == -1) { perror("open"); return 1; }

int num;
read(fd, &num, sizeof(num));         // 4바이트 통째로 읽기
close(fd);
printf("read: %d\n", num);
return 0;

실행:

$ ./write_num
wrote: 1804289383
$ ./read_num
read: 1804289383     # 같은 숫자가 나와야 정상
💡 핵심 트릭: write(fd, &num, sizeof(num)) 는 “int 변수의 주소부터 4바이트” 를 그대로 파일에 씁니다. read 도 같은 4바이트를 변수에 쓰니까 같은 값이 복원됨. 이게 binary I/O 의 기본. 문자열로 변환 안 함.

⚠️ 이식성(portability) 주의: 이 방식은 같은 컴퓨터에서만 안전. CPU 가 다른 시스템 (x86 vs ARM, little-endian vs big-endian) 으로 옮기면 깨질 수 있음.
🎲 srand(time(NULL)): time(NULL) = 1970-01-01 부터 지금까지의 초 단위 정수 (Epoch time). 매 실행마다 다른 시드. 안 쓰면 매번 같은 “난수” 수열이 나옴.

Q1. creat(pathname, 0644) 와 정확히 같은 open() 호출은?
정답: ②. creat 은 “쓰기 전용 + 없으면 생성 + 있으면 비움” 의 단축형.
Q2. read(fd, buf, 100) 이 50 을 반환했을 때 의미는?
정답: ②. 요청한 count 보다 적게 읽혔다고 에러가 아님. 파일 끝 가까이/네트워크 등에서 정상 발생.
Q3. read() 가 0 을 반환하면?
정답: ②. -1=에러, 0=EOF, >0=실제 읽은 바이트 수.
Q4. size_t 가 unsigned 이고 ssize_t 가 signed 인 이유는?
정답: ②. unsigned 는 -1 을 표현 못 함. read/write 의 에러 반환을 위해 signed 필요.
Q5. lseek(fd, 0, SEEK_END) 의 결과는?
정답: ②. 끝에서 +0 = 끝 위치. 반환값(파일 시작 기준 offset) = 파일 크기. 파일 크기 빠르게 확인하는 관용구.
Q6. file hole 에 대한 설명으로 옳은 것은?
정답: ②. 중간이 비어 있어도 디스크엔 실제로 안 차지 (sparse file). VM 디스크 이미지, DB 가 활용.
Q7. 단답형: 이미 열린 fd 의 파일 상태 플래그를 가져오는 fcntl 명령은?
정답: F_GETFL. 설정은 F_SETFL.
Q8. 다음 중 fcntl(fd, F_SETFL, ...) 로 바꿀 수 있는 플래그가 아닌 것은?
정답: ④. 접근 모드(RDONLY/WRONLY/RDWR) 는 open 시점에 결정되고 이후 변경 불가. APPEND/NONBLOCK/ASYNC 만 동적으로 토글 가능.
Q9. 시스템 콜이 실패해서 -1 을 반환했을 때 에러 사유는 어디에?
정답: ②. <errno.h> 인클루드 후 사용.
Q10. perror("open") 의 출력은?

Practice #1 — lseek2.c (다중 file hole)

🇬🇧 English

Write a program lseek2.c that creates file.hole2 with the layout below using open(), read(), write(), lseek().

🇰🇷 한국어

lseek() 으로 점프하면서 데이터 → hole → 데이터 → hole 패턴 만들기.

✅ 풀이 — lseek2.c

목표 레이아웃:

오프셋   내용
 0-9    a b c d e f g h i j
10-29   \0 ...           (hole)
30-39   K L M N O P Q R S T
40-59   \0 ...           (hole)
60-69   u v w x y z a b c d
70-89   \0 ...           (hole)
90-99   A B C D E F Z H I J
#include <fcntl.h>
#include <unistd.h>

int main(void) {
    int fd = open("file.hole2", O_RDWR | O_CREAT | O_TRUNC, 0644);
    if (fd == -1) { perror("open"); return 1; }

    // 0~9: 소문자
    write(fd, "abcdefghij", 10);

    // 30~39: 대문자 (20 byte 건너뛰기)
    lseek(fd, 30, SEEK_SET);
    write(fd, "KLMNOPQRST", 10);

    // 60~69: 소문자 알파벳 끝쪽
    lseek(fd, 60, SEEK_SET);
    write(fd, "uvwxyzabcd", 10);

    // 90~99: 대문자 (마지막은 Z 주의)
    lseek(fd, 90, SEEK_SET);
    write(fd, "ABCDEFZHIJ", 10);

    close(fd);
    return 0;
}

$ ./lseek2
$ ls -l file.hole2     # 크기 100 byte
$ od -c file.hole2     # 바이트 단위 보기 — \0 영역이 보임

Practice #3 — srand 가 있을 때 vs 없을 때

🇬🇧 English

Run write_num.c and read_num.c (from Lec13 종합 예제). Then remove srand(time(0)); and observe the difference.

🇰🇷 한국어

Lec13 종합 예제의 srand(time(0)); 줄을 제거하고 여러 번 실행해서 차이를 관찰.

✅ 풀이 — 의사 난수의 비밀

관찰 결과:

srand(time(0)) 있을 때srand 제거
1회차 실행예: 18042893831804289383
2회차 실행예: 846930886 (다름)1804289383 (같음!)
3회차 실행예: 1681692777 (다름)1804289383 (같음!)

왜? rand() 는 의사 난수(pseudo-random) 입니다. 진짜 난수가 아니라 “수학 공식으로 계산되는 수열”. 시드(seed) 가 같으면 결과 수열도 같음. 기본 시드는 1 이라서 srand 없으면 매번 같은 1804289383 부터 시작합니다.

srand(time(NULL)) = “현재 초” 를 시드로 → 매번 다른 시작점.

🎯 시험 포인트: rand() 가 매번 같은 값을 반환하는 “버그” 같은 현상을 보면, 99% 시드 문제. 보안용 진짜 난수가 필요하면 /dev/urandom 같은 OS 의 엔트로피 소스를 써야 합니다 (시스템 프로그래밍 깊이 가면 등장).

Practice #1 — my_cat.c

🇬🇧 English

Write a program that reads a file and prints its contents to the shell.

  • Name: my_cat.c
  • Takes one argument: filename
  • Use open(), read(), write(), close() — NOT fopen() family
  • Consider error handling with perror() / strerror()
🇰🇷 한국어

cat 명령처럼 동작하는 프로그램 작성. 단 표준 라이브러리(fopen) 가 아니라 시스템 콜(open/read/write/close) 만 사용.

✅ 풀이 — my_cat.c 
#include <stdio.h>
#include <stdlib.h>
#include <fcntl.h>
#include <unistd.h>
#include <errno.h>
#include <string.h>

int main(int argc, char *argv[]) {
    if (argc != 2) {
        fprintf(stderr, "Usage: %s <filename>\n", argv[0]);
        return 1;
    }

    int fd = open(argv[1], O_RDONLY);
    if (fd == -1) {
        perror(argv[1]);           // 예: "filename: No such file or directory"
        return 1;
    }

    char buf[4096];
    ssize_t n;
    while ((n = read(fd, buf, sizeof buf)) > 0) {
        write(STDOUT_FILENO, buf, n);   // fd 1 = stdout
    }

    if (n == -1) {                // read 자체 실패
        perror("read");
        close(fd);
        return 1;
    }

    close(fd);
    return 0;
}

실행:

$ gcc -o my_cat my_cat.c
$ ./my_cat hello.c               # 일반 파일
$ ./my_cat /nonexistent          # my_cat: /nonexistent: No such file or directory
💡 핵심 패턴 (read 루프): 
while ((n = read(fd, buf, sizeof buf)) > 0) {
    write(STDOUT_FILENO, buf, n);
}
read 가 0 을 반환할 때까지 (=EOF) 계속 읽고, 읽은 만큼만 정확히 write. 이게 시스템콜 I/O 의 표준 패턴.

Practice #2 — Linux 핵심 파일 3종 학습

🇬🇧 English

🇰🇷 한국어

리눅스 권한·인증 시스템의 뿌리가 되는 3개 파일의 구조와 역할 이해.

✅ 풀이 — 3종 파일 정리

📋 /etc/sudoers

  • “누가 sudo 를 쓸 수 있는가” 를 정의한 파일
  • 여기 등록된 사용자만 sudo 명령 으로 root 권한을 임시로 빌릴 수 있음
  • 관리자(root) 만 수정 가능. 보통 visudo 명령으로 안전하게 수정

📋 /etc/passwd — 사용자 계정 정보

각 줄이 한 사용자, 콜론(:) 으로 7개 필드 구분.

#필드예
1Usernamejaea
2Passwordx (= 실제 해시는 /etc/shadow 에)
3UID (User ID)1000 (root=0, 시스템=1~999, 일반=1000~)
4GID (Group ID)1000
5설명JaeA Lee,,,
6홈 디렉토리/home/jaea
7로그인 셸/bin/bash
jaea:x:1000:1000:JaeA Lee,,,:/home/jaea:/bin/bash

일반 사용자도 읽기 가능 (권한 644).

📋 /etc/shadow — 실제 비밀번호 (해시)

콜론으로 8개 필드 구분. root 만 읽기 가능 (권한 640 또는 600).

#필드
1Username
2Password (해시) — $id$salt$hashed 형식
3마지막 비밀번호 변경일 (1970-01-01 기준 일수)
4최소 변경 주기 (days)
5최대 비밀번호 유효 기간
6만료 경고 시작 일수
7비활성 기간
8계정 만료일

Password 필드의 $id$ 알고리즘 표:

$id$알고리즘
$1$MD5
$2a$, $2y$Blowfish
$5$SHA-256
$6$SHA-512 (현대 리눅스 기본)
🔐 왜 분리됐나? 옛날엔 /etc/passwd 에 해시도 같이 있었음. 그런데 누구나 읽을 수 있는 파일에 해시가 있으면 오프라인 무차별 대입 공격에 취약해서, 해시만 /etc/shadow 로 분리하고 root 권한 없으면 못 보게 막은 것.

🔫 execve() 어셈블리 예시 (shell code)

mov %0x0, %edx
mov %0x0, %esi
lea 0x93306(%rip), %rdi    # rdi 에 "/bin/sh" 의 주소
mov $0x3b, %eax            # 0x3b = 59 = execve 시스템 콜 번호 (x86-64)
syscall                    # 시스템 콜 실행 → /bin/sh 띄움

$rdi 가 가리키는 메모리: 0x0068732f6e69622f → 리틀 엔디안 해석: /bin/sh\0 (소문자 16진수 → ASCII 로 거꾸로 읽기).

⚠️ shell code 의 본질: 이런 어셈블리 시퀀스를 “바이너리 데이터”로 만들어 메모리에 주입하면, 적당한 조건에서 그 데이터가 코드처럼 실행됨 (학습서 Practice GDB I 의 buffer overflow + 이 어셈블리 = 진짜 익스플로잇).

참고: shell-storm.org 같은 사이트에 shell code 예제 모음 있음.

② File 과 Inode

🧐 문제 제기: 파일에는 “내용” 만 있는 게 아니라 “소유자·권한·생성시간·크기” 같은 정보도 있죠. 그건 어디에 저장되어 있을까요?

👉 답: inode 라는 별도 자료구조에 저장됩니다.

┌────────────────┐
│  파일 이름      │ ← 디렉토리 엔트리에 저장
└────┬───────────┘
     ↓ (inode 번호로 가리킴)
┌────────────────────────┐
│  inode (메타데이터)     │
│  - 소유자 / 그룹       │
│  - 권한                │
│  - 크기                │
│  - 시간 (atime/mtime/ctime)│
│  - 데이터 블록 포인터  │
└────┬───────────────────┘
     ↓
┌────────────────┐
│  실제 데이터     │
└────────────────┘
💡 흥미로운 사실: “파일 이름” 은 inode 가 아니라 디렉토리 에 저장. 같은 inode 를 여러 디렉토리 엔트리가 가리키면 그게 hard link 입니다 (뒤에서).

③ stat() / fstat() / lstat() — 파일 메타데이터 가져오기

#include <sys/stat.h>

int stat(const char *pathname, struct stat *statbuf);
int fstat(int fd,           struct stat *statbuf);
int lstat(const char *pathname, struct stat *statbuf);
함수의미
stat(path, ...)경로로 파일 정보 가져오기. 심볼릭 링크면 가리키는 대상의 정보
fstat(fd, ...)이미 열려 있는 fd 의 정보
lstat(path, ...)stat 과 같지만, 심볼릭 링크 자체의 정보 (가리키는 대상 X)

반환: 성공 0, 실패 -1.

호출 예:

struct stat sb;
if (stat("hello.c", &sb) == -1) {
    perror("stat");
    return 1;
}
printf("size = %ld bytes\n", sb.st_size);
printf("mode = %o\n", sb.st_mode & 0777);
⚠️ struct stat * 의 함정: 호출자가 먼저 구조체를 선언해두고, 그 주소를 넘겨야 함. stat 이 내부에서 malloc 해주는 게 아니에요. Lec12 의 read/write 처럼 “버퍼는 호출자가 준비, 시스템 콜은 그 버퍼를 채움” 패턴.

자료 슬라이드의 따옴표 친절히 짚어준 “not in the case of the file content modification” 은 “ctime 은 단순 내용 변경 외에도 권한 변경 시에도 바뀐다” 는 뉘앙스.

정답: ③. PDF 의 핵심 문장: “There is no distinction to the Linux kernel whether this data is text or binary.”
Q2. 파일의 메타데이터(소유자·권한·크기·시간)는 어디에 저장?
정답: ②. inode 에 저장. 파일 이름만 디렉토리에 있고 inode 번호로 매핑.
Q3. stat() 과 lstat() 의 차이는?
정답: ②. 심볼릭 링크 다룰 때 핵심 차이.
Q4. 단답형: 이미 열린 fd 의 메타데이터를 얻는 함수는?
정답: fstat(fd, &sb).
Q5. struct stat 의 st_mtime 이 갱신되는 경우는?
정답: ②. mtime = modification time = 내용 변경. atime=접근, ctime=상태(권한 등) 변경.
Q6. st_ctime 의 의미로 옳은 것은?
정답: ②. ctime 의 c 는 “change of status” — 권한·소유자·hardlink 개수 등 메타 변경. creation time 이 아님이 시험 함정.

정답: ②. -s 가 symbolic 옵션. 안 붙이면 hard link.
Q8. hard link 와 file 복사의 가장 큰 차이는?
정답: ②. 슬라이드 핵심: “Making a hard link is not the same as copying a file.”
Q9. 원본 파일이 삭제됐을 때 깨지는 것은?
정답: ②. 심볼릭 링크는 “경로 문자열” 만 저장하므로 대상이 사라지면 broken. 하드 링크는 inode 를 직접 가리켜서 원본 이름이 지워져도 inode 가 살아 있어 동작.
Q10. ls -l 의 첫 글자가 d 인 파일은?
정답: ②. d = directory. 디바이스는 b 또는 c.
Q11. /dev/sda (디스크) 의 파일 타입은?
정답: ②. 디스크는 고정 블록 단위 I/O → block special. 터미널은 character special.
Q12. 프로세스 간 통신(IPC)용 파일 타입은?
정답: ②. FIFO 는 첫 글자 p (pipe). Socket 은 네트워크용.

정답: 파일(file). “Everything is a file.” 디스크·키보드·네트워크 모두 file 인터페이스로 통일.
Q14. sparse file 의 hole 영역은 st_blocks 에 카운트되나?
정답: ②. st_blocks 는 “실제로 디스크에 할당된 블록 수”. hole 은 0 으로 채워진 척하지만 디스크에는 안 적혀 있어서 카운트 X. 그래서 st_size 와 st_blocks × 블록크기 가 다를 수 있음 = sparse file 판별 트릭.

Practice #1 — sh.c 로 disas / disas /m / ni 비교

🔧 1단계: 소스 작성

// sh.c — shell 을 띄우는 가장 짧은 C 프로그램
#include <unistd.h>
#include <stdlib.h>

int main(void) {
    // execve("/bin/sh", NULL, NULL) 의 가장 흔한 형태.
    // execl 은 가변 인자, 마지막은 반드시 (char *)NULL.
    execl("/bin/sh", "sh", (char *)0);
    return 0; // execl 이 성공하면 여기까진 절대 안 옴
}
$ gcc -g -o sh sh.c    # -g : gdb 가 소스 라인까지 추적할 수 있도록 디버그 심볼 포함
💡 왜 execl 뒤에 코드를 두면 안 되는가? execve 계열은 "지금 프로세스의 메모리 이미지를 새 프로그램으로 통째로 교체"합니다. 성공하면 이전 코드는 메모리에서 사라지므로 return 0; 은 도달 불가능. 학습서 Lec9 의 fork+exec 패턴과 같은 개념.

🔬 2단계: gdb 안에서 차례차례 실행

$ gdb sh
(gdb) b main            # main 진입점에 breakpoint
(gdb) r                 # 실행 → main 들어가자마자 멈춤
(gdb) disas             # 현재 함수(main)의 어셈블리만 전부 출력
(gdb) disas /m          # /m = mixed → C 소스 라인과 어셈블리를 섞어 보여줌

🧐 disas 와 disas /m 의 차이

명령결과언제 쓰나
disas순수 어셈블리만최적화 후 흐름만 빠르게 확인할 때
disas /mC 라인 옆에 그 줄에서 만들어진 어셈블리들이 묶여서 보임"이 C 한 줄이 몇 개 어셈블리로 변환됐나?" 보고 싶을 때 (-g 빌드 필수)

🐢 3단계: ni 로 어셈블리 한 칸씩 (vs n)

(gdb) b 4               # execl 호출 줄에 멈추도록
(gdb) c                 # continue → 거기까지 달려감
(gdb) disas /m          # 멈춘 시점 컨텍스트 다시 보기
(gdb) ni                # next instruction — 어셈블리 1개 실행
(gdb) ni                # 또 1개
(gdb) disas /m          # 어디까지 왔는지 다시 확인
명령단위
n (next)C 소스 한 줄 단위 — 함수 호출 안으로 들어가지 않음
ni (next instruction)어셈블리 1개 단위 — 어떤 일이 1 instruction 단위로 벌어지는지 보고 싶을 때

⚠️ ni 는 한 줄을 끝내는 데 어셈블리 여러 개가 필요할 때 도움이 됩니다. 그러나 어셈블리만 보면서 변수 추적이 어려워지므로, 의심되는 한 줄에서만 짧게 쓰는 게 정석.

Practice #2 — disas 결과를 옮긴 shell.s 작성 + as + ld

🧠 아이디어

Practice #1 에서 본 sh 의 디스어셈블 결과를 그대로 옮겨 적어 어셈블리 소스 파일 (shell.s) 을 만들고, gcc 없이 어셈블러(as) 와 링커(ld) 만으로 실행 파일을 만들어 봅니다. Lec9 의 gcc 4단계(전처리 → 컴파일 → 어셈블 → 링크) 중 뒤쪽 두 단계만 직접 수행하는 셈.

🔧 shell.s (x86-64 / GAS 문법 — AT&T 스타일, % 와 $ 사용)

// shell.s — sh 프로그램을 disassemble 한 결과를 손으로 옮김
.global _start

_start:
    mov     $0, %rdx                 # execve 의 envp = NULL
    mov     $0, %rsi                 # execve 의 argv = NULL (간단 버전)
    lea     msg(%rip), %rdi          # execve 의 첫 인자 = "/bin/sh" 주소
    mov     $59, %rax                # execve 의 syscall 번호 (x86-64) = 59
    syscall                          # 시스템콜 진입 → shell 띄움

msg:
    .ascii  "/bin/sh\0"              # NUL 종료 문자열

🔨 어셈블 + 링크

$ as -o shell.o shell.s    # GNU assembler → 오브젝트 파일
$ ld -o shell  shell.o     # GNU linker → 실행 파일
$ file shell               # ELF 64-bit, statically linked... 가 찍히면 성공
$ ./shell                  # 진짜로 sh 가 떠야 함
sh-5.1$                    # 새 shell 프롬프트 (Ctrl-D 로 빠져나오기)
💡 왜 main 이 아니라 _start 인가? 평소엔 gcc 가 C 런타임(crt1.o)을 넣고 main 으로 점프해 줍니다. 여기선 그런 런타임 없이 ld 가 직접 실행하므로 커널이 처음 진입할 심볼 인 _start 를 우리가 만들어 줘야 해요. 학습서 Lec9 에서 본 gcc 의 "보이지 않는 도움" 의 정체를 직접 마주하는 순간.
⚠️ 어셈블리 문법 함정 — 어셈블러마다 표기가 다릅니다.
  • as (GAS) 는 AT&T 문법 — mov $59, %rax 처럼 "src, dst" 순서, 레지스터 앞 %, 즉시값 앞 $
  • Intel 문법은 "dst, src" 순서 — mov rax, 59
objdump -d 의 기본 출력도 AT&T 입니다. objdump -M intel -d 로 바꿔 볼 수도 있어요.

Practice #3 — 기계어 추출 → C 의 함수 포인터로 "데이터 실행"

🧠 핵심 아이디어 (Lec14 의 본질)

실행 파일에 들어있는 .text 섹션의 바이트들 은 우리 눈에는 "데이터" 처럼 보이지만, CPU 가 RIP(instruction pointer) 로 그 주소를 가리키는 순간 코드 가 됩니다. 이 실습은 그 "데이터 ↔ 코드" 의 경계선이 얼마나 얇은지 직접 보여줍니다.

🔧 1단계: shell 의 .text 만 뽑기

$ objdump -D shell                       # 모든 섹션 디스어셈블 (눈으로 .text 확인)
$ objcopy -O binary --only-section=.text \
          shell shell.text                # .text 섹션만 raw 바이너리로 저장
$ hexdump -C shell.text                   # 추출된 기계어를 16진수로 보기

00000010  3d ...                                            |=...|
도구역할

objcopy -O binary --only-section=.textELF 헤더·심볼·메타 다 떼고 "기계어 바이트만" 추출

🔧 2단계: shellcode.c — 함수 포인터로 데이터를 호출

// shellcode.c
#include <stdio.h>
#include <string.h>

// Practice #3 의 hexdump 결과를 옮겨 적은 기계어 바이트 배열
// (예시 — 실제 본인 빌드 결과 그대로 옮기세요)
unsigned char code[] = {
    0x48, 0xc7, 0xc2, 0x00, 0x00, 0x00, 0x00,
    0x48, 0xc7, 0xc6, 0x00, 0x00, 0x00, 0x00,
    // ... 이어서 /bin/sh\0 까지
};

int main(void) {
    // 1) code[] 의 주소를 "인자 없음, 반환 없음" 함수 포인터로 캐스팅
    void (*fp)(void) = (void (*)(void)) code;

    // 2) 함수처럼 호출 → CPU 가 code[0] 부터 instruction 으로 해석
    fp();

    return 0;
}

🔨 빌드 — -z execstack 이 핵심

$ gcc -z execstack -o shellcode shellcode.c
$ ./shellcode
sh-5.1$
⛔ -z execstack 옵션이 없으면 "Segmentation fault". 최신 리눅스는 보안상 스택/데이터 영역은 실행 불가(NX bit, no-execute) 로 표시합니다. 그러면 데이터 영역에 놓인 기계어를 호출하는 순간 CPU 가 권한 위반을 일으켜 커널이 SIGSEGV 를 보냅니다.

-z execstack 은 "이 실행파일은 스택/데이터를 실행 가능하게 매핑해라" 라고 링커에게 부탁하는 옵션 — 실험·교육 용으로만 사용해야 합니다. 실제 운영 서버에선 절대 켜지 마세요.
💡 학습서 다른 섹션과의 연결
  • Practice GDB I 의 buffer overflow + 이 "기계어 주입" 을 합치면 진짜 shell code 익스플로잇 — 이 흐름이 HW11 (gdb4 root escalation) 의 뼈대입니다.
  • Lec14 ① 의 "Linux 는 텍스트/바이너리 구분 안 함" 이 여기서 "데이터 = 실행 가능" 으로 이어집니다.

② File Access Permission 9bit — 의미 정리

비트심볼일반 파일에서디렉토리에서

0200S_IWUSR소유자 쓰기소유자가 파일 생성/삭제 가능

💡 디렉토리의 권한은 일반 파일과 의미가 완전히 다릅니다 — 시험 단골.
  • 일반 파일: r=내용 읽기, w=내용 쓰기, x=실행 가능
  • 디렉토리: r=이름 목록 읽기 (ls), w=파일 생성/삭제, x=그 안으로 들어가기 (cd, 그 안의 파일 열기)
특히 디렉토리에 r 만 있고 x 가 없으면 ls 는 이름만 보이고 ls -l 의 자세한 정보가 모두 "?" 로 가려집니다. 디렉토리에 x 만 있고 r 이 없으면 이름 목록은 못 보지만, 정확한 이름을 안다면 cat dir/file.txt 처럼 직접 접근은 가능합니다.

🛤 경로 탐색의 함정

/home/me/work/hello.c 를 열려면 /, home, me, work 모든 부모 디렉토리에 x 권한이 있어야 합니다. 중간 한 곳이라도 x 없으면 Permission denied. 이 규칙이 종종 "분명 chmod 했는데 왜 안 되지?" 의 원인.

③ Real UID vs Effective UID — 같은 사람, 다른 신분증

🪪 일상 비유

회사에 출입증과 임시 권한 카드가 있다고 상상하세요.

  • Real UID (RUID) = 항상 내 이름이 적힌 사원증. "나는 진짜로 누구인가".
  • Effective UID (EUID) = 지금 이 작업에 대해 시스템이 권한을 판단할 때 보는 카드. 평소엔 사원증과 같지만, 특정 프로그램을 실행하면 "관리자 임시 권한 카드" 로 잠깐 바뀝니다.

🧩 누가 EUID 를 바꾸는가? — setuid 비트 (S_ISUID)

실행 파일에 setuid 비트가 켜져 있으면, 그 프로그램이 실행될 때 EUID 가 그 파일의 소유자(st_uid) 로 바뀝니다.

비트심볼효과
04000S_ISUID실행 시 EUID = 파일 소유자의 UID. ls -l 에서 ---s------
02000S_ISGID실행 시 EGID = 파일 소유자 그룹의 GID. ------s---
01000S_ISVTXsticky bit (디렉토리에서 의미 있음 — 본인 파일만 삭제 가능)

📝 대표 사례 — passwd 명령

$ ls -l /usr/bin/passwd
-rwsr-xr-x 1 root root  ... /usr/bin/passwd
   ▲
   └── 's' 가 보임 — root 소유 + setuid 켜짐

일반 사용자가 본인의 비밀번호를 바꾸려고 passwd 를 실행하면 — 일반 사용자는 /etc/shadow 에 쓰기 권한이 없어야 정상이지만 — passwd 의 setuid 덕분에 EUID 가 잠깐 root 가 되어 /etc/shadow 에 쓸 수 있게 됩니다. 끝나면 다시 원래 EUID 로 돌아옴.

⚠️ setuid 가 root 인 프로그램은 잠재적 폭탄. 그 프로그램에 버그가 있으면 일반 사용자가 root 권한을 빼앗을 수 있습니다 (학습서 HW11 (gdb4) 의 본질이 정확히 이것 — root 소유 + setuid 가 켜진 취약 프로그램 → root shell 획득).

🔍 파일 접근 권한 판정 흐름 (커널 입장)

1) EUID == 0 (root)?            → 무조건 허용
2) EUID == st_uid (소유자)?     → owner 비트(rwx) 검사
3) EGID == st_gid (그룹)?       → group 비트(rwx) 검사
4) 위 모두 아님 → other 비트(rwx) 검사

④ unlink() — 파일 삭제는 사실 "이름 떼기"

#include <unistd.h>
int unlink(const char *pathname);
// 성공 0, 실패 -1 (errno set)

동작:

  1. 해당 inode 의 st_nlink (하드 링크 카운트) 를 1 감소시킴.
  2. st_nlink == 0 이 되었고, 아무도 열고 있지 않으면 → inode 와 데이터 블록 해제 (진짜 삭제).
  3. 아직 누군가가 open 으로 열고 있다면 → inode 는 살아 있고 그 fd 는 계속 사용 가능. 모든 fd 가 닫힐 때 진짜 삭제.
💡 "이름은 사라졌는데 파일은 살아있다" 의 정체. 리눅스에서 rm 은 사실 unlink() 호출 한 번입니다. 디렉토리에서 그 inode 를 가리키는 이름 엔트리만 떼는 것 — 그래서 하드 링크가 다른 곳에 있거나 어떤 프로세스가 fd 로 들고 있으면 데이터는 여전히 디스크에 존재합니다.

⑤ access() — "내가 이 파일에 권한이 있나?" 미리 확인

#include <unistd.h>

mode 상수의미
R_OK읽을 수 있나?
W_OK쓸 수 있나?

⑥ chown / lchown — 소유자/그룹 바꾸기

#include <unistd.h>
int chown(const char *pathname, uid_t owner, gid_t group);
int lchown(const char *pathname, uid_t owner, gid_t group);  // symlink 자체
int fchown(int fd,                uid_t owner, gid_t group);  // fd 기반

-1 을 owner 또는 group 에 넘기면 "그 항목은 그대로 두기" 의미.

💡 일반 사용자는 보통 chown 으로 다른 사용자에게 파일을 넘길 수 없습니다 (root 권한 필요). 그룹은 자기가 속한 그룹들 사이에서만 바꿀 수 있어요.

⑧ [Note] TOCTTOU — Time-Of-Check to Time-Of-Use

🚨 문제 시나리오 (root 권한으로 도는 utility)

// chmod_for_root_files.c — root 가 소유한 파일에만 chmod 해주는 utility (라고 의도)
if (stat(filename, &statbuf) == 0
    && statbuf.st_uid == 0) {        // ← Time Of Check (root 소유 확인)
    chmod(filename, 0666);          // ← Time Of Use (그 파일 권한 변경)
}

⏱ 공격자의 트릭 — 그 사이에 끼어들기

           [Root utility]                      [Attacker]
1.  stat(filename) → root 소유 확인 ✓
                                          rm filename            # unlink — 이름 떼기
                                          ln -s /etc/shadow filename  # symlink 로 바꿔치기
2.  chmod(filename, 0666)               
    └── 실제로는 /etc/shadow 가 666 으로 바뀜!

1번에서 본 파일과 2번에서 만지는 파일이 이름은 같지만 다른 객체 가 되어버린 것입니다. 이름(path) 만으로 객체를 식별한 게 화근.

    fchmod(fd, 0666);                       // 같은 fd 로 변경
close(fd);
⚠️ 왜 fd 가 안전한가? fd 는 이름이 아니라 inode 자체를 가리킵니다. 중간에 공격자가 이름을 바꿔치기 해도 우리가 들고 있는 fd 는 처음 열었을 때의 그 inode 를 계속 참조합니다. 학습서 Lec14 ② 의 "이름은 디렉토리, 데이터는 inode" 구조를 정확히 이용한 방어법.
💡 TOCTTOU 는 시험 단골 — "TOC vs TOU 사이에 공격자가 무엇을 했나" 그리고 "왜 fchmod 가 chmod 보다 안전한가" 가 자주 묻습니다. 참고: 2005년 USENIX FAST 의 "TOCTTOU Vulnerabilities in UNIX-Style File Systems" 논문이 슬라이드의 출처.

⑨ truncate() — 파일 길이를 강제로 맞추기

#include <unistd.h>
int truncate (const char *path, off_t length);
int ftruncate(int fd,                off_t length);
  • length 가 현재 파일 크기보다 작으면 → 뒷부분 잘려나감.
  • length 가 더 크면 → 그 길이까지 0 으로 확장 (file hole 생길 수 있음 — 학습서 Lec13 ④ 의 lseek hole 과 짝지어 이해).

⑩ chdir / fchdir / getcwd — 작업 디렉토리

#include <unistd.h>
int chdir (const char *path);   // 셸의 cd 와 같은 일

① Process Start — main(argc, argv) 는 누가 채워주나

int main(int argc, char *argv[]);
인자의미
argcargument count — 명령행 인자 개수 (프로그램 이름 포함)
argv[]argument vector — 각 인자를 가리키는 문자열 포인터 배열

흐름:

  1. 셸이 fork + execve("./prog", argv, envp) 호출 (학습서 Lec9 의 fork/exec).
  2. 커널이 새 프로그램을 메모리에 매핑하고 C Start-Up Routine (_start) 으로 점프.
  3. C 런타임(crt1.o) 이 argc/argv/envp 를 정리해 main 호출.
  4. main 의 반환값은 다시 C 런타임이 받아서 exit 에 넘김.
💡 학습서 Practice (Lec14) 의 _start 가 정확히 이 진입점입니다. 평소엔 우리가 그걸 안 보지만 직접 만들어 보면 "main 은 시스템콜이 아니라 그냥 C 함수" 라는 사실이 뚜렷해져요.

② Process Termination — 종료의 5가지 방법

✅ 정상 종료 3가지

방법특징
return from mainC 런타임이 받아 exit 호출. 가장 흔한 패턴
exit(status)<stdlib.h>. cleanup 수행: stdio 버퍼 flush, 열린 stream 닫기, atexit 핸들러 실행
_exit(status)<unistd.h>. cleanup 안 함 — 즉시 커널에게 끝났다고 알림

❌ 비정상 종료 2가지

방법의미

🔍 exit vs _exit — 시험 단골

// 1) exit — cleanup 포함
printf("Hello");   // stdout 버퍼에만 들어가 있을 수 있음
exit(0);             // 버퍼 flush + stream close + atexit → "Hello" 출력됨

// 2) _exit — cleanup 안 함
printf("Hello");
_exit(0);            // 버퍼 그대로 사라짐 → "Hello" 출력 안 될 수도
⚠️ fork 직후 자식 프로세스 에서 종료할 때는 _exit 를 쓰는 게 정석입니다. 부모와 자식이 stdio 버퍼를 공유한 상태에서 자식이 exit 하면 같은 버퍼가 부모/자식 양쪽에서 두 번 flush 되어 "출력 중복" 이 발생할 수 있어요.

③ atexit() — 종료 핸들러 등록

#include <stdlib.h>
int atexit(void (*function)(void));

정상 종료(return/exit) 직전에 자동 실행할 함수를 등록. 여러 번 호출하면 역순(stack 처럼 LIFO) 으로 실행됩니다.

void bye_a(void) { puts("bye A"); }
void bye_b(void) { puts("bye B"); }
int main(void) {
    atexit(bye_a);   // 1번째 등록
    atexit(bye_b);   // 2번째 등록
    puts("in main");
}                       // 출력: in main, bye B, bye A  (역순)
💡 주의: _exit 로 종료하면 atexit 핸들러도 호출 되지 않습니다. cleanup 자체를 건너뛰니까.

④ Environment Variables — environ 전역 배열

extern char **environ;   // 마지막은 NULL 인 문자열 포인터 배열

// 예: environ 가 가리키는 메모리
//   environ[0] → "USER=wjsong"
//   environ[1] → "HOME=/home/prof/wjsong"
//   environ[2] → "PATH=/bin:/usr/local/bin:..."
//   ...
//   environ[N] → NULL

char *getenv(const char *name);
int    putenv(char *string);              // "NAME=VAL" 한 문자열 통째로
int    setenv(const char *name,

getenv("PATH")값 문자열 포인터 반환 (없으면 NULL)반환된 포인터를 수정/free 하지 말 것

setenvname·value 따로 받음. 내부에서 복사하므로 호출자가 안전하게 변경/해제 가능대신 잦은 호출 시 메모리 누수 가능성
unsetenv해당 변수 제거없는 변수면 그냥 0 반환
💡 잘 쓰던 변수가 안 보일 때: 자식 프로세스에서 setenv 해도 부모 셸의 환경은 안 바뀝니다. 셸의 export 명령은 셸 자신의 environ 을 직접 수정하는 빌트인 — cd 가 빌트인이어야 하는 이유와 정확히 같은 패턴.

⑦ Signal — 소프트웨어 인터럽트

🛎 비유

당신이 책상에서 코드를 짜고 있을 때, 누군가 어깨를 톡 치며 메모를 건네면 잠깐 멈추고 그 메모에 적힌 일을 처리한 뒤 다시 원래 일로 돌아오죠. 시그널(signal) 은 운영체제가 프로세스에게 그렇게 "메모를 건네는" 메커니즘입니다.

🌱 시그널은 언제 생기나?

  • 터미널 입력: Ctrl-C → SIGINT, Ctrl-Z → SIGTSTP
  • 하드웨어 예외: divide-by-zero → SIGFPE, 잘못된 메모리 접근 → SIGSEGV
  • 다른 프로세스가 kill(pid, signo) 로 보냄
  • 소프트웨어 조건: 알람 만료 → SIGALRM, 깨진 파이프 → SIGPIPE, 자식 종료 → SIGCHLD

🛡 시그널을 받으면 할 수 있는 3가지

  1. 기본 행동(default) — 시그널마다 정해진 동작 (종료/무시/정지/계속)
  2. 무시(ignore) — SIG_IGN 으로 등록. 단, SIGKILL/SIGSTOP 은 무시 불가
  3. 잡기(catch) — 내가 만든 함수(handler) 를 실행

⑧ signal() — 핸들러 등록

#include <signal.h>
typedef void (*sighandler_t)(int);
sighandler_t signal(int signum, sighandler_t handler);

handler 에 넘길 수 있는 것:

  • SIG_DFL — 기본 행동으로 되돌리기
  • SIG_IGN — 무시
  • 내 함수 포인터 — 잡기

📌 예제 1 — SIGINT 잡기

#include <signal.h>
#include <stdio.h>
#include <unistd.h>

void on_int(int sig) {                  // 핸들러: int 인자 = 시그널 번호
    printf("received SIGINT (%d). bye!\n", sig);
    _exit(0);
}

int main(void) {
    signal(SIGINT, on_int);              // Ctrl-C 누르면 on_int 호출
    while (1) pause();                   // 시그널 올 때까지 무한 대기
}
함수역할
pause()시그널이 도착할 때까지 잠듦. 시그널 핸들러가 끝나면 깨어남

Practice #1 — prac_atexit.c (atexit 매크로 양산)

🔧 매크로 함수의 정체

슬라이드 코드는 DEFINE_EXIT(x) 라는 매크로 함수(function-like macro) 를 정의해서 비슷한 함수 여러 개를 한 줄씩으로 만듭니다. 패턴은 보통 이런 식:

// prac_atexit.c (슬라이드 코드의 일반적인 패턴)
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

// ## 은 토큰 연결 연산자 — exit_ 와 x 를 붙여서 새 식별자 만들기
// # 은 토큰을 문자열로 만드는 연산자 ("exit_x" 같이)
#define DEFINE_EXIT(x)                          \
    void exit_##x(void) {                       \
        printf("in %s\n", #x);              \
    }

DEFINE_EXIT(a)   // → void exit_a(void) { printf("in %s\n", "a"); }
DEFINE_EXIT(b)   // → void exit_b(void) { printf("in %s\n", "b"); }
DEFINE_EXIT(c)   // → void exit_c(void) { printf("in %s\n", "c"); }

int main(void) {
    // 등록 순서: a → b → c    /    호출 순서: c → b → a  (역순 = LIFO)
    atexit(exit_a);
    atexit(exit_b);
    atexit(exit_c);

    printf("in main\n");
    return 0;   // return 이 끝나면 C 런타임이 자동으로 exit() 호출
}

Practice #2 — prac_env (env 명령 직접 만들기, 5줄 챌린지)

🧠 한 줄 비유

셸의 env 명령은 그저 "내 프로세스가 갖고 있는 environment list 를 줄줄이 출력" 하는 프로그램입니다. 우리는 그 list 에 extern char **environ 으로 직접 접근할 수 있으니 — for 루프 한 번이면 끝.

🔧 최소 구현 (main 만 5줄)

// prac_env.c
#include <stdio.h>

extern char **environ;   // 학습서 Lec16 ④

int main(void) {
    for (char **e = environ; *e != NULL; e++)
        puts(*e);          // 한 줄 출력 + 자동 \n
    return 0;
}

Practice #3 — prac_signal.c (signal 핸들러 매크로 + __FUNCTION__ 트릭)

🔧 매크로 + 함수 이름 자기 참조

이번엔 시그널 핸들러들을 매크로로 양산합니다. 매크로 패턴:

// prac_signal.c (슬라이드 패턴)
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <signal.h>

#define DEFINE_SIGHAND(x)                                         \
    void sh_##x(int sig) {                                         \
        /* __FUNCTION__ 는 현재 함수의 이름 = "sh_INT" 같은 문자열       */  \
        /* (char*)&( ((char*)__FUNCTION__)[2] ) = 그 문자열의 3번째 글자부터의 주소 */  \
        /* 즉 "sh_INT" 에서 [2]번째 글자 '_' 부터 가리키는 포인터 → "_INT" */  \
        printf("caught signal: %s (signo=%d)\n",                      \
               (char*)&(((char*)__FUNCTION__)[2]), sig);                \
    }

DEFINE_SIGHAND(INT)    // → void sh_INT(int sig) { ... }
DEFINE_SIGHAND(USR1)   // → void sh_USR1(int sig) { ... }

int main(void) {
    signal(SIGINT,  sh_INT);
    signal(SIGUSR1, sh_USR1);

    printf("my pid = %d\n", getpid());

    // 자기 자신에게 SIGUSR1 보내고, 잠시 후 SIGINT 보내기
    kill(getpid(), SIGUSR1);
    sleep(1);
    kill(getpid(), SIGINT);

    return 0;
}

🔬 __FUNCTION__ 트릭 풀어보기

표현의미
__FUNCTION__현재 함수의 이름 문자열 (예: "sh_INT"). 컴파일러가 자동 생성
(char*)__FUNCTION__그 문자열의 첫 글자 주소 (그냥 캐스팅)
((char*)__FUNCTION__)[2]3번째 글자 (0부터 세서 2번째). "sh_INT" 라면 '_'
&(((char*)__FUNCTION__)[2])그 글자가 있는 주소
(char*)&...그 주소를 다시 char* 로 → 그 위치부터의 부분 문자열
💡 요약: (char*)&(((char*)__FUNCTION__)[2]) = "현재 함수 이름에서 3번째 글자부터의 부분 문자열". 함수 이름 prefix "sh" 두 글자를 떼고 "_INT" / "_USR1" 같은 식으로 출력하기 위한 트릭. 슬라이드의 짧은 데모 코드(printf("%s\n", &str[3]) 등) 가 이걸 보여주려는 의도예요.

📚 같이 봐야 할 매뉴얼

$ man 2 signal       # 시그널 핸들러 등록
$ man 2 kill         # 시그널 보내기

caught signal: _USR1 (signo=10)

⚠️ 주의: sh_INT 핸들러 안에서 그냥 return 하면 main 으로 복귀해서 다음 줄이 실행됩니다. main 에서 kill(SIGINT) 직후 return 0 이면 정상 종료. 하지만 만약 SIGINT 의 기본 동작(프로세스 종료)을 원하면 핸들러 안에서 exit(0) 명시.

#!/bin/bash
# calculator_2019012345.sh

# 5개 연산 함수 정의
addition() {
  echo $(($1 + $2))
}
subtraction() {
  echo $(($1 - $2))
}
multiplication() {
  echo $(($1 * $2))
}
division() {
  echo $(($1 / $2))
}
modulo() {
  echo $(($1 % $2))
}

# 1) 인자 개수 검사
if [ "$#" -ne 3 ]; then
  echo "Error: exactly 3 arguments required (operand1 operator operand2)"
  exit 1
fi

# 2) 인자 이름 붙이기
op1="$1"
op="$2"
op2="$3"

# 3) 연산자별 분기 → 해당 함수 호출
case "$op" in
  "+") addition       "$op1" "$op2" ;;
  "-") subtraction    "$op1" "$op2" ;;
  "x") multiplication "$op1" "$op2" ;;
  "/") division       "$op1" "$op2" ;;
  "%") modulo         "$op1" "$op2" ;;
  *)
    echo "Error: invalid operator '$op'"
    exit 1
    ;;
esac

int main(int argc, char *argv[]) {
    if (argc != 2) {
        fprintf(stderr, "usage: %s <path>\n", argv[0]);
        return 1;

    if (lstat(path, &sb) == -1) {
        perror("lstat");
        return 1;
    }

    // 여기서부터 stat 명령과 똑같이 12개 항목 출력
    // (다음 ②~⑤ 단계 참고)

}

// PDF 힌트가 ctime() 이라서 이걸 그대로 활용 (간단 버전)
// ctime 은 끝에 '\n' 을 자동으로 붙이므로, 우리 printf 의 줄바꿈은 빼야 함

char *atime_s = ctime(&sb.st_atime);
char *mtime_s = ctime(&sb.st_mtime);
char *ctime_s = ctime(&sb.st_ctime);

printf("Access: %s", atime_s);  // 끝에 이미 \n 있음
printf("Modify: %s", mtime_s);
printf("Change: %s", ctime_s);
⚠️ ctime() 의 함정: 반환 문자열의 끝에 이미 \n 이 붙어있습니다. printf("...%s\n", ctime(...)) 처럼 쓰면 빈 줄이 한 줄 더 들어가서 채점 불일치. 위처럼 \n 없이 %s 만 쓰세요.
💡 실제 stat 의 출력 형식은 더 화려합니다 (예: 2026-06-04 10:11:25.123456789 +0900). 본인 환경의 출력에 더 가깝게 맞추려면 strftime(buf, sizeof buf, "%Y-%m-%d %H:%M:%S.%%09ld %z", localtime(&t)) + st_atim.tv_nsec 까지 다뤄야 합니다. PDF 가 "ctime() 그냥 써도 된다" 고 명시했으니 일단 ctime 으로 제출 → 시간 항목 9점만 제대로 채점되면 OK.

# 5가지 케이스를 진짜 stat 과 비교
$ for p in Desktop /usr/bin/stat /bin/vim /dev/sda /dev/ttyS0; do

diff 결과가 아무 출력이 없으면 완벽 일치. 라인 단위로 차이가 나오면 그 줄만 맞추면 됩니다.

⚠️ 자주 하는 실수 — 채점 0점 직행 5종
  1. stat() 을 씀 → 심볼릭 링크 케이스 깨짐. 반드시 lstat().
  2. tab 위치/공백 개수 다름 → diff 가 줄 단위 불일치로 잡음. 진짜 stat 의 출력에서 tab 인지 space 인지 cat -A 로 확인.
  3. ctime 뒤에 \n 추가 → 빈 줄 한 줄 더 들어감.
  4. readlink 후 NUL 미부착 → File 줄에 쓰레기 문자 섞임.
  5. 장치 파일에서 0 nlink 출력 등 형식 자릿수 안 맞음 → %5u 자릿수 맞추기.
