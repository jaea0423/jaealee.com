03프록시(BurpSuite)·파이어폭스 설정

1차시 · 교안 14~21쪽

BurpSuite 프록시 설정 (4단계)

화면 세부: 시작 창은 Burp Suite Community Edition v2021.10 · Disk-based project는 Professional 전용이라 Temporary project 선택 · Proxy Listeners 표(Running ☑ · Interface 127.0.0.1:8080 · Certificate Per-host)에서 행을 선택하면 주황색 표시 → 왼쪽 Edit

왜 8081로 바꾸나

BurpSuite 기본 포트는 8080인데, 실습 포트 목록(3306, 8000, 8100, 8200, 8080, 8081)에 8080도 들어 있어 교안은 프록시를 8081로 옮깁니다. Bind to address는 Loopback only(127.0.0.1)입니다.

파이어폭스 설정 (3단계)

Step할 일
1오른쪽 위 ≡ 메뉴 → 설정 → ‘일반’ 맨 아래 네트워크 설정 → 설정 버튼
2수동 프록시 설정 → HTTP 프록시 127.0.0.1, 포트 8081 → 확인 (HTTPS에도 사용은 체크 안 함)
3주소창 about:config → ‘위험을 감수하고 계속’ → network.proxy.allow_hijacking_localhost 값을 true로
Step 3을 하는 이유

파이어폭스는 기본적으로 “localhost, 127.0.0.1/8, ::1에 대한 연결은 프록시를 사용하지 않습니다”. 실습 서버가 localhost라서, 이 제한을 풀어야 BurpSuite가 요청을 가로챌 수 있습니다.

BurpSuite 프록시 동작

이후 그 브라우저의 모든 HTTP 요청을 BurpSuite가 가로챕니다(intercept). 주소를 입력해도 BurpSuite가 붙잡고 있어 화면이 안 나오고, Proxy › Intercept에서 ‘Intercept is on’을 눌러 off하면 대기하던 요청이 전달되어 화면이 나타납니다. (Forward = 한 건 보내기, Drop = 버리기)

05HTTP 구조 — 요청·응답·메서드·상태코드

교안 퀴즈 출제1차시 · 교안 25~33쪽
정의 (교안)

HTTP(HyperText Transfer Protocol): WWW에서 HTML 문서 같은 리소스를 가져올 수 있게 해 주는 프로토콜. 요청(Request)–응답(Response) 구조, 무상태 방식(Stateless).

왜 “무상태”인데 로그인이 유지되나

HTTP 자체는 이전 요청을 기억하지 않아서, 서버가 발급한 세션 ID를 쿠키(Cookie: JSESSIONID=…)로 매 요청마다 함께 보내 상태를 흉내 냅니다. 교안 21·28쪽 요청의 Cookie 헤더가 바로 그것입니다. 2주차 STRIDE 실습의 “세션 탈취”가 노리는 값도 이 쿠키입니다.

교수님 설명 · 1차시 18:29~19:33

HTML뿐 아니라 이미지·CSS·자바스크립트 등 모든 웹 리소스가 HTTP 요청으로 전송된다. HTTP는 무상태(Stateless) — 서버는 각 요청을 독립적으로 처리하고 이전 요청을 기억하지 않으므로 인증·세션 정보는 요청 메시지 안에 항상 명시적으로 담겨야 한다. HTTP는 TCP/IP 위에서 동작하고 위로는 HTML·CSS·JS와 연결되는 네트워크와 애플리케이션을 잇는 중간 계층.

BASE64 인코딩

이진 데이터를 텍스트 형식으로 변환하는 방식.

  • 데이터를 6비트 단위로 나눠 64개 문자(A–Z, a–z, 0–9, +, /)로 표현 (26 = 64)
  • 6비트씩 처리하므로 모자란 비트는 0으로 패딩하고, =로 표현
  • 사용 이유: 이메일·JSON·XML 같은 텍스트 전송 환경에서 안전하게 사용, 전송 중 데이터 손상·인코딩 문제 방지
  • 교안 예: Hello, World! → SGVsbG8sIFdvcmxkIQ==

package com.example.board.entity;

import jakarta.persistence.*;
import lombok.Getter;
import lombok.NoArgsConstructor;
import lombok.Setter;
import java.time.LocalDateTime;

@Entity                 // 이 클래스 = DB 테이블 하나 (JPA가 테이블과 연결)
@Getter @Setter         // Lombok: getter/setter 자동 생성
@NoArgsConstructor      // JPA가 객체를 만들 때 필요한 기본 생성자
public class Post {
    @Id                                                   // 기본 키(PK)
    @GeneratedValue(strategy = GenerationType.IDENTITY)   // 값은 DB가 자동 증가로 채움
    private Long id;

    private String title;
    private String content;
    private LocalDateTime createdAt = LocalDateTime.now();  // 객체 생성 시각을 저장

Javaservice/PostService.java
@Service                                   // 비즈니스 로직 계층으로 등록
public class PostService {
    private final PostRepository postRepository;

    public PostService(PostRepository postRepository) {   // 생성자 주입: 스프링이 Repository를 넣어 줌
        this.postRepository = postRepository;
    }

    public List<PostResponseDto> getAllPosts() {         // 목록 조회
        return postRepository.findAll().stream()
                .map(PostResponseDto::new)             // Entity 하나씩 DTO로 변환
                .collect(Collectors.toList());
    }

    public PostResponseDto getPostById(Long id) {          // 상세 조회
        Post post = postRepository.findById(id).orElseThrow();   // 없으면 예외
        return new PostResponseDto(post);
    }

    public PostResponseDto createPost(PostRequestDto requestDto) {   // 작성
        Post post = new Post();
        post.setTitle(requestDto.getTitle());
        post.setContent(requestDto.getContent());
        postRepository.save(post);                         // INSERT → id 자동 부여
        return new PostResponseDto(post);
    }

    @Transactional                                         // 메서드 끝에 변경 내용이 DB에 반영됨
    public PostResponseDto updatePost(Long id, PostRequestDto requestDto) {   // 수정
        Post post = postRepository.findById(id).orElseThrow();
        post.setTitle(requestDto.getTitle());             // save() 호출 없이 값만 바꿔도 반영
        post.setContent(requestDto.getContent());
        return new PostResponseDto(post);
    }

    public void deletePost(Long id) {                   // 삭제
        postRepository.deleteById(id);
    }
}

import 줄(dto·entity·repository·Service·Transactional·List·Collectors)은 교안 13쪽과 같아 생략했습니다. updatePost에 save()가 없는 이유를 주석으로 남긴 것은, 수정 메서드만 @Transactional이 붙은 까닭이 거기에 있어서입니다. (@Transactional 안에서 조회한 엔티티의 값이 바뀌면 트랜잭션이 끝날 때 JPA가 UPDATE를 자동 실행 — 변경 감지)

@Transactional이 updatePost에 꼭 필요한 이유 — 교수님이 설명하신 내용 아님

변경 감지(Dirty Checking)는 트랜잭션 안에서 조회한 엔티티의 값이 바뀌었을 때, 트랜잭션이 끝나며(커밋) UPDATE 문을 보내는 방식입니다. 그래서 save()가 없는 updatePost가 동작하려면 트랜잭션이 필요합니다. 동시 접근 문제는 트랜잭션의 격리 수준이나 잠금(Lock)이 다루는 부분이라, 교수님 말씀(동시 접근 무결성)은 트랜잭션의 한 측면을 말씀하신 것으로 보는 것이 맞습니다. 예상 문제 Q5 답도 이 기준입니다.
