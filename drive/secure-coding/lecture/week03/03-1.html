03프록시(BurpSuite)·파이어폭스 설정

1차시 · 교안 14~21쪽

BurpSuite 프록시 설정 (4단계)

화면 세부: 시작 창은 Burp Suite Community Edition v2021.10 · Disk-based project는 Professional 전용이라 Temporary project 선택 · Proxy Listeners 표(Running ☑ · Interface 127.0.0.1:8080 · Certificate Per-host)에서 행을 선택하면 주황색 표시 → 왼쪽 Edit

왜 8081로 바꾸나

BurpSuite 기본 포트는 8080인데, 실습 포트 목록(3306, 8000, 8100, 8200, 8080, 8081)에 8080도 들어 있어 교안은 프록시를 8081로 옮깁니다. Bind to address는 Loopback only(127.0.0.1)입니다.

파이어폭스 설정 (3단계)

Step할 일
1오른쪽 위 ≡ 메뉴 → 설정 → ‘일반’ 맨 아래 네트워크 설정 → 설정 버튼
2수동 프록시 설정 → HTTP 프록시 127.0.0.1, 포트 8081 → 확인 (HTTPS에도 사용은 체크 안 함)
3주소창 about:config → ‘위험을 감수하고 계속’ → network.proxy.allow_hijacking_localhost 값을 true로
Step 3을 하는 이유

파이어폭스는 기본적으로 “localhost, 127.0.0.1/8, ::1에 대한 연결은 프록시를 사용하지 않습니다”. 실습 서버가 localhost라서, 이 제한을 풀어야 BurpSuite가 요청을 가로챌 수 있습니다.

BurpSuite 프록시 동작

이후 그 브라우저의 모든 HTTP 요청을 BurpSuite가 가로챕니다(intercept). 주소를 입력해도 BurpSuite가 붙잡고 있어 화면이 안 나오고, Proxy › Intercept에서 ‘Intercept is on’을 눌러 off하면 대기하던 요청이 전달되어 화면이 나타납니다. (Forward = 한 건 보내기, Drop = 버리기)

05HTTP 구조 — 요청·응답·메서드·상태코드

교안 퀴즈 출제1차시 · 교안 25~33쪽
정의 (교안)

HTTP(HyperText Transfer Protocol): WWW에서 HTML 문서 같은 리소스를 가져올 수 있게 해 주는 프로토콜. 요청(Request)–응답(Response) 구조, 무상태 방식(Stateless).

왜 “무상태”인데 로그인이 유지되나

HTTP 자체는 이전 요청을 기억하지 않아서, 서버가 발급한 세션 ID를 쿠키(Cookie: JSESSIONID=…)로 매 요청마다 함께 보내 상태를 흉내 냅니다. 교안 21·28쪽 요청의 Cookie 헤더가 바로 그것입니다. 2주차 STRIDE 실습의 “세션 탈취”가 노리는 값도 이 쿠키입니다.

HTTP 흐름 — TCP 위에서

번호위치동작
1서버 HTTP 부모 프로세스 → TCP연결대기
2브라우저 HTTP → TCP연결요청
3~5브라우저 ↔ 서버SYN → SYN/ACK → ACK (3-way handshake, TCP 연결설정)
6·7양쪽 TCP → HTTP연결확인 / 연결승락
8서버HTTP 부모 프로세스가 자식 프로세스 생성
9~12브라우저 → 서버HTTP요청 → DATA(Request) → ACK → 자식 프로세스로 전달
13자식 프로세스 ↔ 저장소웹 페이지 읽기
14~17서버 → 브라우저HTTP응답 → DATA(Response) → ACK → 브라우저 HTTP로 전달
18~21브라우저 ↔ 서버FIN → ACK → FIN → ACK (4-way handshake, TCP 연결해제)

HTTP Request Method

Method설명
GET자원 요청(기본값). 파라미터를 URL에 붙여 전송 → 보안이 필요 없는 짧은 데이터, 북마크가 필요한 경우. 예: test.jsp?id=kim&pass=1234
POST자원 요청. 파라미터를 Body에 붙여 전송 → 데이터가 많거나 비밀 정보를 보낼 때. 예: <form method="post">
HEADHTTP Header 정보만 요청 — 메타 정보 획득, 링크 유효성 검사
PUTURL 자원을 생성하도록 요청 — 파일 업로드 가능
DELETEURL 자원을 삭제하도록 요청 — 파일 삭제 가능
TRACE진단 목적 — 서버가 받은 요청을 응답 바디에 그대로 돌려보냄
OPTIONS응답 가능한 HTTP Method를 요청
GET 예시가 보여주는 것

교안의 GET 예시 test.jsp?id=kim&pass=1234는 비밀번호가 URL에 그대로 드러나는 형태입니다. 그래서 비밀 정보는 POST로 보내라는 것이 교안의 기준입니다.

HTTP Response Status Code

401 vs 403 (교안 강조)

401 = 인증 실패(누구인지 모름, 로그인 필요) · 403 = 인가 실패(누구인지는 알지만 권한 없음).

06데이터 인코딩 — BASE64 · URL

교안 퀴즈 출제1차시 · 교안 35~44쪽

인코딩(Encoding): 데이터를 특정 규칙에 따라 다른 형식으로 변환하는 과정.

필요한 이유내용
데이터 전송다양한 환경에서 데이터가 올바르게 해석되도록 보장
보안 강화입력값을 안전하게 처리해 XSS, HTML 인젝션 등 취약점 예방
호환성서로 다른 시스템 간 데이터 포맷 차이로 인한 오류 방지
인코딩 vs 암호화

인코딩: 형태만 바꾼 것이라 누구나 디코딩(역변환) 가능 · 암호화: 보안 목적으로 변환하며 복호화에 키가 필요. 뒤의 Basic 인증 실습이 이 차이를 보여줍니다.

BASE64 인코딩

이진 데이터를 텍스트 형식으로 변환하는 방식.

  • 데이터를 6비트 단위로 나눠 64개 문자(A–Z, a–z, 0–9, +, /)로 표현 (26 = 64)
  • 6비트씩 처리하므로 모자란 비트는 0으로 패딩하고, =로 표현
  • 사용 이유: 이메일·JSON·XML 같은 텍스트 전송 환경에서 안전하게 사용, 전송 중 데이터 손상·인코딩 문제 방지
  • 교안 예: Hello, World! → SGVsbG8sIFdvcmxkIQ==
변환 과정 직접 따라가기 — 교수님이 설명하신 내용 아님

교안 예시 문자열을 제가 비트 단위로 계산해 그린 것입니다. 결과는 교안 값과 같습니다.

URL 인코딩 (퍼센트 인코딩)

URL에서 쓸 수 없는 문자를 안전하게 표현하려고 특정 문자를 % + ASCII 16진수 코드로 바꾸는 방식.

이유예
URL에서 특별한 의미를 가진 문자 처리 (공백, ?, &, #, /, : 등)…?query=hello world → …?query=hello%20world
비 ASCII 문자(한글·일본어 등) 처리 — URL은 ASCII만 허용한글 → %ED%95%9C%EA%B8%80 (UTF-8 한 글자 = 3바이트)
보안·일관성 — <, >, " 등은 보안 문제 유발 가능<script>alert(1);<script> → %3Cscript%3Ealert%281%29%3B%3Cscript%3E
문자 유형예인코딩 값
공백(공백)%20
예약문자 (URL 구조에서 사용)? & # / :%3F %26 %23 %2F %3A
특수문자! @ $ + =%21 %40 %24 %2B %3D
비 ASCII 문자한 · 日%ED%95%9C · %E6%97%A5
인코딩 불필요영문 대소문자, 숫자, - _ . ~그대로

BurpSuite로 BASE64 디코딩 실습

교안 42쪽 캡처 결과가 다른 이유

BurpSuite로 URL 인코딩/디코딩

  1. Decoder 입력창에 http://httpbin.org/basic-auth/user/passwd → Encode as → URL → %68%74%74%70%3a%2f%2f… (BurpSuite는 영문자까지 모든 글자를 %16진수로 바꿈)
  2. 인코딩된 문자열 → Decode as → URL → 원래 주소로 복원

교안 44쪽 설명문은 “Encode as … 선택”이라고 적혀 있지만 그림은 Decode as → URL을 가리킵니다. 디코딩 단계이므로 Decode as가 맞습니다.

package com.example.board.entity;

import jakarta.persistence.*;
import lombok.Getter;
import lombok.NoArgsConstructor;
import lombok.Setter;
import java.time.LocalDateTime;

@Entity                 // 이 클래스 = DB 테이블 하나 (JPA가 테이블과 연결)
@Getter @Setter         // Lombok: getter/setter 자동 생성
@NoArgsConstructor      // JPA가 객체를 만들 때 필요한 기본 생성자
public class Post {
    @Id                                                   // 기본 키(PK)
    @GeneratedValue(strategy = GenerationType.IDENTITY)   // 값은 DB가 자동 증가로 채움
    private Long id;

    private String title;
    private String content;
    private LocalDateTime createdAt = LocalDateTime.now();  // 객체 생성 시각을 저장
}

// ── 요청 DTO: 클라이언트가 보내는 값만 담음 (id·createdAt은 받지 않음)
@Getter
public class PostRequestDto {

    private String content;
}

@Getter
public class PostResponseDto {
    private Long id;
    private String title;
    private String content;
    private LocalDateTime createdAt;

    public PostResponseDto(Post post) {     // Entity → DTO 변환
        this.id = post.getId();
        this.title = post.getTitle();
        this.content = post.getContent();
        this.createdAt = post.getCreatedAt();
    }
}

    public List<PostResponseDto> getAllPosts() {         // 목록 조회
        return postRepository.findAll().stream()
                .map(PostResponseDto::new)             // Entity 하나씩 DTO로 변환
                .collect(Collectors.toList());
    }

    public PostResponseDto getPostById(Long id) {          // 상세 조회
        Post post = postRepository.findById(id).orElseThrow();   // 없으면 예외
        return new PostResponseDto(post);
    }

    public PostResponseDto createPost(PostRequestDto requestDto) {   // 작성
        Post post = new Post();
        post.setTitle(requestDto.getTitle());
        post.setContent(requestDto.getContent());
        postRepository.save(post);                         // INSERT → id 자동 부여
        return new PostResponseDto(post);
    }

    @Transactional                                         // 메서드 끝에 변경 내용이 DB에 반영됨
    public PostResponseDto updatePost(Long id, PostRequestDto requestDto) {   // 수정
        Post post = postRepository.findById(id).orElseThrow();
        post.setTitle(requestDto.getTitle());             // save() 호출 없이 값만 바꿔도 반영
        post.setContent(requestDto.getContent());
        return new PostResponseDto(post);
    }

    public void deletePost(Long id) {                   // 삭제
        postRepository.deleteById(id);
    }
}

import 줄(dto·entity·repository·Service·Transactional·List·Collectors)은 교안 13쪽과 같아 생략했습니다. updatePost에 save()가 없는 이유를 주석으로 남긴 것은, 수정 메서드만 @Transactional이 붙은 까닭이 거기에 있어서입니다. (@Transactional 안에서 조회한 엔티티의 값이 바뀌면 트랜잭션이 끝날 때 JPA가 UPDATE를 자동 실행 — 변경 감지)

12용어 정리

프록시Proxy

브라우저와 서버 사이에서 요청·응답을 대신 주고받는 중계 서버. BurpSuite는 이를 이용해 요청을 가로채고 수정.

WASWeb Application Server

비즈니스 로직을 실행하는 서버. 예: Tomcat, WebLogic, JBoss, JEUS.

무상태Stateless

서버가 이전 요청을 기억하지 않는 방식. 상태 유지는 쿠키·세션으로 보완.

3-way / 4-way handshakeTCP

연결설정 SYN→SYN/ACK→ACK / 연결해제 FIN→ACK→FIN→ACK.

상태코드Status Code

1xx 정보 · 2xx 성공 · 3xx 리다이렉션 · 4xx 요청 오류 · 5xx 서버 오류. 401 인증 실패, 403 인가 실패.

인코딩 vs 암호화Encoding vs Encryption

인코딩은 누구나 되돌릴 수 있음, 암호화는 키가 있어야 복호화.

BASE64Base64

6비트씩 64개 문자로 표현하는 이진→텍스트 인코딩. 모자란 자리는 =.

URL 인코딩Percent-Encoding

URL에 못 쓰는 문자를 %+16진수로 표현. 공백 %20.

프레임워크 / 플랫폼Framework / Platform

개발 구조·규칙을 강제하는 라이브러리 / 앱이 실행되는 환경.

자동 설정Auto Configuration

Spring Boot가 추가한 의존성을 보고 필요한 설정을 자동으로 해 주는 기능.

CRUDCreate · Read · Update · Delete

POST · GET · PUT · DELETE에 대응하는 기본 데이터 조작.

Entity / DTOEntity / Data Transfer Object

DB 테이블과 연결되는 클래스 / 요청·응답 데이터를 담는 클래스.

JPAJava Persistence API

자바 객체와 DB 테이블을 연결(ORM)하는 표준. Spring Data JPA가 Repository를 자동 구현.
