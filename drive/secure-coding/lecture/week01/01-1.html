01현대 애플리케이션 보안 과제

이미지 자료 있음

개인정보보호위원회가 제공한 최근 3년간 개인정보 유출사고 그래프와 2020년 한국 기업 데이터 유출현황·침해 발생원인 그래프가 교안 6~7쪽에 있습니다. 구체적인 수치는 이미지로만 제공되어 텍스트로 추출되지 않았으니, 정확한 수치가 필요하면 01-1-slides1.pdf 6~7쪽을 직접 확인해 주세요.

4대 보안 과제 (출처: 라드웨어)

과제핵심 내용
봇 관리인터넷 트래픽의 52%가 봇에 의한 통신이며 그중 절반이 악성 봇. 기업의 79%는 악성봇과 정상봇을 구분하지 못함. 악성봇은 네트워크 트래픽 낭비, 개인정보 수집, 캡챠 우회, 크리덴셜 스터핑, 봇 공격 등을 유발.
API 보안IoT·클라우드·웹·모바일 등 다양한 환경의 애플리케이션이 API로 연결되어 리소스와 정보를 공유. API 취약점을 이용한 인젝션, 파라미터 조작, 공격 사이트 리다이렉트 등이 발생.
서비스 거부(DoS)애플리케이션 계층 DoS는 오래된 방식이지만 여전히 효과적. HTTP/S 플러드, 슬로우로리스, LOIC, 버퍼오버플로우, 브루트포스가 대표 벡터이며 IoT 봇넷이 자주 동원됨.
지속적인 보안DevOps의 빠른 개발·롤아웃 방법론은 애플리케이션을 계속 수정하지만 보안을 놓치기 쉬움. 완성된 서비스의 취약점 개선은 더 어렵기 때문에 AI 기반 위협 분석·실시간 정책 최적화가 필요.

해결 방안 3가지

애플리케이션 보안 과제를 해결하기 위한 접근으로 SW개발보안 프로세스(DevSecOps), 보안내재화(Security by Design), Zero Trust 3가지가 제시됩니다.

(1) SW개발보안 프로세스

개발자의 실수·논리적 오류로 발생하는 보안약점을 최소화하기 위해 SW개발 각 단계별로 보안 활동을 수행합니다. 현재는 소스코드 구현단계를 중심으로 적용됩니다.

단계보안 활동
요구사항분석요구사항 중 보안요구사항 식별
설계보안요구사항과 위협에 대한 보안통제를 고려한 위협원 도출, 외부 인터페이스 식별, 보안통제 수립
구현표준코딩 정의서 및 SW개발보안 가이드 준수 개발, 소스코드 보안약점 진단(도구 활용)
테스트실행코드 보안취약점 진단(동적분석: 스캐닝, 모의해킹 테스트 등)
용어 구분

보안취약점(Vulnerability): 해킹 등 실제 보안사고에 이용되는 SW 보안약점. 보안약점(Weakness): 보안취약점의 근본 원인이 되는 SW상의 허점·결점·오류.

(2) 보안내재화 — DevSecOps

애플리케이션 수명주기에 따라 반복·지속적으로 보안 제어를 수행하는 것이 필수입니다. 아래는 가트너가 제시한 DevSecOps 10단계 순환 흐름입니다.

단계내용
1. Plan보안 담당 부서, DevSecMetrics 관리 방안·보안위협 모델링 수립·보안 관련 플랫폼 교육 계획
2. Create통합개발환경에 보안 관련 요소 적용
3. VerifySAST(정적 애플리케이션 보안 테스트)/DAST(동적)/IAST(상호작용)/SCA(소프트웨어 구성분석)
4. Preprod카오스 몽키 테스트, 퍼징 테스트, 서비스를 가속화하고 실행 중인 컨테이너에 대한 자동화된 침투테스트 동작 확인
5. Release적용되는 소프트웨어·애플리케이션에 대한 서명 진행
6. Prevent서명에 대한 확인, checksum 등 무결성 검사, 심층 방어 조치 수립
7. DetectRASP(런타임 애플리케이션 자가 보안), UEBA(사용자 행동 분석, 내부위협·표적공격·금융사기 탐지)
8. Respond보안 요건 재검토 및 조정, RASP/WAF(웹 방화벽) 등 런타임 환경 보안 위협 차단
9. PredictIoC(침입흔적), TI(위협정보), STIX·TAXII(위협정보 표현/전송 규격) 등으로 예상 가능한 위협 예측
10. Adapt보안 담당 부서가 보안 위협에 대응해 나가기 위한 계획 수립
이미지 자료 안내

교안 13~16쪽 "DevSecOps AWS 아키텍처" 4개 슬라이드는 이미지(아키텍처 다이어그램)만 있고 텍스트가 추출되지 않았습니다. 정확한 구성은 01-1-slides1.pdf 13~16쪽을 직접 참고해 주세요.

(3) 보안내재화 — Security by Design

제품 설계 단계부터 보안을 고려해 알려진 취약점을 조기에 효과적으로 제거하는 것을 의미합니다.

위협 모델링(Threat Modeling) 6단계

순서내용
1각각의 직무 전문가들로 팀 구성
2다루어질 위협 환경의 범위 설정
3특정 애플리케이션 또는 시스템에 대한 모든 가능한 위협 식별
4각 위협을 위험 수준에 따라 순위를 매김
5완화 조치를 결정하고 실행
6모든 조사 결과와 조치를 문서화

(4) Zero Trust

"아무것도 신뢰할 수 없다"는 가정하에 사용자 및 다양한 정보를 바탕으로 최소한의 권한과 세밀한 통제를 지속적으로 수행하는 보안 활동입니다. 핵심 문구는 "Never Trust, Always Verify".

제로 트러스트 보안 모델 — BeyondCorp 3대 컴포넌트

기기 인증

접근을 요청하는 호스트가 신뢰할 수 있는 기기인지 확인. 디바이스 인벤토리 DB로 모든 접속 기기를 식별하고, 디바이스 인증서로 유일하게 식별.

사용자 인증

정상 임직원인지, 소속 그룹·업무를 확인. User/Group DB 연동, SSO 포털을 통한 Two-factor(계정+OTP 또는 물리적 키) 인증.

접근제어 엔진

기기·사용자·취약점 정보를 상관 분석해 접근 허용 여부 결정. 관측데이터(취약점 스캔 결과 등)와 입력데이터(기기 소유자, 접속 가능 사용자·그룹 등)로 보안등급평가를 거침.

02사고사례로 보는 시큐어코딩

결함(Defects), 실수(Mistake), 장애(Failure), 결점(Fault), 오류(Error), 문제(Problem), 버그(Bugs) — 교안에는 정의 없이 "시큐어한 소프트웨어"와 관련된 용어로만 나열되어 있습니다. 서로 넘나들며 쓰이는 표현들이라는 정도로만 우선 참고하세요.

사례 1 — 스마트 컨트랙트 오버플로우

오버플로우(Overflow)란 숫자가 표현 가능한 최대치 이상으로 증가하는 것을 말합니다. 이더리움 스마트컨트랙트 개발 언어인 솔리디티(Solidity)에서 시큐어코딩 없이 작성된 transferProxy 함수가 대표 사례입니다.

SoliditytransferProxy (취약 코드)
// 문제함수: transferProxy — 잔액 검증 로직에 오버플로우 취약점 존재
function tranferProxy(address _from, address _to, uint256 _value, uint256 _feeSmt,
    uint8 _v, bytes32 _r, bytes32 _s) public transferAllowed(_from) return (bool) {
    if(balances[_from] < _feeSmt + _value) revert();   // _feeSmt+_value가 오버플로우되면 이 검증이 무력화됨
    uint256 nonce = nonces[_from];
    bytes32 h = keccak256(_from, _to, _value, _feeSmt, nonce);
    if ( _from != ecrecover(h,_v,_r,_s)) revert();
    if(balance[_to] + value < balances[_to]
        || balances[msg.sender] + _feeSmt < balances[msg.sender]) revert();
    balances[_to] += _value;
    Transfer(_from, _to, _value);
    balances[msg_sender] += _feeSmt;
}
취약점 포인트

_feeSmt + _value가 자료형의 최댓값을 넘으면 값이 0 근처로 돌아가(오버플로우) balances[_from] < _feeSmt + _value 검증을 우회할 수 있습니다. 이더리움 개발에서는 이를 막기 위해 SafeMath 라이브러리(오버플로우·언더플로우 자동 검증)를 사용합니다.

사례 2 — OSS(Open Source Software) 취약점: Log4j

교안 내용

2021년 11월 24일 Alibaba Cloud 보안팀이 처음 발견한 Apache Log4j(자바 로깅 라이브러리) 원격 코드 실행 취약점. 공격자가 로그 메시지를 제어할 수 있는 서버에서 임의 코드를 실행할 수 있었고, Log4j를 사용하는 대부분의 앱이 영향을 받았습니다. (출처: 2023년 SW보안약점 진단원 보수교육)

사례 3 — 공급망 해킹과 SBOM

취약한 소프트웨어를 쓰는 기관·기업에 피해를 주기 쉬운 공급망 해킹이 유행하고 있으며, 공격자는 소프트웨어의 개발-설계-구현-유통 단계별 허점을 노립니다.

SBOM (Software Bill of Materials)

소프트웨어를 빌드할 때 사용된 여러 컴포넌트와 공급망 관계를 형식에 맞춰 기록한 것. 생산·소비·운영 주체가 공급망을 깊이 이해하고, 알려진/새로운 취약점과 위협을 추적해 확산을 저지하기 위한 목적입니다.

1차시 요약 (교안 원문)

현대 애플리케이션의 보안과제에서 API 보안과 지속적인 보안을 학습함. 해결 방안으로 SW개발보안, 보안 내재화, 제로트러스트 보안모델 적용을 학습함. 개발자의 사소한 실수로 발생할 수 있는 보안 사고를 예방하기 위해 시큐어코딩이 필수 보안 활동임을 학습함.

06OWASP TOP 10

시험 가능성 높음

OWASP(Open Web Application Security Project)는 웹 애플리케이션에서 가장 치명적인 보안 취약점 10가지를 정리해 주기적으로 발표합니다. 웹 개발자·보안 전문가·조직이 위협 예방에 활용하는 핵심 지침입니다.

OWASP TOP 10 (2021)

#취약점개요대응 방안
1Broken Access Control
취약한 접근 통제		인증된 사용자도 접근이 제한된 데이터·기능에 접근 가능모든 요청 권한 확인, 최소 권한 원칙, RBAC 구현
2Cryptographic Failures
암호화 실패		보호가 안 돼 기밀 정보가 평문으로 노출HTTPS/TLS, AES·RSA 등 안전한 알고리즘, 비밀번호 해시+솔트
3Injection
인젝션 공격		악성 코드 삽입으로 DB 조작·시스템 장악(SQLi, XSS, Command Injection)입력값 검증·필터링, Prepared Statement/ORM 사용
4Insecure Design
보안 설계 미흡		보안을 고려하지 않은 설계로 취약점 발생Security by Design, 위협 모델링, 설계 반영 및 주기적 검토
5Security Misconfiguration
보안 설정 오류		기본 설정 유지, 디버그 모드 활성화 등불필요 기능 비활성화, 패치 적용, 설정파일 접근 제한
6Vulnerable and Outdated Components
취약·오래된 구성요소		패치 안 된 오래된 라이브러리·프레임워크 사용최신 버전 유지, 오픈소스 보안 이슈 확인, SBOM 관리
7Identification and Authentication Failures
인증·세션 관리 취약점		약한 비밀번호, 세션 하이재킹 등으로 인증 우회MFA, 안전한 세션 관리(토큰 만료·회수), 강력한 비밀번호 정책
8Software and Data Integrity Failures
SW·데이터 무결성 실패		무결성 미검증 코드·데이터로 악성코드 실행 가능코드 서명·무결성 검증, CI/CD 보안 강화, 서드파티 신뢰성 검토
9Security Logging and Monitoring Failures
보안 로깅·모니터링 실패		보안 이벤트 미기록·미탐지로깅+중앙화 로그관리, SIEM 도입, 인시던트 대응체계
10Server-Side Request Forgery
SSRF		서버를 이용해 내부망 스캔·외부 공격외부요청 제한(Allowlist), 입력값 검증, CSP, API 호출 제한

OWASP API Security Risk TOP 10 (2023)

#취약점개요대응 방안
1Broken Object Level Authorization
객체 수준 권한 관리 실패		사용자 권한 미검증으로 타인 데이터 조회·수정·삭제 가능요청마다 인증·권한 검사, 최소 권한 원칙, ID 기반 접근제어
2Broken Authentication
취약한 인증		인증 과정이 보호되지 않아 인증 우회·계정 탈취 가능MFA, JWT·OAuth2 등 강화된 토큰, 토큰 만료·회수 정책
3Broken Object Property Level Authorization
객체 속성 수준 권한 관리 실패		응답에서 민감 데이터 과다 노출, 속성 무단 수정 가능응답 노출 데이터 최소화, 서버 측 권한 검증 필수
4Unrestricted Resource Consumption
제한 없는 리소스 소비		과도한 요청으로 CPU·메모리·네트워크 소모(DDoS 가능)Rate Limiting, 타임아웃·최대크기 제한, 이상 트래픽 자동 차단
5Broken Function Level Authorization
기능 수준 권한 관리 실패		일반 권한으로 관리자 기능 실행, 미인가 엔드포인트 호출RBAC 적용, 모든 기능 인증·권한 검증, 미인가 요청 즉시 차단
6Unrestricted Access to Sensitive Business Flows
민감 비즈니스 흐름 무제한 접근		인증 없이 중요 프로세스 실행(예: OTP 없이 비밀번호 재설정)강력한 인증·접근제어, 워크플로우 기반 검증, 추가 보안 확인
7Server Side Request Forgery
SSRF		API를 통해 서버가 임의 외부 URL을 요청하도록 조작외부요청 차단·Allowlist, URL/IP 검증, 불필요 외부요청 최소화
8Security Misconfiguration
보안 설정 오류		기본값 사용·디버그 모드 등 설정 미흡보안정책 수립·정기점검, 최소권한 설정, 패치·디버그 로그 보호
9Improper Inventory Management

07CVE와 CWE

시험 가능성 높음

CVE (Common Vulnerabilities and Exposures)

소프트웨어·하드웨어의 보안 취약점을 표준화하여 공개하는 시스템입니다. 개발자는 이를 활용해 취약점을 사전에 예방하고 신속히 패치를 적용합니다.

순서CVE 작동 방식
1. 취약점 발견   — 보안 연구원·기업·기관이 새 취약점 발견
2. CVE 요청     — CVE Numbering Authority(CNA)에 취약점 보고
3. CVE ID 할당  — MITRE가 검토 후 CVE ID 부여
4. 공개 및 업데이트 — NVD 등에 세부정보 등록, 보안 패치·대응책 제공
CVE 예제

CVE-2022-24086 (2022.2.13 발견) — Adobe Commerce·Magento Open Source 2.3.3~2.4.3-p1. 입력 데이터 검증 미흡으로 SQL 쿼리를 조작해 임의 코드 실행·정보 탈취가 가능했던 취약점. Adobe가 보안 패치를 배포, 최신 버전 업데이트를 권장.

CWE (Common Weakness Enumeration)

미 국토안보부가 관리하며 소프트웨어·하드웨어의 보안약점을 체계적으로 정리한 공개 목록입니다.

각 교안 마지막에 포함된 퀴즈입니다. 아래 07 "예상 문제"와는 별개로, 교수님이 직접 낸 문제라 시험·과제에 참고될 가능성이 가장 높습니다.

1차시 퀴즈

1다음 중 SW개발보안 프로세스에 해당하지 않는 것은?객관식
  1. 설계
  2. 요구사항분석
  3. 테스트
  4. 배포
정답 ④ 배포SW개발보안 프로세스는 요구사항분석·설계·구현·테스트로 이루어집니다.
2제품 설계단계부터 보안을 고려해 알려진 취약점을 조기에 효과적으로 제거하는 것은?객관식
  1. DevSecOps
  2. 보안내재화
  3. 제로트러스트
  4. 보안일체화
정답 ② 보안내재화영어로 Security By Design이라고 합니다.
3'오버플로우'에 대한 설명이 맞는 것은?객관식
  1. 연산 결과가 과하게 반올림됨
  2. 연산 결과가 허용할 수 있는 범위를 벗어남
  3. 연산 결과의 부호가 역전됨
  4. 정수형과 실수형을 혼합하여 연산함
정답 ②저장할 수 있는 값의 범위를 초과하는 연산이 이루어질 때 오버플로우가 발생했다고 합니다.

2차시 퀴즈

4행정안전부 SW개발보안 가이드와 관련 없는 내용은?객관식
  1. 행정·공공기관 정보시스템 개발자 대상
  2. SW보안약점 잔존여부 진단
  3. 테스트 단계부터 SW개발 보안을 적용하기 위한 기준
  4. 진단 범위는 설계단계 산출물과 소스코드 전체
정답 ③SW개발보안 가이드는 SW개발 '단계부터' 보안을 적용하기 위한 기준을 제시합니다(테스트 단계부터가 아님).
5클라우드 서비스 보안 인증에서 소프트웨어 보안과 관련된 통제 항목이 아닌 것은?객관식
  1. 접근통제
  2. 시스템 개발 및 운영 보안
  3. 취약점 관리
  4. 개발 조직의 신원 관리 및 통제
정답 ④개발 조직 관리는 소프트웨어 보안과 관련이 없습니다.
6클라우드 서비스 보안 인증을 나타내는 용어는?객관식
  1. CSAP
  2. CCSP
  3. SaaS
  4. PaaS
정답 ①CSAP는 Cloud Security Assurance Program의 약어입니다.

3차시 퀴즈

7'취약한 접근 통제' 취약점에 대한 설명이 맞는 것은?객관식
  1. 인증된 사용자가 접근이 제한된 데이터나 기능에 접근 가능
  2. 손쉬운 암호 설정으로 브루트포스 공격 가능
  3. 없는 주소 입력 시 에러 메시지와 함께 서버 정보 노출
  4. 틀린 암호를 무제한으로 시도 가능
정답 ①적절한 인가 처리가 이루어지지 않아 중요한 리소스·기능이 권한 없는 사용자에게 노출될 수 있는 취약점입니다.
8'인젝션 공격'에 대한 설명으로 틀린 것은?객관식
  1. 악성 코드를 삽입하는 공격이다
  2. 사용자 입력값을 검증·필터링하면 방어할 수 있다
  3. 커맨드 인젝션 방어를 위해 Prepared Statement를 사용해야 한다
  4. 주로 사용자 입력값을 그대로 파라미터로 사용할 때 발생한다
정답 ③Prepared Statement는 DB 쿼리를 만드는 방법으로 SQL 인젝션 예방에 쓰입니다(커맨드 인젝션 방어책이 아님).
9CVE와 CWE에 대해 잘못 이야기한 것은?객관식
  1. CVE는 SW·HW 보안 취약점을 공개한 시스템이다
  2. 보안 연구원·기업·기관이 발견한 취약점은 CNA에 보고된다
  3. CWE TOP 25는 보안 취약점 중 가장 위험한 25가지를 선정한 목록이다
  4. 특정제품에서 발견된 취약점은 CVE 목록에서 찾을 수 있다
정답 ③CWE는 보안 '약점' 목록이고, 보안 '취약점' 목록은 CVE입니다.

09용어 정리

보안취약점Vulnerability

해킹 등 실제 보안사고에 이용되는 SW 보안약점.

보안약점Weakness

보안취약점의 근본 원인이 되는 SW상의 허점·결점·오류.

제로 트러스트Zero Trust

아무것도 신뢰하지 않는다는 가정하에 지속적으로 검증하는 보안 모델. "Never Trust, Always Verify".

위협 모델링Threat Modeling

시스템의 가능한 위협을 식별하고 위험 순위에 따라 완화 조치를 정하는 프로세스.

인젝션Injection

공격자가 악성 코드나 명령을 입력값에 끼워 넣어 실행시키는 공격 유형.

역직렬화Deserialization

직렬화된 데이터를 다시 객체로 복원하는 과정. 신뢰할 수 없는 데이터를 역직렬화하면 임의 코드 실행 위험이 있음.

공급망 보안Supply Chain Security

소프트웨어 개발-설계-구현-유통 전 단계에서 구성요소의 신뢰성과 무결성을 확보하는 것.

완화Mitigation

식별된 위협·취약점의 영향을 줄이기 위한 조치.

11예상 문제

Q1DevSecOps, 보안내재화(Security by Design), Zero Trust에 대한 설명으로 옳지 않은 것은?객관식
  1. DevSecOps는 애플리케이션 수명주기 전반에서 반복·지속적인 보안 제어를 수행한다
  2. 보안내재화는 설계 단계부터 보안을 고려해 취약점을 조기에 제거한다
  3. Zero Trust는 한 번 인증된 사용자는 이후 계속 신뢰하는 모델이다
  4. 세 가지 모두 애플리케이션 보안 과제 해결 방안으로 제시되었다
정답 ③Zero Trust의 핵심은 "Never Trust, Always Verify" — 한 번 인증됐다고 계속 신뢰하지 않고 지속적으로 검증합니다.
Q2CWE와 CVE의 차이를 설명하시오.서술형
모범답안CWE는 SQL Injection, XSS처럼 보안약점(Weakness)의 유형을 개념적으로 분류한 목록이고, CVE는 특정 제품에서 실제로 발생한 개별 보안취약점(Vulnerability)에 고유 ID를 부여해 관리하는 시스템이다.
Q3아래 transferProxy 함수에서 balances[_from] < _feeSmt + _value 검증이 무력화될 수 있는 이유를 설명하시오.코드
모범답안_feeSmt + _value의 합이 정수형이 표현할 수 있는 최댓값을 넘으면 오버플로우가 발생해 값이 작은 수로 돌아간다. 이 경우 실제로는 잔액이 부족해도 검증식이 참이 되지 않아 revert()가 호출되지 않고 통과할 수 있다.
Q4OWASP TOP 10 중 'Injection'의 주요 대응 방안 두 가지를 쓰시오.서술형
모범답안① 사용자 입력값을 검증·필터링한다. ② SQL 쿼리에는 Prepared Statement 또는 ORM을 사용해 입력값이 그대로 실행되지 않도록 한다.

  • vulnerability/ˌvʌlnərəˈbɪləti/n.

    취약점 — 실제 해킹 등 사고에 이용될 수 있는 보안상 약점

  • weakness/ˈwiːknəs/n.

    CWE lists common types of software weakness.CWE는 흔한 소프트웨어 약점 유형을 정리한 목록이다.

  • mitigation/ˌmɪtɪˈɡeɪʃn/n.

  • authentication/ɔːˌθentɪˈkeɪʃn/n.

  • authorization/ˌɔːθəraɪˈzeɪʃn/n.

    Broken authorization lets a user access another user's data.인가가 깨지면 다른 사용자의 데이터에 접근할 수 있다.

  • injection/ɪnˈdʒekʃn/n.

    삽입(공격) — 입력값에 악성 코드나 명령을 끼워 넣는 공격

    SQL injection can expose an entire database.SQL 인젝션은 데이터베이스 전체를 노출시킬 수 있다.

  • enumeration/ɪˌnjuːməˈreɪʃn/n.
