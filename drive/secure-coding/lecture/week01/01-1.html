오버플로우 (Overflow)

숫자가 자료형이 표현할 수 있는 최대치 이상으로 증가하는 것. 넘친 값은 표현 범위 안으로 되돌아가(wraparound) 엉뚱한 값이 됩니다.

이산수학·자료구조 연결 — 2의 보수

부호 있는 8비트 정수는 맨 앞 비트가 부호(0 양수, 1 음수)이고 범위는 −128 ~ 127입니다. 01111111(127)에 1을 더하면 10000000이 되는데, 2의 보수 표현에서 이 값은 −128입니다. 부호 없는 8비트(0 ~ 255)에서는 11111111+1의 9번째 자리 올림수가 버려져 0이 됩니다.

문제 함수: transferProxy (교안 26쪽 코드 그대로 + 주석)

SoliditytransferProxy (취약한 코드)
// 대리 송금 함수: _from의 토큰을 _to에게 _value만큼 보내고, 수수료 _feeSmt는 호출자에게 준다
function tranferProxy(address _from, address _to, uint256 _value, uint256 _feeSmt,
    uint8 _v, bytes32 _r, bytes32 _s) public transferAllowed(_from) return (bool) {
    // ① 잔액 검사 — 공격자가 _value·_feeSmt에 아주 큰 값을 넣으면
    //    _feeSmt + _value 가 uint256 최댓값을 넘어 작은 값으로 되돌아감(오버플로우)
    //    → 잔액이 없어도 이 조건이 거짓이 되어 revert()가 실행되지 않음
    if(balances[_from] < _feeSmt + _value) revert();
    uint256 nonce = nonces[_from];                          // 재사용 방지용 일련번호
    bytes32 h = keccak256(_from, _to, _value, _feeSmt, nonce); // 서명 대상 해시
    if ( _from != ecrecover(h,_v,_r,_s)) revert();          // 서명한 사람이 _from인지 확인
    // ② 받는 쪽 잔액의 오버플로우만 검사 — ①의 합계 오버플로우는 막지 못함
    if(balance[_to] + value < balances[_to]
        || balances[msg.sender] + _feeSmt < balances[msg.sender]) revert();
    balances[_to] += _value;          // ③ 엄청난 양의 토큰이 _to에게 생성됨
    Transfer(_from, _to, _value);
    balances[msg_sender] += _feeSmt;  // 수수료도 거대한 값으로 지급
}

왜 이렇게 주석을 달았나: 교안이 주황 상자로 강조한 두 곳(함수 인자, ①의 if)이 취약점의 입구와 원인이라서, 값이 흘러가는 순서대로 설명했습니다.

교안 코드의 오타 (슬라이드 원문 그대로 둠)

tranferProxy→transferProxy, return (bool)→returns (bool), balance[_to] + value→balances[_to] + _value, msg_sender→msg.sender. 컴파일되는 코드가 아니라 구조를 보여주는 슬라이드용 코드로 보면 됩니다.

대응: SafeMath 라이브러리

이더리움 스마트컨트랙트 개발 언어 솔리디티(Solidity)는 오버플로우(overflow)·언더플로우(underflow) 처리를 위해 SafeMath 라이브러리를 제공합니다. 솔리디티에서 라이브러리는 특수한 컨트랙트(Contract)입니다.

SoliditySafeMath (교안 27쪽)
library SafeMath {
  function mul(uint256 a, uint256 b) internal pure returns (uint256) {
    if (a == 0) { return 0; }   // 0으로 나누는 검증을 피하려고 먼저 처리
    uint256 c = a * b;
    assert(c / a == b);            // 곱을 다시 나눠 원래 값이 안 나오면 오버플로우 → 중단
    return c;
  }
  function div(uint256 a, uint256 b) internal pure returns (uint256) {
    // assert(b > 0); // 0으로 나누면 솔리디티가 자동으로 예외 발생
    uint256 c = a / b;
    // assert(a == b * c + a % b); // 항상 성립하므로 검사 불필요
    return c;
  }
  function sub(uint256 a, uint256 b) internal pure returns (uint256) {
    assert(b <= a);                // 빼는 값이 더 크면 음수 → uint에서 언더플로우
    return a - b;
  }
  function add(uint256 a, uint256 b) internal pure returns (uint256) {
    uint256 c = a + b;
    assert(c >= a);                // 더했는데 작아졌다면 오버플로우
    return c;
  }
}

검사 원리: 연산 후에 결과가 수학적으로 맞는지(곱→나눗셈, 합≥피연산자) 다시 확인해, 틀리면 assert로 거래 전체를 되돌립니다. transferProxy의 ①을 balances[_from] < _feeSmt.add(_value)로 썼다면 오버플로우 시 중단됐을 것입니다.

솔리디티 0.8 이후 — 교수님이 설명하신 내용 아님

솔리디티 0.8.0부터는 산술 연산에 오버플로우 검사가 언어 차원에서 기본으로 들어가, SafeMath 없이도 오버플로우 시 거래가 되돌려집니다. 교안 사례(2018년)는 그 이전 버전 기준입니다.

CWE Top 25

SW에서 가장 위험한 보안 약점 25가지. MITRE가 관리하며 NVD(National Vulnerability Database) 데이터를 기반으로 합니다. 약점의 발생빈도와 심각도로 선정하며, 최근 2년간 CVE 데이터로 점수를 계산합니다.

수식CWE Top 25 점수 산정
점수(CWEX) = Fr(CWEX) × Sv(CWEX) × 100

Freq = { NVD에 매핑된 각 CWEX′의 개수 }

Fr(CWEX) = count(CWEX ∈ NVD) − min(Freq)max(Freq) − min(Freq) // 빈도를 0~1로 정규화

Sv(CWEX) = avg CVSS(CWEX) − min(CVSS)max(CVSS) − min(CVSS) // 평균 심각도(CVSS)를 0~1로 정규화

두 값 모두 (값 − 최솟값) ÷ (최댓값 − 최솟값) 형태의 최소-최대 정규화이므로 0~1 사이이고, 곱에 100을 곱해 점수는 0~100 사이가 됩니다. 자주 나오면서 심각한 약점일수록 점수가 높습니다.

1. 오버플로우 그림 — 교안 오류로 판단 (계산으로 확인)

교안 25쪽: 01111111 + 00000001 = 00000000. 실제 결과는 10000000입니다(부호 있는 8비트면 127+1 → −128). 결과가 0이 되려면 첫 수가 11111111(부호 없는 255)이어야 합니다. 퀴즈 1-3의 정답(범위를 벗어남)에는 영향 없습니다. 본문 그림은 올바른 두 경우로 고쳐 그렸습니다.

2. CSAP 통제항목 수 79 vs 표 합계 78 — 해결 (교안 원본 불일치)

원본 PDF 14쪽의 숫자가 변환본과 같습니다. 표 합계 78은 교안 원본의 불일치이고, 본문 “13개 분야 79개”가 공식 기준(기사 확인)입니다. 어느 칸이 1개 적은지는 교안만으로는 알 수 없습니다.
