  • 2024년 유출 원인 중 해킹이 171건으로 약 55%. 해킹 세부 유형에서는 관리자 페이지 비정상 접속이 가장 많고(원인미상 제외), SQL 인젝션·XSS·웹쉘·파라미터 변조 같은 보안 취약점이 사고 원인.
  • XSS·SQL 인젝션처럼 익숙한 유형이 여전히 원인이라는 것은 SW 개발보안 인식이 아직 부족하다는 증거 — 국내 SW가 잘 알려진 취약점에도 대응하지 못하고 있다.
  • 정리: 개발 단계에서 취약점이 최대한 생기지 않게 개발하되, 그래도 발견되는 취약점은 빠르게 대응해 제거하는 체계를 구축해 보안성을 강화한다.

기사 ① 국내 SW, 잘 알려진 보안 취약점도 대응 못 해 (2021.02.19)

  • 국내 SW에서 발견되는 취약점 대부분이 이미 흔히 알려진 유형(XSS·SQL 등) → SW 개발보안 인식 부족을 보여줌
  • KISA는 2012년부터 보안 취약점 신고포상제를 운영, 포상 지급 취약점은 2020년까지 총 3,173건

기사 ② OECD “소스코드는 곧 취약점…쉬쉬해선 안 돼” (2021.03.17)

OECD 보고서 인용 (교안)

“취약점은 디지털 생활의 일부다. 모든 취약점을 제거하는 것은 불가능하다. 그보다는 취약점 조치를 개선해 보안 위협을 줄이고 디지털 전환 시대의 신뢰를 도모해야 한다.”

  • 취약점을 사업 리스크나 잘못으로 보기보다 일상적 현상으로 받아들이고, 제보 체계와 지속적 보안 업데이트를 정착시켜야 함
  • KISA가 OECD 보고서 ‘취약점 조치의 장려(Encouraging vulnerability treatment)’ 번역본 공유
  • 국내 문제점: 취약점을 알려줘도 고소·고발로 대응하는 경우가 많음

  • 정적 분석 = 실행하지 않은 채 코드를 분석(구현 단계). 동적 분석 = 실행 중인 프로그램에 데이터를 입출력해 진단(테스트 단계). 보통은 도구 스캐닝을 뜻하지만 모의해킹·모의침투테스트까지 통틀어 동적 분석이라 할 수 있다.

  • 보안내재화: SW·시스템 개발 과정에 보안을 기능처럼 자연스럽게 포함시키는 접근·실천 방법 — 개발·배포 과정에 실제로 녹여내는 것.
  • Security by Design: 시스템을 설계할 때부터 보안을 핵심 요소로 고려하는 철학·전략.

교안 퀴즈 1-2는 정답 해설에서 “보안내재화 = 영어로 Security By Design”이라고 같은 것으로 다룹니다. 교안 퀴즈와 같은 형태로 나오면 보안내재화를 고르고, 서술형으로 “차이”를 물으면 위 교수님 설명(실천 방법 vs 철학·전략)으로 쓰면 됩니다.

  1. 팀 구성: 각 직무 전문가로 팀을 꾸리고, 팀 리더는 보안 전문가가 맡는 것이 가장 효과적. (화면에서 이 단계에 밑줄)
  2. 범위 설정: 보통 DFD(Data Flow Diagram)를 사용 — 사용자, 프로세스, 데이터 저장소, 데이터 흐름을 표시해 개발할 시스템을 파악.
  3. 위협 식별: 예) 로그인 기능 — 성공할 때까지 아이디·패스워드를 무작위로 넣거나, 훔친 아이디·패스워드로 로그인을 시도하는 위협 등 가능한 모든 위협 식별.

  5. 완화 조치: 위협을 어떻게 다룰지 정하고 대응 가능한 시스템을 설계 — 완화 · 수용 · 기능 제거 · 위임 중 결정.
  6. 문서화: 모든 조사 결과와 조치를 문서화해 “[불명확] 구조”를 만들 수 있도록 함 → 확인 필요 5

오버플로우 (Overflow)

숫자가 자료형이 표현할 수 있는 최대치 이상으로 증가하는 것. 넘친 값은 표현 범위 안으로 되돌아가(wraparound) 엉뚱한 값이 됩니다.

교수님 설명 · 1차시 33:27~34:38 — 오버플로우 그림 설명

“4바이트 정수에서 첫 번째 비트는 사인(부호) 비트 — 0이면 양수, 1이면 음수. 그런데 unsigned int의 경우 첫 번째 비트는 항상 0이면서 변경되지 않는다. 첫 줄 값은 가장 큰 양수인데, 여기에 1을 더하면 올림이 계속 올라가 부호 비트까지 넘어가고, unsigned int는 이 비트가 0으로 고정되어 있어 오버플로우가 발생해 연산 결과가 0이 된다.”

교수님 설명과 실제 동작이 다릅니다

부호 없는 정수(unsigned int)에는 부호 비트가 없습니다. 모든 비트가 크기를 나타내므로 8비트면 0~255, 32비트면 0~4,294,967,295입니다. 따라서 01111111(127)+1은 부호 없는 경우 10000000(128)이 되어 오버플로우가 아니고, 부호 있는 경우에는 10000000(−128)이 됩니다. 결과가 0이 되는 것은 모든 비트가 1인 최댓값(11111111)에 1을 더해 맨 위 올림수가 버려질 때입니다. 아래 그림은 이 두 경우로 고쳐 그린 것입니다. 교안 퀴즈 1-3은 정의(“범위를 벗어남”)만 묻기 때문에 영향이 없지만, 비트 계산 문제가 나오면 실제 동작 기준으로 푸는 것이 맞습니다.

이산수학·자료구조 연결 — 2의 보수

부호 있는 8비트 정수는 맨 앞 비트가 부호(0 양수, 1 음수)이고 범위는 −128 ~ 127입니다. 01111111(127)에 1을 더하면 10000000이 되는데, 2의 보수 표현에서 이 값은 −128입니다. 부호 없는 8비트(0 ~ 255)에서는 11111111+1의 9번째 자리 올림수가 버려져 0이 됩니다.

문제 함수: transferProxy (교안 26쪽 코드 그대로 + 주석)

SoliditytransferProxy (취약한 코드)
// 대리 송금 함수: _from의 토큰을 _to에게 _value만큼 보내고, 수수료 _feeSmt는 호출자에게 준다
function tranferProxy(address _from, address _to, uint256 _value, uint256 _feeSmt,
    uint8 _v, bytes32 _r, bytes32 _s) public transferAllowed(_from) return (bool) {
    // ① 잔액 검사 — 공격자가 _value·_feeSmt에 아주 큰 값을 넣으면
    //    _feeSmt + _value 가 uint256 최댓값을 넘어 작은 값으로 되돌아감(오버플로우)
    //    → 잔액이 없어도 이 조건이 거짓이 되어 revert()가 실행되지 않음
    if(balances[_from] < _feeSmt + _value) revert();
    uint256 nonce = nonces[_from];                          // 재사용 방지용 일련번호
    bytes32 h = keccak256(_from, _to, _value, _feeSmt, nonce); // 서명 대상 해시
    if ( _from != ecrecover(h,_v,_r,_s)) revert();          // 서명한 사람이 _from인지 확인
    // ② 받는 쪽 잔액의 오버플로우만 검사 — ①의 합계 오버플로우는 막지 못함
    if(balance[_to] + value < balances[_to]
        || balances[msg.sender] + _feeSmt < balances[msg.sender]) revert();
    balances[_to] += _value;          // ③ 엄청난 양의 토큰이 _to에게 생성됨
    Transfer(_from, _to, _value);
    balances[msg_sender] += _feeSmt;  // 수수료도 거대한 값으로 지급
}

왜 이렇게 주석을 달았나: 교안이 주황 상자로 강조한 두 곳(함수 인자, ①의 if)이 취약점의 입구와 원인이라서, 값이 흘러가는 순서대로 설명했습니다.

교안 코드의 오타 (슬라이드 원문 그대로 둠)

tranferProxy→transferProxy, return (bool)→returns (bool), balance[_to] + value→balances[_to] + _value, msg_sender→msg.sender. 컴파일되는 코드가 아니라 구조를 보여주는 슬라이드용 코드로 보면 됩니다.

교수님 설명 · 1차시 34:38~38:21
  • 매개변수: _from 송금자 주소, _to 받는 사람 주소, _value 송금액, _feeSmt 송금 수수료.
  • 첫 if: 송금자 잔고가 (수수료 + 송금액)보다 작으면 revert로 송금하지 않고 종료. 그런데 _feeSmt + _value가 오버플로우를 일으키면 0으로 처리되어(화면에 손글씨로 “0”) 잔고와 관계없이 송금이 수행된다 → 공격자는 입력값 _value·_feeSmt를 조작해 원하는 만큼 보냄.
  • _value가 uint256이라 1경 개 이상의 토큰이 있는 것처럼 처리될 수 있었다.
  • 왜 “사소한 실수”인가: 스마트 컨트랙트 언어 Solidity 가이드가 오버플로우·언더플로우 처리를 위해 SafeMath 사용을 권고하는데, 개발자가 평소 습관대로 그냥 사칙연산(+)으로 처리했기 때문. 새 언어가 나오고 개발 기간이 짧아 기능 개발을 서두르면 이런 의도치 않은 취약점이 생기며, 구현·테스트 단계에서 걸러내지 못하면 그대로 사고 원인이 된다.

대응: SafeMath 라이브러리

이더리움 스마트컨트랙트 개발 언어 솔리디티(Solidity)는 오버플로우(overflow)·언더플로우(underflow) 처리를 위해 SafeMath 라이브러리를 제공합니다. 솔리디티에서 라이브러리는 특수한 컨트랙트(Contract)입니다.

SoliditySafeMath (교안 27쪽)
library SafeMath {
  function mul(uint256 a, uint256 b) internal pure returns (uint256) {
    if (a == 0) { return 0; }   // 0으로 나누는 검증을 피하려고 먼저 처리
    uint256 c = a * b;
    assert(c / a == b);            // 곱을 다시 나눠 원래 값이 안 나오면 오버플로우 → 중단
    return c;
  }
  function div(uint256 a, uint256 b) internal pure returns (uint256) {
    // assert(b > 0); // 0으로 나누면 솔리디티가 자동으로 예외 발생
    uint256 c = a / b;
    // assert(a == b * c + a % b); // 항상 성립하므로 검사 불필요
    return c;
  }
  function sub(uint256 a, uint256 b) internal pure returns (uint256) {
    assert(b <= a);                // 빼는 값이 더 크면 음수 → uint에서 언더플로우
    return a - b;
  }
  function add(uint256 a, uint256 b) internal pure returns (uint256) {
    uint256 c = a + b;
    assert(c >= a);                // 더했는데 작아졌다면 오버플로우
    return c;
  }
}

검사 원리: 연산 후에 결과가 수학적으로 맞는지(곱→나눗셈, 합≥피연산자) 다시 확인해, 틀리면 assert로 거래 전체를 되돌립니다. transferProxy의 ①을 balances[_from] < _feeSmt.add(_value)로 썼다면 오버플로우 시 중단됐을 것입니다.

교수님 설명 · 3차시 10:36~24:07 — 항목별로 교안에 없는 설명
  1. 접근 통제: 인증과 인가는 다른 개념 — 인증으로 사용자를 식별하고, 식별된 정보로 인가 정책을 세운다. 인증된 사용자에게 모든 리소스를 허용하면 다른 계정 데이터 조회·관리자 기능 수행 사고가 난다.
  2. 암호화 실패: 예) 주민등록번호 같은 민감정보를 평문 저장·전송. 먼저 암호화할 중요정보를 식별 → 전송은 TLS 기반 HTTPS, DB 저장(주민번호·여권번호)은 AES·RSA로 암·복호화. 복호화할 필요가 없는 비밀번호는 단방향 해시로 저장하고, 짧은 입력은 긴 솔트로 무작위 대입 공격을 방어.
  3. 인젝션: SQL 인젝션(쿼리 조작), 커맨드 인젝션(명령어 삽입), XSS(사용자 브라우저에서 스크립트 실행)를 통합해 인젝션으로 분류. 필터링은 값을 차단하거나 안전한 값으로 치환. 정책은 안전하게 처리 가능한 값만 통과시키고 나머지는 모두 차단하는 화이트리스트 정책이 바람직.
  4. 보안 설계 미흡: 예) 관리자 페이지 URL을 직접 입력하면 인증 없이 접근 가능. 대응: 설계 단계 위협 모델링으로 위협을 미리 식별해 구조를 설계, 보안 설계를 코드에 반영하고 주기적으로 소스코드 진단·동적 진단.
  5. 보안 설정 오류: 설치 시 기본 설정값, 디버깅 모드로 동작하는 SW가 원인. 특히 환경설정 파일처럼 시스템에 큰 영향을 주는 파일은 철저한 접근통제.
  6. 취약하고 오래된 구성요소: 오픈소스 취약점 공격이 늘어나는 추세, 패치 안 된 오픈소스는 쉬운 먹잇감 → 주기적 패치, 최근에는 SBOM 작성으로 해결.
  7. 인증 및 세션 관리: 예) 무작위 비밀번호 대입, 세션 인가에 쓰는 JWT(JSON Web Token) 유출. 대응: 다중 요소 인증(예: 휴대폰 기기 + 아이디·패스워드), 토큰 유효기간을 두 레이어로 관리 — 실제 쓰는 액세스 토큰과 이를 관리하는 리프레시 토큰으로 이중 관리해 유출에도 대응, 강력한 비밀번호 정책.
  8. 무결성 실패: 서명 없는 업데이트, 외부 객체를 검증 없이 역직렬화, 신뢰할 수 없는 CI/CD 상의 코드·실행 파일. 대응: 코드 서명 첨부 + 사용 전 무결성 검증. CI/CD는 개발→빌드 단계에서 코드 검토·취약점 스캔·권한 관리를 자동화하고, 빌드→배포 단계에서 아티팩트 무결성 검증·자동 동적 보안 테스트.
  9. 로깅·모니터링 실패: 로깅은 사고 예방, 피해 범위 확인·복구에 중요(2차시에서도 강조). SIEM 등으로 로그·이벤트를 모아 분석하고 이상징후를 실시간 탐지·대응. 사고 대응 체계를 미리 구축해야 우왕좌왕하지 않는다.
  10. SSRF: 쉽게 말해 서버를 속여 공격자가 원하는 곳으로 요청을 보내게 하는 공격. 피해: 내부 관리자 페이지 접근, 내부망 스캔, 클라우드 메타데이터 접근. 사용자가 입력한 URL을 서버가 그대로 요청할 때 주로 발생 → 내부망·민감 리소스 주소를 못 넣게 입력값 검증. CSP(Content Security Policy) = 브라우저에서 악성 콘텐츠 로드를 막는 HTTP 응답 헤더, 원래 XSS 방어 목적이지만 SSRF와 연계된 클라이언트 측 공격 제한에도 도움. 애플리케이션에서 나가는 요청을 네트워크 장비·정책으로 통제.

CVE — 공통 취약점 및 노출 (Common Vulnerabilities and Exposures, cve.mitre.org)

SW·HW의 보안 취약점을 표준화하여 공개하는 시스템. 기업·개발자는 이를 활용해 보안을 강화하고, 특히 개발자는 CVE 데이터로 취약점을 사전 예방하고 신속히 패치합니다. (교안 캡처 당시 CVE 누적 136,476건)

교수님 설명 · 3차시 32:01~33:33

CWE Top 25 = SW에서 가장 위험한 보안약점 25가지, 매년 발표. 발생 빈도와 심각도로 선정 — “더 구체적인 선정 방식은 넘어가겠다”고 하심(아래 산정식은 설명하지 않음). 목적: 가장 빈번하고 심각한 약점을 강조해 사고 예방, 개발·보안팀이 우선 해결할 약점 파악, 보안 교육·훈련에 활용, 우선순위를 정해 제한된 자원을 효과적으로 쓰는 것이 가장 큰 목적.

수식CWE Top 25 점수 산정
점수(CWEX) = Fr(CWEX) × Sv(CWEX) × 100

Freq = { NVD에 매핑된 각 CWEX′의 개수 }

Fr(CWEX) = count(CWEX ∈ NVD) − min(Freq)max(Freq) − min(Freq) // 빈도를 0~1로 정규화

Sv(CWEX) = avg CVSS(CWEX) − min(CVSS)max(CVSS) − min(CVSS) // 평균 심각도(CVSS)를 0~1로 정규화

두 값 모두 (값 − 최솟값) ÷ (최댓값 − 최솟값) 형태의 최소-최대 정규화이므로 0~1 사이이고, 곱에 100을 곱해 점수는 0~100 사이가 됩니다. 자주 나오면서 심각한 약점일수록 점수가 높습니다.

CWE의 주요 목적은 소프트웨어 및 하드웨어 취약점을 분류하고 표준화하며 보안 취약점의 예방 및 완화를 위한 지침을 제공하는 건데요. 더불어 보안평가나 코드 분석 도구와 연계를 하여 소프트웨어의 보안성을 강화하도록 합니다. CWE는 개발자의 보안 코딩 가이드라인이나 정적 또는 동적 보안 점검 도구에서 CWE 목록 기반 취약점을 탐지하는 항목 그리고 OWASP, NIST, CVE 등과 연계하여 보안 개선 등에 다양한 곳에서 활용하고 있습니다. 그럼 이제 앞에서 설명했던 CVE와는 어떤 차이점이 있는지 한번 볼까요? CWE는 보안약점의 개념적인 분류라고 본다면 개념적인 정의고 CVE는 실제 특정 제품에서 발생한 보안 취약점이 되겠습니다. 그래서 A사의 B제품에서 보안사고가 발생했다면 보안사고를 통해 CVE가 NVD에 등록되어 있는 경우 해당 [불명확: 분서의] 상세 내용에서는 이 사고의 원인이 된 보안약점은 CWE-89가 원인이었다. 이런 식으로 작성이 된다고 보시면 되겠습니다. CWE의 경우에는 해마다 CWE TOP 25라는 목록을 발표를 하는데요. 소프트웨어에서 가장 위험한 보안 약점 25가지를 선정한 목록입니다.
