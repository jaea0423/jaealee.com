01SW 개발보안 방법론

교안 퀴즈 출제1차시 · 교안 6~9쪽

SW 개발보안 방법론: SW 개발 과정에서 보안성을 강화하기 위해 적용하는 체계적인 접근 방식. SDLC(Software Development Life Cycle, 소프트웨어 개발 생명주기) 전반에 보안 요구사항을 반영하고 취약점을 예방하는 것이 목표입니다.

주요 개념 3가지

개념영어내용
보안 내재화Security by Design개발 초기부터 보안을 고려해 설계
취약점 최소화Minimization of Vulnerabilities코드·시스템의 보안 결함을 줄이는 방식 적용
지속적인 보안 점검Continuous Security Assessment주기적인 테스트 및 검증 수행
SW 개발보안이란? (교안 7쪽)

안전한 SW 개발을 위해 소스코드 등에 존재할 수 있는 잠재적인 보안약점을 제거하고, 보안을 고려하여 기능을 설계·구현하는 등 SW 개발 과정에서 실행되는 일련의 보안활동.

보안취약점(Vulnerability)·보안약점(Weakness) 정의도 1주차와 동일하게 다시 나옵니다 — 1주차 04번 섹션 참고.

SW 개발보안 방법론 적용의 중요성

  • 해킹, 데이터 유출 등 보안 사고 예방
  • 법적 규제 준수 (개인정보 보호법, GDPR, ISO 27001 등)
  • 개발 비용 절감 — 초기 단계에서 보안 문제를 해결하면 비용이 줄어듦
  • 신뢰할 수 있는 SW 제공으로 기업 이미지·서비스 경쟁력 강화

03MS-SDL — 개발보안 적용 우수사례

교안 퀴즈 출제1차시 · 교안 11~18쪽

MS-SDL(Microsoft Security Development Lifecycle): 마이크로소프트가 개발한 SW 보안 개발 방법론. SDLC 전반에 보안을 내재화하는 것이 목표이며, 취약점 최소화·사고 예방·강력한 보안 정책을 개발 과정에 적용합니다. 자체 개발한 생명주기를 제품 개발 전 과정에 적용해 보안취약점의 원인을 제거했습니다.

MS-SDL의 주요 목표

목표내용
1. 보안 취약점 예방개발 초기부터 보안 요구사항을 반영해 보안 문제를 사전에 차단
2. 위험 감소보안 테스트와 코드 검토로 공격 노출 최소화
3. 법규·규제 준수개인정보 보호, 보안 표준(ISO/IEC 27001, GDPR 등) 준수
4. 비용 절감개발 후반이 아닌 초기에 보안 문제를 해결해 유지보수 비용 절감

MS-SDL 7단계

단계보안 활동
Training
교육 및 보안인식		개발팀 구성원 대상 매년 한 번 보안 기초와 최신 동향 교육 · 내용: 안전설계, 위협모델링, 시큐어코딩, 보안테스팅, 프라이버시
Requirements
요구사항 정의		보안 및 개인정보 보호 요구사항 정의 · 법적·규제 요건(GDPR, HIPAA, ISO 27001) 검토 · 위협 모델링 수행 필요성 확인
Design
설계		위협 모델링(Threat Modeling) 수행 — 공격 표면(Attack Surface) 분석, 보안 위험 평가 및 설계 개선 · 안전한 SW 아키텍처 설계 · 데이터 보호·암호화 정책 정의
Implementation
구현		안전한 코딩 원칙 적용 — OWASP Secure Coding Guide 준수, 보안 API 활용(인증·접근제어·암호화) · 정적 분석(SAST)으로 코드 내 취약점 자동 탐지(SQL Injection, XSS) · 취약한 라이브러리·구성요소 제거 — 최신 패치, 서드파티 취약점 관리
Verification
검증		보안 테스트 — SAST 및 DAST, 침투 테스트(Penetration Testing) · 위험 기반 보안 점검 — 인증·접근제어·암호화 검증, 코드 리뷰 및 취약점 제거
Release
배포		최종 보안 점검(Security Review) — 남은 이슈 해결 · 디지털 서명 및 무결성 검증 — 배포 패키지 검증 · 보안 가이드 문서 제공 — 사용자용 정책·설정 안내
Response
운영 및 유지보수		보안 모니터링·로그 분석(이상 징후 탐지·대응 체계) · 보안 패치·업데이트 관리 · 보안 사고 대응 프로세스(침해사고 대응 계획 실행)
시험 함정 — 위협 모델링은 어느 단계?

요구사항 단계는 위협 모델링 필요성 확인까지, 실제 수행은 설계(Design) 단계입니다. 교안 퀴즈 1-3이 바로 이 구분을 묻습니다.

1차시 요약 (교안)

SW 개발보안은 개발 전 과정에서 보안을 적용하는 방법론 · 분석~테스트 단계별 보안 활동 · 조기 보안 적용은 사고 예방과 비용 절감에 효과적 · MS-SDL은 마이크로소프트의 대표적 보안 개발 방법 · 교육부터 운영까지 모든 단계에 보안 반영.

04위협모델링 개요

교안 퀴즈 출제2차시 · 교안 6~11쪽
정의 (교안)

위협 모델링(Threat Modeling)은 SW·시스템·네트워크의 보안 취약점을 사전에 식별하고, 이를 평가하여 적절한 보안 대책을 수립하는 과정.

주요 개념내용
사전 예방적 보안 접근법설계 단계에서 보안 위협을 예측하고 방어책 마련
공격자 관점의 분석공격자가 시스템을 어떻게 악용할지 분석해 취약점 최소화
개발 프로세스 내 통합보안이 SDLC에서 자연스럽게 반영되도록 구조화된 방법론 적용

핵심 목표 4가지

위협 모델링이 중요한 이유

  1. 사전 보안 강화 — 개발 초기에 보안을 고려해 비용 절감·보안성 향상
  2. 보안 사고 예방 — 공격자 시각에서 취약점 분석
  3. 법규 및 표준 준수 — 금융·의료 등 특정 산업에서는 필수 절차
  4. DevSecOps 연계 — 개발·운영 과정에 보안이 지속 반영되도록 지원

참가자 및 역할

직무역할참여 이유
개발팀
Developers		시스템 구조를 이해하고 보안 요구사항을 코드에 반영앱의 동작·구현을 가장 잘 앎 · 취약점이 생기기 쉬운 코드 영역 식별 · 제안된 보안 개선을 직접 구현
보안 전문가
Security Engineers / Architects		보안 위협 식별, 취약점 분석·대응책 수립공격자 관점에서 위협 예측·방어 전략 제안 · 최신 위협 동향 제공 · STRIDE·DREAD 등 프레임워크로 체계적 분석
시스템 아키텍트
System Architects		시스템 설계 담당, 보안을 고려한 설계 구조 반영앱·인프라 전반 구조 설계 · 보안 요구사항에 맞춰 아키텍처 조정 · 보안 설계 원칙 적용
제품 관리자
Product Owners / PM		보안 요구사항을 개발 프로세스에 반영, 일정 관리보안이 제품 기능에 주는 영향 조율 · 보안과 비즈니스 요구의 균형 · 결과를 제품 라이프사이클에 반영
운영팀
DevOps / IT Operations		배포된 앱의 보안 운영과 지속적 모니터링운영 환경 위협 파악 · 로그·모니터링 데이터로 결과 보완 · DevSecOps 자동 점검·대응 전략
QA 및 테스터
QA Engineers / Penetration Testers		보안 테스트·취약점 점검으로 위협 모델링 검증정의된 시나리오 기반 테스트 · 침투 테스트로 실제 공격 가능성 평가 · 보안 요구사항 충족 확인

05위협모델링 프레임워크 — STRIDE · DREAD

교안 퀴즈 출제교안 ★ 표시2차시 · 교안 12~17쪽

위협 모델링 프레임워크는 보안 위협을 체계적으로 식별·분석하는 방법론이며, 환경과 목적에 따라 알맞은 것을 골라야 합니다.

프레임워크주요 특징적용 분야
STRIDE ★가장 널리 쓰이는 기법, 6가지 보안 위협 유형 정의애플리케이션 보안, MS-SDL, 클라우드 보안
PASTA공격자 관점 분석 + 비즈니스 영향도 평가금융, 의료, 대규모 엔터프라이즈
DREAD ★위협을 정량적으로 평가, 위험도를 수치화해 우선순위 결정침투테스트, 보안 리스크 평가
Attack Tree공격 목표 중심으로 공격 경로를 트리로 시각화IoT, 산업제어시스템(ICS), 네트워크 보안
OCTAVE조직 전반의 보안 위험을 거버넌스 중심으로 평가기업 보안, IT 리스크 관리

STRIDE (Microsoft 개발)

위협 유형설명깨지는 보안 속성보안 대응책
Spoofing
신원 위조		공격자가 허가 없이 허가된 사용자로 가장인증 (Authentication)강력한 인증 (MFA, OAuth)
Tampering
데이터 변조		데이터가 불법적으로 변경·조작됨무결성 (Integrity)무결성 검사 (Hash, 디지털 서명)
Repudiation
부인		공격자가 악의적 행동을 부인 가능감사 (Audit) — 부인 방지로깅·감사로 책임 추적 (Audit Logs)
Information Disclosure
정보 노출		기밀 데이터가 외부에 노출기밀성 (Confidentiality)데이터 암호화 (AES, TLS, SSL)
Denial of Service
서비스 거부		시스템을 사용할 수 없게 하는 공격가용성 (Availability)트래픽 제한, WAF, DDoS 보호
Elevation of Privilege
권한 상승		공격자가 권한을 올려 관리자 권한 획득접근 제어 (Access Control)최소 권한 원칙, 권한 검증 강화

“깨지는 보안 속성” 열은 3단계 설명(교안 21쪽)의 STRIDE → 보안 위협 대응표를 합친 것입니다.

각 교안 마지막의 퀴즈를 그대로 옮겼습니다. 아래 “예상 문제”와 별개입니다.

1차시

1-1다음 중 SW개발보안 방법론의 주요 개념이 아닌 것은?객관식
  1. 지속적인 보안 점검
  2. 보안 내재화
  3. SBOM 다중화
  4. 취약점 최소화
정답 ③ SBOM 다중화주요 개념은 보안 내재화, 취약점 최소화, 지속적인 보안 점검입니다.
1-2다음 중 SW 결함 수정비용이 가장 많이 필요한 경우는?객관식
  1. 코딩과정 발생한 결함이 통합 단계에서 발견된 경우
  2. 설계과정 발생한 결함이 제품 출시 단계에서 발견된 경우
  3. 설계과정 발생한 결함이 코딩 단계에서 발견된 경우
  4. 통합과정 발생한 결함이 제품출시 단계에서 발견된 경우
정답 ②최초 과정의 결함을 최종 출시 단계에서 알게 되면 가장 비쌉니다 (표 기준 30배. ①10배 ③5배 ④20배).
1-3다음 중 MS-SDL 보안개발 방법론에 대한 설명 중 틀린 것은?객관식
  1. 보안 문제를 사전에 차단한다.
  2. 요구사항 정의 단계에 위협 모델링을 수행한다.
  3. 구현 단계에서 정적 분석을 수행한다.
  4. 배포 단계에서 보안 가이드 문서를 제공한다.
정답 ②위협 모델링은 설계 단계에 수행합니다. 요구사항 단계는 필요성 확인까지.

2차시

2-1다음 중 위협모델링의 핵심 목표가 아닌 것은?객관식
  1. 위험 평가
  2. 보안 조치 적용
  3. 시스템 이해
  4. SW 구조 이해
정답 ④핵심 목표는 시스템 이해, 위협 식별, 위험 평가, 보안 조치 적용입니다.
2-2다음 중 위협모델링 프로세스 단계에 대한 내용이 틀린 것은?객관식
  1. 시스템 정의 - 구성원간 상호 협업 시스템을 명확히 정의
  2. 위협 식별 - 발생할 수 있는 잠재적 위협을 식별
  3. 완화 계획 수립 - 보안조치를 설계하고 구현
  4. 검토 및 개선 - 결과를 검토하고 지속적으로 개선
정답 ①시스템 정의 단계는 위협 모델링을 위해 보호할 대상을 명확히 정의하는 단계입니다.
2-3다음 중 STRIDE 프레임워크에서 정의한 주요 위협요소에 대한 설명으로 올바른 것은?객관식
  1. 신원 위조 - 사용자가 악의적인 행동을 부인 가능
  2. 권한 상승 - 기밀 데이터가 외부에 노출
  3. 서비스 거부 - 시스템을 사용할 수 없도록 하는 공격
  4. 정보 노출 - 데이터가 불법적으로 변경되거나 조작됨
정답 ③①은 부인(Repudiation), ②는 정보 노출, ④는 변조(Tampering)의 설명입니다. 서비스 거부 대응: 트래픽 제한, WAF, DDoS 보호.

3차시

3-1다음 중 위협모델링 도구 선정 기준으로 가장 적합하지 않은 것은?객관식
  1. 자동화 지원 여부
  2. 보안 프레임워크 지원 여부
  3. 무료/유료 여부
  4. CWE/CVE 연계 분석 여부
정답 ④위협모델링 도구는 SW 약점·취약점 목록과 직접 연관될 필요가 없습니다.
3-2다음 중 데이터 흐름 다이어그램(DFD)의 주요 구성요소가 아닌 것은?객관식
  1. Process
  2. Data Flow
  3. External Interactor
  4. Module
정답 ④ ModuleDFD 구성요소: External Interactor, Process, Data Store, Data Flow.
3-3다음 중 데이터 흐름 다이어그램(DFD)을 작성하는 단계는?객관식
  1. 시스템 이해 및 범위 정의
  2. 위협 식별
  3. 위협 평가 및 대응 우선 순위 결정
  4. 위협 완화 및 대응 전략 수립
정답 ①데이터 흐름을 그리는 것은 전체 시스템의 정보 흐름을 이해하기 위해서입니다.

10용어 정리

SDLCSoftware Development Life Cycle

소프트웨어 개발 생명주기. 분석→설계→구현→테스트→배포·운영.

MS-SDLMicrosoft Security Development Lifecycle

Training → Requirements → Design → Implementation → Verification → Release → Response 7단계 보안 개발 방법론.

위협 모델링Threat Modeling

취약점을 사전에 식별·평가해 보안 대책을 세우는 과정. MS-SDL에선 설계 단계에서 수행.

공격 표면Attack Surface

공격자가 시스템에 접근·입력할 수 있는 지점 전체. 설계 단계에서 분석.

STRIDESpoofing · Tampering · Repudiation · Info Disclosure · DoS · Elevation

6가지 위협 유형 분류. 각각 인증·무결성·감사·기밀성·가용성·접근제어를 깨뜨림.

DREADDamage · Reproducibility · Exploitability · Affected users · Discoverability

5개 항목을 0~10점으로 매겨 위험도를 수치화하는 평가 모델.

PASTAProcess for Attack Simulation and Threat Analysis

공격자 관점 분석과 비즈니스 영향도 평가를 결합한 프레임워크.

DFDData Flow Diagram

데이터 흐름도. External Interactor, Process, Data Store, Data Flow로 구성.

신뢰 경계Trust Boundary

신뢰 수준이 달라지는 경계선. 경계를 넘는 데이터 흐름에서 위협이 주로 생김.

MTMTMicrosoft Threat Modeling Tool

STRIDE 기반 무료 위협모델링 도구. DFD를 그리면 위협 목록을 자동 생성(Windows).

침투 테스트Penetration Testing

실제 공격처럼 시스템을 공격해 취약점을 확인하는 테스트.

11확인 필요

1. DREAD 예시 총점 42 → 43 — 교안 계산 오류 (원본 PDF도 42로 인쇄, 확인 완료)

5+10+10+8+10 = 43. 위협 수준(Critical)은 같습니다. 시험에서 합계를 계산하라고 하면 43이 맞습니다.

2. 개별 실습(댓글 작성 위협모델링) 제출 여부 — 해결

과제 공지가 없어 제출 과제가 아닌 것으로 정리했습니다.

3. DREAD 척도 차이 — 해결

2차시는 총점(0~50) 기준, 3차시 실습은 평균(0~10) 기준입니다. 교안이 두 기준을 모두 쓰고 있어 본문에 나눠 적었습니다.

12예상 문제

Q1MS-SDL 7단계를 순서대로 쓰고, 위협 모델링과 정적 분석(SAST)이 각각 처음 수행되는 단계를 쓰시오.단답
정답Training → Requirements → Design → Implementation → Verification → Release → Response. 위협 모델링 수행 = Design, SAST = Implementation (Verification에서도 SAST·DAST 수행).
Q2다음 DREAD 점수의 총점과 위협 수준을 쓰시오. D=7, R=8, E=6, A=9, D=7계산
정답총점 37 → 31~50 구간이므로 치명적(Critical). 평균으로 보면 7.4 → 3차시 기준 “높음”. (교안 실습의 “게시글 폭주 등록”과 같은 점수)
Q3STRIDE의 각 위협이 깨뜨리는 보안 속성을 짝지으시오. (Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege)단답
정답인증 · 무결성 · 감사(부인 방지) · 기밀성 · 가용성 · 접근 제어(권한)
Q4게시글 작성 기능에서 “API 요청에 관리자 플래그를 넣어 권한 상승”이 가능한 이유와 대응 방안을 설명하시오.서술형
모범답안서버가 권한 판단에 클라이언트가 보낸 값을 그대로 믿기 때문이다. 요청 본문은 사용자가 마음대로 바꿀 수 있으므로, 권한 검증은 서버가 가진 사용자 세션 정보 기준으로만 하고 요청의 권한 필드는 무시해야 한다.
Q5NIST 결함 수정비용 표에서 수정비용 배수가 서로 같은 것을 모두 고르시오.객관식
  1. 설계 결함을 통합단계에서 발견
  2. 코딩 결함을 통합단계에서 발견
  3. 통합 결함을 베타제품에서 발견
  4. 코딩 결함을 제품출시에서 발견
정답 ①②③ (모두 10배)① 10배, ② 10배, ③ 10배, ④ 30배. “늦을수록 비싸다”만 외우면 헷갈리고, 표 숫자를 정확히 기억해야 풀리는 문제.
Q6데이터 흐름도(DFD)에서 신뢰 경계(Trust Boundary)를 표시하는 이유를 게시글 작성 DFD를 예로 설명하시오.서술형
모범답안신뢰 수준이 다른 영역(인터넷의 사용자 ↔ 서버) 사이를 데이터가 지나는 지점에서 위조·변조 같은 위협이 주로 생기기 때문이다. 게시글 DFD에서는 Internet Boundary를 넘는 “게시글 작성” 흐름에 대해 인증 확인(S)과 입력값 검증(T)이 필요하다.

시큐어코딩 필수 용어

이번 주차 교안에 나온 단어 중 원서·공식 문서에서 다시 만날 것들만 골랐습니다.

  • threat/θret/n.

    위협 — 자산에 피해를 줄 수 있는 잠재적 사건·공격

    We list every threat in the design step.우리는 설계 단계에서 모든 위협을 나열한다.

  • spoofing/ˈspuːfɪŋ/n.

    위장·신원 위조 — 다른 사용자인 척하는 것

    Spoofing is stopped by strong authentication.신원 위조는 강한 인증으로 막는다.

  • tampering/ˈtæmpərɪŋ/n.

    변조 — 데이터를 허가 없이 바꾸는 것

    A hash can detect data tampering.해시로 데이터 변조를 탐지할 수 있다.

  • repudiation/rɪˌpjuːdiˈeɪʃn/n.

    부인 — 자신이 한 행동을 하지 않았다고 주장하는 것

    Audit logs help prevent repudiation.감사 로그는 부인을 막는 데 도움이 된다.

  • privilege/ˈprɪvəlɪdʒ/n.

    권한 — 시스템에서 할 수 있는 일의 범위

    Give each user the least privilege.각 사용자에게 최소 권한을 주어라.

  • reproducibility/ˌriːprəˌduːsəˈbɪləti/n.

    재현 가능성 — 같은 공격을 다시 성공시킬 수 있는 정도

    High reproducibility raises the DREAD score.재현 가능성이 높으면 DREAD 점수가 올라간다.

  • boundary/ˈbaʊndri/n.

    경계 — 신뢰 수준이 바뀌는 선

    Data crosses the trust boundary here.데이터가 여기서 신뢰 경계를 넘는다.

  • lifecycle/ˈlaɪfsaɪkl/n.

    생명주기 — 만들어져 사라질 때까지의 전체 단계

    MS-SDL covers the whole software lifecycle.MS-SDL은 소프트웨어 생명주기 전체를 다룬다.
