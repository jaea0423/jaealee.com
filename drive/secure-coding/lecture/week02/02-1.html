01SW 개발보안 방법론

교안 퀴즈 출제1차시 · 교안 6~9쪽

SW 개발보안 방법론: SW 개발 과정에서 보안성을 강화하기 위해 적용하는 체계적인 접근 방식. SDLC(Software Development Life Cycle, 소프트웨어 개발 생명주기) 전반에 보안 요구사항을 반영하고 취약점을 예방하는 것이 목표입니다.

주요 개념 3가지

개념영어내용
보안 내재화Security by Design개발 초기부터 보안을 고려해 설계
취약점 최소화Minimization of Vulnerabilities코드·시스템의 보안 결함을 줄이는 방식 적용
지속적인 보안 점검Continuous Security Assessment주기적인 테스트 및 검증 수행
교수님 설명 · 1차시 01:53~04:49

방법론은 보안 기능을 따로 추가하는 것이 아니라 SDLC 전반에 보안 요구사항을 반영하고 취약점을 사전에 예방하는 것 — 예) 설계에서 어떤 보안 정책을 쓸지 고려, 구현에서 안전한 코딩 기법, 테스트에서 취약점 스캐닝처럼 각 단계마다 보안을 녹여 넣는 방식.

  • 보안 내재화: 사후에 덧붙이지 않고 시스템 설계부터 보안을 고려 — 예) 사용자 인증 구조, 데이터 접근 방식.
  • 취약점 최소화: 보안 결함이 안 생기게 코드 작성 + 구성요소 선택, 의존 라이브러리 관리까지 모든 측면에서 위험 요소 축소.
  • 지속적인 보안 점검: 정기적인 테스트·검증 반복. CI/CD에 보안 점검을 자동으로 넣는 DevSecOps도 이 맥락.

핵심: 보안을 별도 기능이 아니라 개발 전체의 일상적인 활동에 녹여내는 것. 방법론은 “SW개발보안 프로세스”로 구체화되고, 실제 적용 사례가 MS-SDL.

SW 개발보안이란? (교안 7쪽)

안전한 SW 개발을 위해 소스코드 등에 존재할 수 있는 잠재적인 보안약점을 제거하고, 보안을 고려하여 기능을 설계·구현하는 등 SW 개발 과정에서 실행되는 일련의 보안활동.

교수님 설명 · 1차시 05:49~13:11 — 단계별 보안 활동 상세
  • 분석(보안요구사항 식별): 기능·사용자 요구사항을 바탕으로 보안 적용 범위 정의 → 보호할 자산(데이터, 기능, 계정 정보) 식별 → 보안 목표 수립(예: “사용자 개인정보는 외부에 노출되지 않아야 한다” — 기밀성·무결성·가용성 중심) → 법·정책 요건 반영(개인정보보호법, 전자금융감독규정, ISMS) → 구체적인 보안 요구사항을 명세 문서로 작성. 추상적 목표가 아니라 개발 명세로 반영 가능하게 구체화하는 것이 핵심이며, 이후 설계·구현·테스트의 보안 기준이 된다.
  • 설계: ① 위협원 도출 — 구조·흐름·구성요소를 분석해 잠재 위협을 식별하고 줄이는 방안을 설계에 반영 ② 외부 인터페이스 식별 — 외부 시스템·사용자와 데이터를 주고받는 지점을 명확히 함: 외부 시스템·API 연동 목록 작성, 송수신 방식, 인증 방식과 데이터 형식 명시, 입력 검증·필터링 체크포인트 설정 ③ 보안 통제 수립 — 예) 인증 정책은 MFA, 인가 정책은 RBAC, 암호 알고리즘 선정, 로그 기록 범위, 에러 처리 방식, 입력값 검증 방식. 이 단계의 실수·누락은 이후 보안 문제로 이어질 가능성이 매우 커서 매우 중요한 단계.
  • 구현: 표준 코딩 가이드와 개발보안 가이드를 철저히 준수 — 예) 사용자 입력값은 항상 검증, 출력값에는 인코딩, 민감 데이터는 저장 전 암호화. 정적 분석 도구는 컴파일 이전에 소스코드를 분석해 알려진 패턴의 취약점을 빠르게 식별.
  • 테스트: 실행 가능한 바이너리·웹앱 대상 진단 — 동적 분석 스캐닝, 모의해킹, 퍼징 테스트. 결과는 보고서로 개발팀에 전달 → 코드 수정 = 보안 피드백 사이클.

보안취약점(Vulnerability)·보안약점(Weakness) 정의도 1주차와 동일하게 다시 나옵니다 — 1주차 04번 섹션 참고.

SW 개발보안 방법론 적용의 중요성

  • 해킹, 데이터 유출 등 보안 사고 예방
  • 법적 규제 준수 (개인정보 보호법, GDPR, ISO 27001 등)
  • 개발 비용 절감 — 초기 단계에서 보안 문제를 해결하면 비용이 줄어듦
  • 신뢰할 수 있는 SW 제공으로 기업 이미지·서비스 경쟁력 강화
교수님 설명 · 1차시 15:29~17:40

허술한 설계와 취약한 코드는 공격자에게 손쉬운 침입 경로가 된다. 법적 규제로는 개인정보보호법, 전자금융감독규정, GDPR, ISO 27001 등 — 충족하지 못하면 법적 책임과 사회적 신뢰도에 타격. 초기에 문제를 해결할수록 유지보수·사고 대응 비용이 줄어 개발보안이 곧 비용 절감 수단. 결론: SW 개발보안은 기술적 활동만이 아니라 기업 경쟁력을 위한 전략적 접근.

03MS-SDL — 개발보안 적용 우수사례

교안 퀴즈 출제1차시 · 교안 11~18쪽

MS-SDL(Microsoft Security Development Lifecycle): 마이크로소프트가 개발한 SW 보안 개발 방법론. SDLC 전반에 보안을 내재화하는 것이 목표이며, 취약점 최소화·사고 예방·강력한 보안 정책을 개발 과정에 적용합니다. 자체 개발한 생명주기를 제품 개발 전 과정에 적용해 보안취약점의 원인을 제거했습니다.

MS-SDL의 주요 목표

목표내용
1. 보안 취약점 예방개발 초기부터 보안 요구사항을 반영해 보안 문제를 사전에 차단
2. 위험 감소보안 테스트와 코드 검토로 공격 노출 최소화
3. 법규·규제 준수개인정보 보호, 보안 표준(ISO/IEC 27001, GDPR 등) 준수
4. 비용 절감개발 후반이 아닌 초기에 보안 문제를 해결해 유지보수 비용 절감

MS-SDL 7단계

단계보안 활동
Training
교육 및 보안인식		개발팀 구성원 대상 매년 한 번 보안 기초와 최신 동향 교육 · 내용: 안전설계, 위협모델링, 시큐어코딩, 보안테스팅, 프라이버시
Requirements
요구사항 정의		보안 및 개인정보 보호 요구사항 정의 · 법적·규제 요건(GDPR, HIPAA, ISO 27001) 검토 · 위협 모델링 수행 필요성 확인
Design
설계		위협 모델링(Threat Modeling) 수행 — 공격 표면(Attack Surface) 분석, 보안 위험 평가 및 설계 개선 · 안전한 SW 아키텍처 설계 · 데이터 보호·암호화 정책 정의
Implementation
구현		안전한 코딩 원칙 적용 — OWASP Secure Coding Guide 준수, 보안 API 활용(인증·접근제어·암호화) · 정적 분석(SAST)으로 코드 내 취약점 자동 탐지(SQL Injection, XSS) · 취약한 라이브러리·구성요소 제거 — 최신 패치, 서드파티 취약점 관리
Verification
검증		보안 테스트 — SAST 및 DAST, 침투 테스트(Penetration Testing) · 위험 기반 보안 점검 — 인증·접근제어·암호화 검증, 코드 리뷰 및 취약점 제거
Release
배포		최종 보안 점검(Security Review) — 남은 이슈 해결 · 디지털 서명 및 무결성 검증 — 배포 패키지 검증 · 보안 가이드 문서 제공 — 사용자용 정책·설정 안내
Response
운영 및 유지보수		보안 모니터링·로그 분석(이상 징후 탐지·대응 체계) · 보안 패치·업데이트 관리 · 보안 사고 대응 프로세스(침해사고 대응 계획 실행)
교수님 설명 · 1차시 17:40~29:39
  • MS-SDL = 개발보안을 SDLC 전반에 반영하는 개념을 실제로 실천한 대표 사례. 흔히 보안을 개발이 끝난 테스트 때쯤 생각하는데, MS-SDL은 이 순서를 뒤집었다. 마이크로소프트는 수많은 제품군에 적용해 보안 사고를 줄였다고 발표.
  • 목표 설명: 예방 = 사용자 인증 방법, 민감 데이터 암호화 방식을 처음부터 정의 · 위험 감소 = 정적 분석·침투 테스트로 실제 해킹 시나리오 대비 · 규제 준수 = 개인정보보호법·ISO·GDPR을 자연스럽게 만족하도록 프로세스화, 문서로 증명할 수 있게 관리 · 비용 절감 = 완성 후 치명적 버그가 나오면 전체 구조를 바꿔야 할 수도 있음.
  • Training: 개발자·기획자·디자이너 등 개발 참여 인력 전체가 해마다 한 번. 실제 업무와 연계된 내용. 이유: 보안은 기술팀만의 책임이 아니라 구성원 전체가 인식·실천해야 수준이 올라가기 때문.
  • Requirements: GDPR, HIPAA(미국 건강보험 이동성 및 책임에 관한 법률), ISO 등을 검토해 적용 가능한 요구사항으로 변환. 위협 모델링 필요성 판단 — 위험도가 높거나 민감 정보를 다루면 반드시 이후 단계에서 수행.
  • Design: 위협 모델링 = 시스템이 외부와 어떻게 연결되고 공격자가 어떤 경로로 침투할지 분석 → 공격 표면 파악. 예) 입력 검증이 필요한 위치, 인증 절차가 미비한 부분, 민감 데이터 노출 경로.
  • Implementation: OWASP 시큐어 코딩 가이드 우선 준수, 보안 API 활용, 정적 분석으로 SQL 인젝션·XSS가 개발 과정에서 자동 감지되게 설정, 서드파티 라이브러리 점검(Log4j처럼 외부 라이브러리 사고가 많음).
  • Verification: 정적 + 동적 분석 + 침투 테스트(해커 입장), 인증·접근제어·암호화가 제대로 동작하는지 확인, 코드 리뷰.
  • Release: 남은 이슈의 해결 여부 최종 확인, 디지털 서명·무결성 검증 = 배포 패키지가 변조되지 않았는지 확인, 사용자용 보안 가이드 문서(적용된 정책, 설정 방법).
  • Response: “개발이 끝났다고 보안 관리가 끝나는 게 아니라 오히려 이 단계부터가 시작.” 예) 이상 트래픽 지속, 실패한 로그인 급증 → 즉시 대응. 새 취약점에 얼마나 빨리 패치하느냐가 핵심. 사고 시 누구에게 보고하고 어떤 순서로 조치할지 계획을 세우고 훈련.
시험 함정 — 위협 모델링은 어느 단계?

요구사항 단계는 위협 모델링 필요성 확인까지, 실제 수행은 설계(Design) 단계입니다. 교안 퀴즈 1-3이 바로 이 구분을 묻습니다.

04위협모델링 개요

교안 퀴즈 출제2차시 · 교안 6~11쪽
정의 (교안)

위협 모델링(Threat Modeling)은 SW·시스템·네트워크의 보안 취약점을 사전에 식별하고, 이를 평가하여 적절한 보안 대책을 수립하는 과정.

주요 개념내용
사전 예방적 보안 접근법설계 단계에서 보안 위협을 예측하고 방어책 마련
공격자 관점의 분석공격자가 시스템을 어떻게 악용할지 분석해 취약점 최소화
개발 프로세스 내 통합보안이 SDLC에서 자연스럽게 반영되도록 구조화된 방법론 적용
교수님 설명 · 2차시 01:24~03:30

위협 모델링 = 보안 위협을 사전에 식별·대응하기 위한 체계적인 분석 절차 — 사후 대응이 아니라 미리 예측해서 방어하자는 철학. 공격자 관점은 “내가 공격자라면 이 시스템의 어떤 약점을 노릴까?”라는 질문에서 출발. SDLC에 통합되면 단순 점검이 아니라 구조화된 보안 설계 활동이 된다.

핵심 목표 4가지

교수님 설명 · 2차시 03:30~05:48
  • 시스템 이해: 아무것도 모르는 상태에서는 시작할 수 없다 — 보호할 대상을 먼저 파악. 부실하면 이후 식별·대응이 모두 부정확해지므로 아키텍처를 그리고 데이터 흐름을 정리하는 과정이 반드시 선행.
  • 위협 식별: 프레임워크로 체계적으로 — “위험할 것 같다” 수준이 아니라 공격 시나리오까지 도출.
  • 위험 평가: 모든 위협을 같은 수준으로 다룰 수 없으므로 DREAD 같은 정량 평가로 심각도·발생 가능성 기준 우선순위.
  • 보안 조치 적용: 설계 단계에서부터 조치해 위협을 완화하거나 제거.

위협 모델링이 중요한 이유

  1. 사전 보안 강화 — 개발 초기에 보안을 고려해 비용 절감·보안성 향상
  2. 보안 사고 예방 — 공격자 시각에서 취약점 분석
  3. 법규 및 표준 준수 — 금융·의료 등 특정 산업에서는 필수 절차
  4. DevSecOps 연계 — 개발·운영 과정에 보안이 지속 반영되도록 지원
교수님 설명 · 2차시 05:48~08:03

법규 준수: 개인정보보호법·ISO 같은 기준에서 보안 감사·인증이 요구하는 위험 분석 항목을 충족하는 데 효과적. DevSecOps: 개발·보안·운영이 함께 움직이며 보안을 반복 점검·반영하는 구조에서 보안을 체계적으로 반영하도록 지원.
