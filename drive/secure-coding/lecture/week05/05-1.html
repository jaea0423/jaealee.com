인증 = 사용자가 등록된 사용자인지 확인하는 과정. 아이디·패스워드로 로그인하면 시스템은 입력값이 저장된 회원정보와 일치하는지 검증한다. 인가 = 인증된 사용자에게 어떤 리소스에 어떤 권한을 허용할지 결정하는 절차. 예) 관리자는 모든 게시물을 삭제할 수 있지만 일반 사용자는 본인이 작성한 글만 수정 — 이렇게 권한을 제한하는 것이 인가. “인증으로 내가 누구인지 확인하고, 인가로 무엇을 할 수 있는지 제어한다.”

02인증 방식 3가지 · 최신 인증 기술

1차시 · 교안 6~10쪽

인증은 내가 “나”임을 증명하는 것으로, 인증 방법에 따라 지식기반 · 소유기반 · 생체기반으로 구분합니다. 가장 널리 쓰이는 방식은 아이디(ID)와 패스워드(password)입니다.

보완다단계 인증(MFA)과 결합, 질문·답변 주기적 업데이트——
교수님 설명 · 1차시 02:43~05:24
  • 아이디·비밀번호는 편리하지만 유출되면 위험이 크다. OTP·스마트카드 같은 소유기반은 장치를 잃어버리면 불편하지만 공격 저항력은 강하다. 지문·홍채 같은 생체기반은 도용이 어렵지만 센서 오류와 도입 비용을 고려해야 한다. 실무에서는 이 방식들을 조합해 보안을 강화한다.
  • 지식기반: 비밀번호만 기억하면 되어 편리하지만 유출·사회공학 기법에 바로 노출 → 다단계 인증을 결합하고 비밀번호 질문·답변을 주기적으로 갱신.
  • 소유기반: 실제 장치가 있어야 해서 단독으로는 도용이 어렵고 2차 인증으로 자주 쓰임. 분실·도난 시 무력화되므로 관리 절차와 재발급 체계가 필수.
  • 생체기반: 복제·도용이 매우 어렵고 기억할 필요가 없지만, 유출 시 치명적이고 센서 오류·조명·소음 같은 환경 변수에 대비해야 함.
MFA의 정확한 조건 — 교수님이 설명하신 내용 아님

다중 인증(MFA, Multi-Factor Authentication)은 서로 다른 종류의 요소를 2개 이상 쓰는 것입니다. 비밀번호 + 보안 질문은 둘 다 지식 요소라서 “2단계”이긴 해도 다중 요소는 아닙니다. 비밀번호 + OTP(소유), 비밀번호 + 지문(생체)이 MFA입니다. 생체 정보는 비밀번호처럼 바꿀 수 없어서 “유출 시 치명적”이라는 단점이 나옵니다.

FIDO2와 WebAuthn의 관계 — 교수님이 설명하신 내용 아님

FIDO2는 FIDO Alliance의 규격 묶음 이름이고, 그 안에서 브라우저(웹) 쪽 API가 W3C의 WebAuthn, 보안키·기기 쪽 통신 규격이 CTAP입니다. 서버에는 공개키만 저장되고 개인키는 사용자 기기를 떠나지 않으므로, 서버가 털려도 재사용할 비밀번호가 없습니다.

교수님 설명 · 1차시 09:52~11:34

접속하면 세션 저장소가 할당되고 이를 식별하는 세션 ID가 부여된다. 세션 ID는 응답 헤더의 Set-Cookie로 브라우저에 전달된다. 사용자가 아이디·패스워드를 보내면 서버가 검증해 정상이면 할당된 저장소에 인증 정보를 저장. 저장소는 서버가 1대면 메모리, 여러 대면 파일이나 데이터베이스. 이후 요청마다 쿠키의 세션 ID로 저장소의 로그인·권한 정보를 꺼내 인가 정책을 적용 → 그래서 쿠키 보안 조치가 필요: HttpOnly = True, Secure(HTTPS에서만 전송) = True.

교수님 설명 · 1차시 12:50~13:54

로그인 정보를 POST로 보내면 서버는 유효성을 검증하고 JWT를 응답 JSON에 담아 반환. 클라이언트는 이 토큰을 로컬 스토리지나 보안 쿠키에 저장하고, 이후 모든 API 요청에서 Authorization 헤더의 Bearer 키워드와 함께 보낸다. 서버는 서명을 확인한 뒤 페이로드의 클레임으로 신원과 권한을 검증. 상태를 저장하지 않는 스테이트리스 구조라 마이크로서비스 환경에서 확장성이 뛰어나다.

미국 NIST의 최신 지침(SP 800-63B Rev.4, 2025)은 비밀번호만으로 로그인하면 최소 15자, MFA의 한 요소로 쓰면 최소 8자를 요구하고, 주기적 변경 강요와 문자 조합 규칙 강요를 하지 말라고 합니다. 대신 유출된 비밀번호 목록과 대조해 거부하라고 합니다. 교수님의 “주기적 변경 요구”, 교안의 “조합 사용”은 예전 관행입니다. 시험은 교안 표현(8~12자, 조합, 재사용 방지)으로 답하고, 실무 기준이 다르다는 것만 알아 두시면 됩니다.

HSTS가 하는 일 — 교수님이 설명하신 내용 아님

서버가 응답에 Strict-Transport-Security: max-age=31536000; includeSubDomains 같은 헤더를 보내면, 브라우저는 그 기간 동안 해당 도메인에 http://로 입력해도 https://로만 접속합니다. 첫 요청을 평문 HTTP로 보내는 순간을 노리는 SSL 스트리핑을 막습니다.

CSRF는 공격자 사이트가 사용자의 브라우저로 하여금 대상 사이트에 요청을 보내게 하고, 브라우저가 그 요청에 로그인 쿠키를 자동으로 붙이는 성질을 악용합니다. SameSite=Strict면 다른 사이트에서 시작된 요청에는 쿠키를 아예 붙이지 않고, Lax(현재 대부분 브라우저 기본값)는 링크 클릭 같은 최상위 GET 이동에만 붙입니다. CSRF 토큰은 서버가 폼마다 넣어 둔 난수를 요청과 함께 받아 비교하는 방식이라, 공격자 사이트는 그 값을 알 수 없습니다.

  • 인증은 사용자의 신원을 확인하는 과정이며, 인가는 인증된 사용자의 접근 권한을 결정하는 과정이다.

  • 보안 강화를 위해 다중 인증(MFA), 비밀번호 없는 인증, 생체 인증 등의 방식이 활용된다.
  • XSS, CSRF, 세션 하이재킹, 리플레이 공격 등의 위협을 방어하기 위해 입력값 검증, 보안 쿠키 설정, 토큰 서명 검증 등의 대책이 필요하다.
  • 안전한 인증 시스템을 구축하려면 HTTPS/TLS를 통한 암호화, 최소 권한 원칙 적용, 이상 징후 모니터링이 필수적이다.

교수님 설명 · 2차시 01:04~03:20

OAuth는 애플리케이션이 사용자의 비밀번호를 직접 다루지 않고도 사용자 대신 서버 자원에 요청할 수 있게 만든 권한 위임 규격. 예) 쇼핑몰에서 “구글 계정으로 로그인”을 눌러도 쇼핑몰은 구글 비밀번호를 모른다 — 구글 인증 서버가 대신 발급해 준 액세스 토큰만 받아 이메일·프로필을 가져온다. 초기 버전 OAuth 1은 요청마다 복잡한 서명이 필요해 모바일 앱·싱글 페이지 애플리케이션에 적용하기 힘들었다. 2012년 OAuth2는 서명 과정을 없애고 HTTPS만으로 토큰을 주고받는 베어러(Bearer) 방식을 도입해 가벼워졌고 여러 인증 흐름을 지원한다.

교수님 설명 · 2차시 03:20~07:29
  • 클라이언트: 사용자를 대신해 권한을 요청. 로그인을 누르면 권한 서버에 인증 요청을 보내며, 자신을 식별하려고 클라이언트 ID와 클라이언트 시크릿을 함께 보냄 → 사용자가 동의한 범위에 따라 인가 코드를 받고 다시 토큰 요청 단계로.
  • 리소스 소유자: 보호된 리소스의 실제 주인인 사용자. 비밀번호를 클라이언트에 주지 않고 권한 서버가 제공하는 로그인 창에서 증명 → 민감 정보가 클라이언트에 노출되지 않음.
  • 권한 서버(예: 구글): 인가 코드와 시크릿을 검증해 액세스 토큰과 선택적으로 리프레시 토큰을 발급. 액세스 토큰은 유효기간이 짧고, 리프레시 토큰은 만료된 액세스 토큰을 새로 받을 때 사용.
  • 리소스 서버(예: 구글 드라이브 파일을 제공하는 서버): 유효한 액세스 토큰이 있을 때만 리소스 반환. 토큰 유효성뿐 아니라 스코프(적용 범위)까지 확인해 “이 토큰으로 이 API를 불러도 되는가”를 점검.

사용자가 브라우저로 클라이언트(웹 서버)의 URL에 접근하면 인증이 시작되고, 클라이언트가 권한 서버의 로그인 페이지로 리다이렉션. 권한 서버가 로그인 UI를 보여 주고, 인증·동의가 끝나면 인가 코드를 만들어 클라이언트에 전달. 클라이언트는 그 코드를 다시 권한 서버에 제출해 액세스 토큰을 받고, 토큰으로 리소스 서버의 보호 자원을 요청. 핵심: 사용자 비밀번호가 권한 서버 밖으로 나가지 않고, 민감 정보 교환은 보안 채널로.

왜 코드를 먼저 받고, 토큰은 따로 받나 — 교수님이 설명하신 내용 아님

⑤의 인가 코드는 브라우저 주소창(리디렉트 URL)을 거쳐 전달되므로 기록·노출될 수 있습니다. 그래서 수명이 짧고 한 번만 쓸 수 있는 코드만 그 길로 보내고, 진짜 권한인 액세스 토큰은 ⑥⑦에서 서버끼리 직접(back channel), 클라이언트 시크릿으로 자신을 증명한 뒤 받습니다. 코드를 훔쳐도 시크릿(또는 PKCE의 code_verifier)이 없으면 토큰으로 바꿀 수 없습니다. ⑨⑩처럼 리소스 서버가 권한 서버에 토큰을 묻는 방식은 “토큰 조회(introspection)”이고, 토큰이 JWT면 리소스 서버가 서명만 검증하고 묻지 않기도 합니다.

OAuth2는 “인가” 표준 — 로그인에 쓰려면 OpenID Connect — 교수님이 설명하신 내용 아님

OAuth2(RFC 6749)는 원래 “이 앱이 내 자원에 접근해도 된다”는 권한 위임(인가) 규격입니다. 액세스 토큰은 “누구인지”를 표준 형식으로 알려 주지 않기 때문에, 로그인(인증)에 쓰려면 그 위에 얹은 OpenID Connect(scope에 openid, 결과로 ID 토큰 JWT)를 씁니다. 이번 실습은 액세스 토큰으로 userinfo API를 불러 이메일·이름을 받는 방식이라, OIDC 없이 OAuth2만으로 로그인을 흉내 낸 구조입니다. 퀴즈 2-1의 “인증과 인가를 분리한 프로토콜”이 맞는 보기로 처리된 것도 이 맥락입니다.

private String getAccessToken(String authorizationCode, String registrationId) {

    String clientId     = env.getProperty("oauth2." + registrationId + ".client-id");
    String clientSecret = env.getProperty("oauth2." + registrationId + ".client-secret");
    String redirectUri  = env.getProperty("oauth2." + registrationId + ".redirect-uri");

    // 토큰 엔드포인트에 보낼 폼 값 — 교안 8쪽 ⑥ 단계

    params.add("client_id", clientId);
    params.add("client_secret", clientSecret);        // 클라이언트가 자신을 증명 (서버끼리 직접 전송)
    params.add("redirect_uri", redirectUri);          // 인가 요청 때와 같은 값이어야 함
    params.add("grant_type", "authorization_code");

    HttpHeaders headers = new HttpHeaders();
    headers.setContentType(MediaType.APPLICATION_FORM_URLENCODED);
    HttpEntity entity = new HttpEntity(params, headers);

    // POST https://oauth2.googleapis.com/token
    ResponseEntity<String> response = restTemplate.exchange(tokenUri, HttpMethod.POST, entity, String.class);
    try {
        JsonNode accessTokenNode = objectMapper.readTree(response.getBody());
        return accessTokenNode.get("access_token").asText();   // 응답 JSON에서 access_token만 꺼냄
    } catch (IOException e) {
        throw new RuntimeException("Failed to parse access token response", e);
    }

정의 (교안 5쪽)

JSON Web Token은 JSON 형식의 데이터를 안전하게 전송하기 위한 개방 표준(RFC 7519). 주로 인증·인가에 쓰이며 클라이언트-서버 간 정보 교환 용도. 주요 특징: 자체 포함(Self-contained) — 사용자 정보·만료 시간을 토큰 안에 담아 별도 저장소 없이 인증 · 경량(Compact) — URL·헤더·쿠키로 보내기 적합 · 서명(Signature) — HMAC, RSA, ECDSA 등으로 서명해 위변조 확인.

“서명 = 비밀키로 암호화” · “서버는 공개키로 검증” — 정확한 표현

HS256의 서명은 암호화가 아니라 키를 넣은 해시(HMAC)입니다. 원문을 숨기지도, 복호화하지도 않습니다. 같은 비밀키를 가진 쪽이 같은 계산을 다시 해서 값이 같은지 비교할 뿐입니다. 또 교수님이 3차시 03:46에 “서버는 공개키로 서명을 검증”이라고 하신 것은 RS256·ES256 같은 비대칭 방식에만 맞습니다. 교안 실습의 HS256은 서명과 검증에 같은 비밀키를 씁니다(교수님도 25:30에 이렇게 정리). 시험에서 “JWT는 암호화된다”는 보기가 나오면 틀린 보기입니다.

JWT를 활용한 사용자 인가 및 권한 관리 (교안 10쪽)

  • 토큰 내 클레임 활용: 페이로드에 사용자 식별자, 역할(role), 권한(permission) 포함 · 이후 요청 시 HTTP 헤더에 "Bearer <token>"
  • 서버 측 검증 및 인가: 서명·만료시간·발급자 등을 검증해 무결성 확인 → 클레임으로 접근 권한·인가 결정 (예: 특정 API에 필요한 역할이 클레임에 있는지 확인)
  • 무상태(Stateless) 인증: 세션 저장소 없이 JWT 정보로 인가 — 분산 시스템·마이크로서비스에 효과적
  • 토큰 만료 및 갱신: 짧은 만료로 권한 변경을 빨리 반영, Refresh Token과 토큰 회전 전략으로 오래된 권한 정보 토큰 사용 방지

사용 시 고려사항 (교안 11쪽)

  • 보안 강화: HTTPS 전송, HttpOnly/Secure 쿠키 등 안전한 저장소, 최소한의 정보만, 민감 정보는 별도 암호화·안전한 관리

JwtController.java

JavaJwtController.java 전체 (교안 15~18쪽 1~131행, 주석 보강)
package com.example.hellospringboot.controller;

import io.jsonwebtoken.Claims;
import io.jsonwebtoken.Jwts;
import io.jsonwebtoken.SignatureAlgorithm;
import io.jsonwebtoken.security.Keys;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;
import javax.crypto.SecretKey;
import java.util.Date;
import java.util.HashMap;
import java.util.Map;

@RestController
@RequestMapping("/jwt")
public class JwtController {

    // (1/4) 상수 ───────────────────────────────────────────────
    // HS256 알고리즘에 적합한 안전한 비밀키 생성 — 실행할 때마다 새 256비트 난수 키
    // 왜 이렇게: 실습이라 키 관리 없이 바로 쓰려고. 운영에서는 KMS·HSM·환경변수 등에서 고정 키를 읽어야 재시작 후에도 검증된다
    private final SecretKey secretKey = Keys.secretKeyFor(SignatureAlgorithm.HS256);

    // 토큰 만료 시간 (Access: 10분, Refresh: 30분) — 단위 밀리초
    private final long ACCESS_TOKEN_EXPIRATION = 10 * 60 * 1000;    // 600,000ms
    private final long REFRESH_TOKEN_EXPIRATION = 30 * 60 * 1000;   // 1,800,000ms

    // (2/4) /jwt/generate ─────────────────────────────────────
    // 실제 환경에서는 사용자 인증에 성공한 경우에만 호출되어야 함 (이 코드에는 인증 검사 없음)
    @GetMapping("/generate")
    public Map<String, String> generateTokens() {
        String accessToken = Jwts.builder()
                .setSubject("test-user")                  // sub: 사용자 식별
                .setIssuer("example.com")                 // iss: 발급자
                .setIssuedAt(new Date())                  // iat: 발급 시각
                .setExpiration(new Date(System.currentTimeMillis() + ACCESS_TOKEN_EXPIRATION))  // exp
                .claim("role", "user")                    // 커스텀 클레임: 권한
                .signWith(secretKey)                      // 비밀키로 HS256 서명
                .compact();                               // header.payload.signature 문자열로

        // Refresh Token 생성 — tokenType 클레임으로 Access와 구분
        // 왜 이렇게: 같은 키로 서명하므로, 이 표시가 없으면 Access Token을 refresh 에 넣어도 통과해 버린다
        String refreshToken = Jwts.builder()
                .setSubject("test-user")
                .setIssuer("example.com")
                .setIssuedAt(new Date())
                .setExpiration(new Date(System.currentTimeMillis() + REFRESH_TOKEN_EXPIRATION))
                .claim("tokenType", "refresh")
                .signWith(secretKey)
                .compact();

        Map<String, String> tokens = new HashMap<>();
        tokens.put("accessToken", accessToken);
        tokens.put("refreshToken", refreshToken);
        return tokens;                                    // {"accessToken":"…","refreshToken":"…"}
    }

    // (3/4) /jwt/verify?token={토큰} ──────────────────────────
    @GetMapping("/verify")
    public ResponseEntity<?> verifyAccessToken(@RequestParam String token) {
        try {
            Claims claims = Jwts.parserBuilder()
                    .setSigningKey(secretKey)             // 검증에 쓸 키 (HS256이라 서명 키와 같음)
                    .build()
                    .parseClaimsJws(token)                // 서명 + exp 검사, 실패하면 예외
                    .getBody();                           // 통과하면 페이로드(클레임)
            return ResponseEntity.ok(claims);
        } catch (Exception e) {
            // 서명 불일치·만료·형식 오류 → HTTP 400 (교수님 설명의 401이 아님)
            return ResponseEntity.badRequest().body("Invalid Token: " + e.getMessage());
        }
    }

    // (4/4) /jwt/refresh?refreshToken={RefreshToken} ─────────
    @GetMapping("/refresh")
    public ResponseEntity<?> refreshAccessToken(@RequestParam String refreshToken) {
        try {
            Claims claims = Jwts.parserBuilder()
                    .setSigningKey(secretKey)
                    .build()
                    .parseClaimsJws(refreshToken)
                    .getBody();

            // tokenType 클레임을 확인하여 실제 Refresh Token인지 검증
            String tokenType = (String) claims.get("tokenType");
            if (tokenType == null || !tokenType.equals("refresh")) {
                return ResponseEntity.badRequest().body("Invalid Token type !");
            }

            // (선택 사항) DB나 캐시 등에서 기존 토큰 상태를 확인하여 이전 토큰 재사용을 방지하는 로직 추가 가능
            // → 이 부분이 없어서 이전 Refresh Token도 만료 전까지 계속 쓸 수 있음

            String newAccessToken = Jwts.builder()
                    .setSubject(claims.getSubject())      // 리프레시 토큰에서 꺼내는 것은 sub 하나
                    .setIssuer("example.com")
                    .setIssuedAt(new Date())
                    .setExpiration(new Date(System.currentTimeMillis() + ACCESS_TOKEN_EXPIRATION))
                    .claim("role", "user")                // 역할은 추출이 아니라 고정값
                    .signWith(secretKey)
                    .compact();

            // Refresh Token Rotation: 새로운 Refresh Token 발급
            String newRefreshToken = Jwts.builder()
                    .setSubject(claims.getSubject())
                    .setIssuer("example.com")
                    .setIssuedAt(new Date())
                    .setExpiration(new Date(System.currentTimeMillis() + REFRESH_TOKEN_EXPIRATION))
                    .claim("tokenType", "refresh")
                    // 필요 시 고유 토큰 ID 부여 로직 추가 (ex. .setId(newUniqueTokenId()))
                    .signWith(secretKey)
                    .compact();

            Map<String, String> tokens = new HashMap<>();
            tokens.put("accessToken", newAccessToken);
            tokens.put("refreshToken", newRefreshToken);
            return ResponseEntity.ok(tokens);
        } catch (Exception e) {
            return ResponseEntity.badRequest().body("Invalid Refresh Token: " + e.getMessage());
        }
    }
}

서명과 키 관리 (교안 23~24쪽)

  • 서명의 역할: 토큰의 무결성과 진위 보증 — 헤더·페이로드가 변조되지 않았음을 확인, 위변조 방지를 위한 디지털 서명
  • 알고리즘: 대칭키 HS256, HS384, HS512 · 비대칭키 RS256, RS384, RS512, ES256 등

교수님 설명 · 3차시 24:58~27:14

대칭키 방식은 같은 비밀키로 서명·검증, 비대칭키 방식은 개인키로 서명 후 공개키로 검증. 키 관리에서 먼저 고려할 공격은 알고리즘 혼동 공격 — 공격자가 헤더의 알고리즘 값을 일부러 바꿔 서명 검증을 속이므로, 파서 설정 시 반드시 HS256, RS256 등만 허용. 키 유출: 시크릿·개인 키를 코드에 하드코딩하지 말고 HSM이나 클라우드 키 관리 서비스에 보관, 환경변수·키 저장소는 최소 권한으로. 키 회전: 새 키를 도입할 때 새 키와 이전 키를 일정 기간 동시에 허용하고, 기간이 지나면 이전 키를 폐기해 오래된 토큰이 더 이상 유효하지 않게.

“none” 알고리즘 공격의 실제 모습 — 교수님이 설명하신 내용 아님

공격자가 헤더를 {"alg":"none"}으로, 페이로드의 role을 admin으로 바꾸고 서명 부분을 비워 헤더.페이로드.로 보냅니다. 헤더의 alg 값을 그대로 믿고 검증하는 라이브러리는 “서명 없음 = 검증 생략”으로 처리해 통과시킵니다. 또 다른 형태는 RS256(공개키 검증) 서버에 alg를 HS256으로 바꿔 보내, 누구나 아는 공개키를 HMAC 비밀키처럼 쓰게 만드는 것입니다. 대응은 교안 그대로 “서버가 허용 알고리즘을 정해 두고 헤더 값을 믿지 않기”입니다. 교안 실습의 JJWT parseClaimsJws()는 서명이 있는 토큰(JWS)만 받으므로 서명 없는 토큰은 예외로 거부합니다. 녹취의 “알고리즘 값을 일부러 이미 값으로”는 “none 값으로”의 전사 오류로 보입니다(추측 — 확인 필요 13).

  • exp 클레임으로 유효 기간 명시 → 탈취된 토큰의 사용 기간을 제한해 피해 최소화
  • 너무 길면 탈취 시 장기간 악용, 너무 짧으면 사용자 경험 저하·잦은 재인증 → 서비스 특성에 맞게
  • 전략: 짧은 Access Token + 상대적으로 긴 Refresh Token으로 재발급
교수님 설명 · 3차시 27:14~28:24

만료 시점이 지나면 토큰은 즉시 무효. 짧게 잡으면 탈취 피해 범위가 줄지만 너무 짧으면 매우 불편 → 서비스 성격에 맞춰 균형: 금융 서비스처럼 민감도가 높으면 짧게, 일반 웹은 상대적으로 길게. 서버 간 시간 동기화가 맞지 않으면 만료 검증에 오차가 생기므로 모든 서버 시각을 정확히 맞춘다.

3차시 요약 정리 (교안 27쪽)

  • JWT는 인증과 인가를 위한 강력한 도구지만, 서명 검증, 유효기간 관리, 키 보호가 필수적.
  • JWT는 암호화되지 않으므로 민감한 데이터를 직접 포함하면 안 됨.
  • Refresh Token을 활용한 인증 유지 전략을 적용하고, 토큰 탈취 방지를 위한 XSS 방어 및 안전한 저장소 사용이 중요.

18용어 정리

인증Authentication

등록된 사용자인지(누구인지) 확인하는 과정. 예: 로그인.

인가Authorization

인증된 사용자에게 리소스 접근 권한을 부여·제한하는 과정. 예: 등급별 권한.

다중 인증MFA, Multi-Factor Authentication

지식·소유·생체 중 서로 다른 종류 2개 이상을 함께 쓰는 인증.

패스워드리스Passwordless — FIDO2 / WebAuthn

공개키 기반으로 기기의 생체·PIN을 이용해 비밀번호 없이 인증.

적응형 인증Risk-based / Adaptive Authentication

위치·기기·시간 등으로 위험도를 평가해 필요하면 추가 인증 요구.

분산 신원DID, Decentralized Identity

분산원장 기반으로 사용자가 검증 가능한 증명서를 직접 보관·제시.

RBAC · ABAC · PBACRole / Attribute / Policy-Based Access Control

역할 / 속성 조합 / 조건 정책으로 권한을 정하는 접근 제어.

최소 권한 원칙Principle of Least Privilege

필요한 최소한의 권한만 부여. 기본 금지, 필요할 때만 허용.

세션 ID · JSESSIONIDSession ID

서버 세션 저장소를 가리키는 값. Set-Cookie로 받고 Cookie로 보냄.

HSTSHTTP Strict-Transport-Security

브라우저가 해당 도메인에 HTTPS로만 접속하도록 강제하는 응답 헤더.

크리덴셜 스터핑Credential Stuffing

다른 곳에서 유출된 계정·비밀번호 조합을 자동으로 대입하는 공격.

IDORInsecure Direct Object References

URL 등의 객체 식별자만 바꿔 남의 데이터에 접근. 서버의 소유자 검사로 방어.

CSRFCross-Site Request Forgery

로그인된 사용자의 브라우저로 원치 않는 요청을 보내게 하는 공격. CSRF 토큰·SameSite.

OAuth2Open Authorization 2.0 (RFC 6749)

비밀번호를 넘기지 않고 토큰으로 권한을 위임하는 개방형 표준.

인가 코드Authorization Code

사용자 동의 후 리디렉트로 받는 일회용 코드. 시크릿과 함께 토큰으로 교환.

Access / Refresh Token

짧게 쓰는 접근용 토큰 / 재로그인 없이 Access Token을 다시 받는 장기 토큰.

state 파라미터state

인가 요청에 넣는 난수. 돌아온 값과 비교해 CSRF 방지.

PKCEProof Key for Code Exchange

code_verifier·code_challenge로 인가 코드 가로채기를 막는 확장.

JWTJSON Web Token (RFC 7519)

헤더.페이로드.서명 구조의 토큰. 인코딩+서명이며 암호화가 아님.

클레임Claim

페이로드에 담는 정보. 표준(iss, sub, aud, exp, iat) + 커스텀(role 등).

토큰 회전Token Rotation

Refresh 때 새 Refresh Token도 발급하고 이전 것을 무효화하는 전략.

알고리즘 혼동 공격Algorithm Confusion

alg를 none 등으로 바꿔 서명 검증을 우회. 허용 알고리즘 고정으로 방어.

HSM · KMS · JWKSHardware Security Module / Key Management Service / JSON Web Key Set

키를 안전하게 보관하는 장치·클라우드 서비스 / 검증용 공개키 목록을 배포하는 형식.
