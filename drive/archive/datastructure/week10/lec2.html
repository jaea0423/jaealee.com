2-3-4 트리 — 정의 · Search · Insert

이진트리가 아닌 다중 키 탐색트리, B-트리의 사촌

01 2-3-4 트리란?

2-3-4 트리 (2-3-4 Tree)는 한 노드가 키를 여러 개 가질 수 있는 탐색 트리 (Search Tree)입니다. 이진 트리가 아닙니다.

BST나 AVL, 레드블랙은 한 노드에 키가 1개씩만 들어가는 이진 트리였어요. 2-3-4 트리는 다릅니다 — 한 노드가 키를 최대 3개까지 가질 수 있고, 자식은 최대 4개까지 가질 수 있어요.

이름의 의미

"2-3-4"는 한 노드가 가질 수 있는 자식 수의 종류를 뜻합니다.

노드 종류 키 개수 자식 개수 예시
2-노드 1개 2개 [37, _, _]
3-노드 2개 3개 [30, 34, _]
4-노드 3개 4개 [48, 60, 82]
연결 학습 — 레드블랙 트리와의 관계
2-3-4 트리는 레드블랙 트리와 등가입니다. 2-3-4 트리의 각 노드를 색칠된 이진 노드로 풀어쓰면 레드블랙 트리가 됩니다. 그래서 2-3-4 트리를 이해하면 레드블랙 트리의 동작 원리도 더 쉽게 이해돼요. DB 인덱스에서 자주 쓰이는 B-트리 (B-Tree)의 가장 작은 사례이기도 합니다.

02 2-3-4 트리의 조건

2개 조건을 모두 만족해야 2-3-4 트리입니다.

1
모든 노드의 자식 수는 2, 3, 4 중 하나

키가 k개면 자식이 k+1개. 즉 키 1개 → 자식 2개, 키 2개 → 자식 3개, 키 3개 → 자식 4개.

2
모든 리프 노드는 같은 레벨(높이)에 존재

트리가 한쪽으로 기울지 않고 항상 균형 유지. 이게 깨지면 2-3-4 트리가 아님.

핵심 규칙 2가지
  • 자식 수는 경계 수로 결정됨 (키 개수 + 1)
  • 자식의 위치는 경계값으로 결정됨 (키들이 자식 영역을 나누는 경계)

예: [30, 34]의 자식 3개 위치

키 30과 34가 경계 역할을 합니다:

  • 1번째 자식 = 30보다 작은 값 영역
  • 2번째 자식 = 30 ~ 34 사이 영역
  • 3번째 자식 = 34보다 큰 값 영역

03 트리 예시

다음 트리를 가지고 search와 insert를 연습합니다. 잘 외워두세요.

2-노드키 1, 자식 2
3-노드키 2, 자식 3
4-노드키 3, 자식 4
3칸 통일 표기 — 점선 칸은 비어있는 자리, 자식 간선은 실제 자식 수만큼만
표기 약속
모든 노드를 3칸짜리 박스로 통일해서 그립니다 (실제 4-노드 최대 키 수 기준). 실선 칸 = 키 들어있음, 점선 칸 = 비어있음. 자식 간선은 실제 자식 수만큼만 그려요.

05 search(53) 탐색 과정

BST의 탐색과 비슷한데, 한 노드 안에 키가 여러 개라서 어느 자식으로 갈지 결정하는 비교가 좀 더 들어갑니다.

탐색 규칙

  • 현재 노드의 키들과 차례로 비교
  • 찾는 값 x가 노드 안에 있으면 → 발견
  • 없으면 → 키들이 만드는 경계 영역 중 x가 속하는 자식으로 내려감
  • 리프까지 갔는데 없으면 → 없음

53 찾는 과정

빨강 = 탐색 경로, 노랑 = 찾은 키

단계별 설명

  1. Step 1 — 루트 [37] 방문. 53 > 37이므로 오른쪽 자식으로
  2. Step 2 — [48, 60, 82] 방문. 48 < 53 < 60이므로 2번째 자식(가운데)으로
  3. Step 3 — [50, 53, 57] 방문. 53 발견 ✓
시간 분석
방문한 노드 수 = 트리의 높이 h만큼 → 시간 복잡도는 O(h)

06 그렇다면 높이 h는?

search가 O(h)인데, h가 얼마나 작은지가 중요하겠죠. 두 극단을 생각해봅니다.

최선의 경우 — 모든 노드가 4-노드

연결 학습 — 이진트리에서의 직관
이진트리에서 자식을 꽉 채운 완전 이진트리의 높이는 log2n이었어요. 자식이 2개일 때 높이가 그렇게 된다는 뜻이죠. 2-3-4 트리에서 자식이 4개씩 꽉 차면 똑같은 논리로 log4n이 됩니다.

모든 노드가 4개씩 자식을 가지면 한 레벨 내려갈 때마다 노드 수가 4배씩 늘어남 → 높이가 가장 짧음:

hmin = log4 n

최악의 경우 — 모든 노드가 2-노드

반대로 모든 노드가 자식 2개씩만 가지면 이진트리와 다를 게 없음 → 높이가 가장 김:

hmax = log2 n

종합

log4 n  ≤  h  ≤  log2 n 밑이 다른 두 로그 사이
빅오 표기에서 로그의 밑은 무시
빅오 표기법에서 로그의 밑은 상수배 차이만 만들기 때문에 무시합니다. log4n과 log2n은 결국 같은 O(log n).
최종 결과
h = O(log n)  ⟹  search(x) = O(log n)

36이 들어갈 자리는 [35,_,_] — 빈 칸이 있으니 그냥 들어감

삽입 후 결과

결론

08 insert(55) — split이 필요한 경우

문제 상황
55가 들어갈 자리는 [50, 53, 57] 노드인데 이미 키 3개로 가득 차 있음. 더 못 넣음 → split 필요.

split의 핵심 아이디어

Top-down Split
내려가는 길에 가득 찬 노드(4-노드, 키 3개)를 만나면 미리 쪼개고 내려갑니다.
  • 가운데 키를 부모로 올림
  • 나머지 두 키는 좌/우로 분리
  • 이렇게 미리 깨고 내려가면 리프에 도달했을 때 항상 자리가 있음

왜 미리 쪼개나?

리프에서 가득 찼다고 그제서야 쪼개려면 부모도 가득 찼을 수 있고, 그러면 부모도 쪼개야 하고... 위로 연쇄적으로 영향이 가요. 미리 깨고 내려가면 부모가 항상 여유가 있어서 안전합니다.

Step 1 — 시작 트리

Step 1insert(55) 시작
빨강 = 가득 찬 노드 (4-노드). [48,60,82]와 [50,53,57]이 둘 다 가득 차 있음

Step 2 — [48, 60, 82] split

55가 가는 길에 첫 번째로 만나는 가득 찬 노드는 [48, 60, 82]. 미리 쪼갭니다.

Split 과정
  1. 가운데 키 60을 부모(루트)로 올림 → 루트 [37]이 [37, 60, _]가 됨
  2. 나머지 두 키 48과 82는 두 노드로 분리 → [48, _, _]와 [82, _, _]
  3. [48, 60, 82]의 자식 4개를 새 노드 두 개가 나눠 가짐 (왼쪽 2개는 [48], 오른쪽 2개는 [82])
Step 2[48,60,82] split 결과
초록 = 새로 생긴 키/노드. 60이 루트로 올라가고 [48,60,82]가 [48]과 [82]로 분리됨

Step 3 — split 후 55가 갈 길 결정

이제 split된 트리에서 다시 55가 어디로 갈지 봅니다:

  • 루트 [37, 60, _]에서 비교: 37 < 55 < 60 → 2번째 자식 [48, _, _]로
  • [48, _, _]에서 비교: 48 < 55 → 오른쪽 자식 [50, 53, 57]로
  • 도착! 그런데 [50, 53, 57]이 또 가득 참 → 또 split 필요

Step 4 — [50, 53, 57] split

두 번째 split
  1. 가운데 키 53을 부모 [48, _, _]로 올림 → [48, 53, _]가 됨
  2. 나머지 두 키 50과 57은 두 노드로 분리 → [50, _, _]와 [57, _, _]
  3. 부모의 자식이 2개에서 3개로 늘어남
Step 4[50,53,57] split 결과
[50,53,57]이 [50]과 [57]로 쪼개지고 53이 부모로 올라감 → 55 들어갈 자리 생김

Step 5 — 55 삽입

이제 55가 들어갈 자리를 다시 찾습니다:

  • 루트 [37, 60]에서: 37 < 55 < 60 → 2번째 자식 [48, 53]으로
  • [48, 53]에서: 53 < 55 → 3번째 자식 [57, _, _]로
  • [57, _, _]에 자리 있음 → [55, 57, _]로 삽입 완료 ✓
Step 5insert(55) 완료
최종 결과 — 55가 [55, 57, _] 자리에 정렬된 상태로 삽입됨

split 정리

split의 효과
  • 가득 찬 노드를 만나면 가운데 키를 부모로 올림
  • 나머지 두 키는 좌/우 두 노드로 분리
  • 결과적으로 가지(자식)가 하나 더 생기는 효과
  • 리프에 도착했을 때는 항상 자리가 있음을 보장
루트가 가득 차 있을 때는?
가운데 키를 올릴 부모가 없으면 새 루트가 생성되고 트리 높이가 1 증가합니다. 이게 2-3-4 트리에서 높이가 늘어나는 유일한 경로 (그래서 모든 리프가 같은 레벨 유지됨).

09 Insert 시간복잡도 분석

Split 1회의 비용

Split 한 번에 드는 작업은:

  • 가운데 키 하나를 부모로 올림
  • 나머지 두 키를 두 노드로 분리
  • 자식 4개를 새 두 노드에 2개씩 나눠줌

전부 상수 시간에 끝나는 작업이에요.

1번의 split = O(1)

Insert 전체 시간

최악의 경우
리프까지 가는 길의 모든 레벨이 4-노드(가득 참)여서 매 레벨마다 split을 해야 하는 상황.

이때도 split이 일어나는 횟수는 트리 높이 h를 넘지 않습니다 (각 레벨마다 한 번씩).

Insert = (search 시간) + (split 횟수 × O(1))
= O(h) + O(h) · O(1)
= O(h)
결론
Insert = O(h) = O(log2 n) = O(log n)
시험 안내
교수님 말씀: 기말고사부터는 코드를 직접 알려주지 않으면 외울 필요 없음. 원리 이해 + 연산 시간 계산에 집중.

10 Delete 연산 — 새 예시 트리

Delete 설명을 위해 새 트리를 가지고 시작합니다. 더 큰 트리(Level 3)예요.

전제
Delete의 기본 가정: 삭제할 키 x가 리프에 있다. 리프에 없으면 리프로 옮겨와서 지우는 트릭을 씀 (§12에서 설명).

새 예시 트리

트리 구조 (Level 3까지)

이 트리로 delete 케이스 3가지를 살펴봅니다:

  • delete(32) — 리프에 있고, 지워도 조건 안 깨짐 (제일 쉬움)
  • delete(20) — 내부 노드에 있음 (successor 교체)
  • delete(70) — 지우면 조건 1 위반 (fusion 필요)

11 delete(32) — 리프에 있고 조건 안 깨질 때

32는 리프 노드 [32, 34, _]에 있어요. 그냥 지우면 됩니다.

지운 후 [32, 34, _] → [34, _, _]가 됩니다. 키가 1개여도 2-노드 = 유효한 형태라서 조건 안 깨짐.

결과delete(32) 완료
언제 fusion 없이 그냥 지울 수 있나?
리프 노드가 3-노드 또는 4-노드(키 2개 이상)일 때. 키 하나를 빼도 노드가 여전히 살아있음.

12 delete(20) — 내부 노드에 있을 때

20은 루트 [20, 50, _]에 있어서 리프가 아니에요. 직접 못 지웁니다.

해결 — 다음 값(successor)과 교체

연결 학습 — BST 삭제와 동일
이건 BST의 삭제 알고리즘과 똑같은 트릭이에요. 내부 노드를 지울 때 in-order successor(중위순회 다음 값)와 교체한 뒤, 리프에서 지웁니다. Predecessor(이전 값)와 교체해도 됩니다.

20의 successor 찾기

BST 규칙: 20의 오른쪽 서브트리에서 가장 작은 값을 찾으면 됨.

  • 20의 바로 오른쪽 자식 → [30, _, _]
  • [30, _, _]의 왼쪽 자식 → [22, 24, 26]
  • [22, 24, 26]은 리프 → 가장 왼쪽 키 = 22가 successor

처리 과정

2단계
  1. 루트의 20 자리에 22를 옮김 → 루트가 [22, 50, _]가 됨
  2. 리프 [22, 24, 26]에서 22를 지움 → [24, 26, _]가 됨
결과delete(20) 완료
조건 1, 2 여전히 만족 — 트리는 유효한 2-3-4 트리

delete(32) 다른 관점

참고로 delete(32)도 같은 트릭으로 처리 가능:

  • 32는 리프에 있지만, 내부 노드 [30, _, _]의 successor임
  • 만약 30을 지우라고 했다면 → 30의 successor 찾기 → 32와 교체 → 리프에서 32 지움

13 Fusion — 표준 방식 (Redistribution)

delete(70)을 해봅시다. 70은 리프 [70, _, _]에 있는데, 지우면 [70, _, _]의 부모 [80, _, _]의 자식이 1개가 돼버려요. 조건 1 위반!

fusion 개념

Fusion은 split의 반대. 내려가는 길에 2-노드를 만나면 미리 3-노드 또는 4-노드로 바꿔놓고 내려갑니다.
Top-down fusion
Insert의 top-down split과 마찬가지로, Delete도 내려가는 길에 2-노드를 만나면 미리 처리합니다. 이렇게 하면 리프에서 키를 지울 때 항상 안전하게 지울 수 있어요 (최소 3-노드 보장).

표준 방식 — Redistribution (재분배)

2-노드를 처리하는 첫 번째 방법: 인접한 형제가 키 2개 이상이면 그 형제에서 키 하나를 빌려옵니다.

구체적인 절차 (회전과 비슷)

표준 Redistribution
  1. 형제에서 키를 빌려옴 — 단, 형제 키를 바로 가져오는 게 아니라 BST 순서 유지를 위해 부모를 거쳐서 옴
  2. 부모의 키(2-노드와 형제 사이 키)가 2-노드로 내려옴
  3. 형제의 인접 키가 부모로 올라감

delete(70) 예시로 보면:

현재 상태

  • 부모 [50, _, _]의 자식이 [30, _, _]과 [80, _, _] (둘 다 2-노드)
  • 아 — 여기는 [80, _, _]이 2-노드라서 fusion이 필요한 게 맞는데, 형제 [30, _, _]도 2-노드라 빌릴 곳이 없음. 이 경우는 다음 절(§15)에서 다룸.

형제가 3-노드인 경우를 가정해서 표준 방식을 보여드릴게요. 만약 [80, _, _]의 형제가 [22, 24, 26]이었다고 가정 (다른 시나리오):

표준 방식형제에서 빌리기 (가상 시나리오)
표준 redistribution — 부모 50이 내려오고, 형제의 26이 부모로 올라감

핵심 동작 정리

  • 부모 키 내림: 50이 [80, _, _]로 내려와서 [50, 80, _]가 됨
  • 형제 키 올림: [22, 24, 26]의 가장 큰 키 26이 부모로 올라가 [50] → [26]이 됨
  • BST 순서: 왼쪽 모두 < 26 < 50 < 80 ✓
왜 이렇게 복잡하게?
그냥 형제 키를 바로 가져오면 BST 순서가 깨져요. 부모를 거쳐서 가져와야 키 순서가 유지됩니다. (레드블랙 트리의 회전과 비슷한 발상)

14 Fusion — 교수님 노트 방식

강의에서는 다른 예시(delete(32) 시나리오)로 fusion을 설명하셨어요. 그대로 재현해볼게요.

가정 시나리오

지금부터 다루는 시나리오: 중간 노드 [30, _, _]이 2-노드여서 fusion을 미리 해야 하는 상황. 형제 [10, 15, _]는 3-노드.

교수님 설명

교수님 방식
  1. [10, 15, _]에서 15를 위(부모)로 보냄
  2. 부모 [20, _, _]가 [20, 30, _]이 되도록 30을 흡수
  3. [10, 15, _]의 자식 18을 [20, 30, _]의 새 자식으로 이동
  4. 결과: [20, 30, _]의 자식이 [18, _, _], [22, 24, 26], [32, 34, _]
잠깐, 이게 표준 방식과 뭐가 달라?

사실 본질은 같습니다. 결과만 보면:

  • 형제의 키 하나가 부모로 올라감 (15)
  • 원래 부모 키가 2-노드로 내려옴 (20 → 그런데 여긴 30 자리)
  • 형제의 자식 하나가 옮겨감 (18)

표현 방식이 약간 다를 뿐 redistribution과 동일한 효과입니다. 시험 답안은 교수님 표현대로 쓰는 게 안전.

시각화 — 교수님 노트 그대로

Beforedelete 내려가는 중 [30,_,_] 만남
Afterfusion 결과
[30, _, _]이 [20, 30, _] 3-노드로 변신, 자식이 3개로 늘어남
중요
이렇게 미리 fusion을 해놓으면, 그 뒤 32를 지우러 내려가도 안전합니다. (어차피 [32, 34, _]는 리프에서 그냥 지우면 되는데, 핵심은 2-노드를 만나면 무조건 미리 처리한다는 것)

이렇게 fusion이 1번 일어나면 O(1)로 끝납니다.

15 Fusion — 형제도 2-노드면? (Merge)

위 두 방식 모두 형제가 3-노드 이상일 때 가능했어요. 형제마저 2-노드면 빌려올 게 없습니다. 이때는 합치기 (Merge).

Merge 절차

Merge
  1. 부모의 키 1개를 끌어내려서 두 형제를 하나의 4-노드로 합침
  2. 두 자식 노드와 부모 키 1개 → 새 4-노드
  3. 부모는 키 하나 잃음 (자식도 1개 줄어듦)

예시 — 강의 자료 그대로

다음 상황이라고 가정:

  • 루트 [50, _, _]
  • 중간: [10, 20, 30] (4-노드!) / [80, _, _]
  • 리프: [1, 5, _] [18, _, _] [22, 24, 26] [35, 34, _] / [70, _, _] [100, _, _]

여기서 만약 형제도 2-노드인 상황이 더 진행되면 결국 부모와 두 자식을 다 합쳐서:

Merge 결과부모와 자식들 합치기
루트가 2-노드일 때 fusion 하면 트리 높이가 1 줄어듦

특수 케이스 — 루트가 2-노드

루트 fusion = 높이 감소
  • 일반 fusion은 높이 안 바꿈 — 그냥 노드들 재배치
  • 하지만 루트가 2-노드인데 자식들도 2-노드면 → 셋이 합쳐져서 새 4-노드가 새 루트가 됨
  • 이게 2-3-4 트리에서 높이가 줄어드는 유일한 경로 (반대로 insert에서 split이 높이를 늘리는 유일한 경로)

16 Delete 시간복잡도 분석

Fusion 1회의 비용

Fusion은 split과 마찬가지로 상수 시간 작업:

  • 형제, 부모, 자기 자신만 보면 됨
  • 키와 자식 포인터 몇 개 옮기는 작업
1번의 fusion = O(1)

Delete 전체 시간

최악의 경우
리프까지 가는 길의 모든 레벨이 2-노드여서 매 레벨마다 fusion을 해야 하는 상황.

이때도 fusion 횟수는 트리 높이 h를 넘지 않습니다.

Delete = (search 시간) + (fusion 횟수 × O(1))
= O(h) + O(h) · O(1)
= O(h)
결론
Delete = O(h) = O(log2 n) = O(log n)

3개 연산 시간 정리

연산 최선 최악 점근적 복잡도
search(x) O(log4 n) O(log2 n) O(log n)
insert(x) O(log4 n) O(log2 n) O(log n)
delete(x) O(log4 n) O(log2 n) O(log n)
전부 O(log n)
2-3-4 트리는 항상 균형이 유지되기 때문에 search, insert, delete 모두 로그 시간이 보장됩니다. 레드블랙 트리와 동일한 성능 — 둘이 본질적으로 같은 트리니까 당연한 결과예요.

17 2-3-4 트리 ↔ 레드블랙 트리

2-3-4 트리와 레드블랙 트리는 1:1 변환이 가능합니다. 같은 트리를 다른 표현으로 본 것뿐이에요.

변환 규칙

노드 종류별 변환
  • 2-노드 (자식 2개) → 1레벨로 구성: [a] (black)
  • 3-노드 (자식 3개) → 2레벨로 구성: [b] black을 부모로, <a> red를 왼쪽 자식
  • 4-노드 (자식 4개) → 2레벨로 구성: [b] black을 부모로, <a> <c> red를 양쪽 자식
왜 이런 변환이 가능?

레드블랙 트리는 자식이 최대 2개(이진 트리). 2-3-4 트리의 4-노드는 자식이 4개이므로 그대로 못 옮김. 그래서 한 4-노드를 black-red 2레벨 구조로 펼쳐서 자식을 2개씩 분산시키는 거예요.

예시 — 우리 트리를 변환해보기

섹션 §3에서 본 트리를 변환합니다:

  • 루트 [37] (2-노드) → [37] black 한 레벨
  • [30, 34] (3-노드) → [34] black 위, 왼쪽 자식 <30> red
  • [48, 60, 82] (4-노드) → [60] black 위, 양쪽 자식 <48> <82> red
  • [5] → [5] black
  • [32, 33] → [33] black + <32> red (3-노드)
  • [35] → [35] black
  • [40] → [40] black
  • [50, 53, 57] → [53] black + <50> <57> red (4-노드)
  • [69] → [69] black
  • [86, 98] → [98] black + <86> red (3-노드)

변환된 레드블랙 트리

[ ] Black 노드
< > Red 노드
None Null 리프 (black)
[ ] = Black, < > = Red, 회색 = None(리프, black)

레드블랙 조건 검증

조건 5 (Black Height) 검증

루트 [37]에서 모든 리프(None)까지 가는 경로의 black 노드 수를 세보면:

  • 예: 37(B) → 34(B) → 30(R) → None(B) → ... black 4개
  • 예: 37(B) → 60(B) → 48(R) → 40(B) → None(B) → ... black 4개

모든 경로가 black 4개로 동일 → 조건 5 만족 ✓

핵심 통찰
이 변환이 1:1이라는 건, 두 자료구조가 본질적으로 같은 정보를 가지고 같은 일을 한다는 뜻. 그래서 시간 복잡도도 같음 (모두 O(log n)).

18 높이 분석 — 상계와 하계

레드블랙 트리에서 우리는 h ≤ 2·log₂ n까지 봤어요(섹션 §9, 10-1 강의노트 참고). 그런데 2-3-4 트리와의 관계를 이용하면 이걸 더 타이트하게 만들 수 있다는 게 오늘 핵심.

교수님 보충 예정
수업 시간에 막힌 부분이라 다음 시간에 보충 예정. 지금 노트에는 강의에서 다룬 만큼만 정리해둡니다.

레드블랙 vs 2-3-4 트리 높이 관계

변환 규칙에서:

  • 2-노드 → 1레벨 (black만)
  • 3-노드 → 2레벨 (black + red)
  • 4-노드 → 2레벨 (black + red 2개)

즉 2-3-4 트리에서 1레벨이 레드블랙 트리에서 최대 2레벨이 됨. 따라서:

hRB ≤ 2 · h234

2-3-4 트리에서 h ≤ log₂ n이었으니까:

hRB ≤ 2 · log2 n   (이미 알던 결과)

더 타이트한 분석

2-3-4 트리의 더 좋은 분석을 통해 2·log₃ n까지 줄어든다는 것을 보일 수 있어요. (자세한 증명은 다음 시간)

hRB ≤ 2 · log3 n log₃ < log₂이므로 더 타이트한 상계

상계와 하계 개념

연결 학습 — 알고리즘 분석 일반
이건 알고리즘 분석에서 자주 등장하는 개념. 이산수학에서도 함수의 bound 개념으로 나옴.

하계 (Lower Bound)

a ≤ 성능,   b ≤ 성능

여기서 a, b는 하계. 성능이 적어도 이만큼은 된다는 보장.

하계는 클수록 좋음 — 더 강한 보장을 의미.

상계 (Upper Bound)

성능차이 ≤ c,   성능차이 ≤ d

여기서 c, d는 상계. 성능 차이(또는 비용)가 최대 이만큼.

상계는 작을수록 좋음 — 더 효율적임을 의미.

트리에서의 상계 = 높이

핵심
트리에서는 상계가 높이 h

왜냐하면 search, insert, delete 모두 O(h) 시간이 걸리기 때문에, 최악 비용의 상계가 곧 트리의 높이.

왜 더 타이트한 상계를 구하나?
  • 2·log₂ n과 2·log₃ n은 둘 다 O(log n)으로 같음 (빅오 관점)
  • 하지만 실제 상수 계수까지 보면 2·log₃ n이 더 작음
  • 이론적으로 알고리즘이 얼마나 좋은지 더 정밀하게 보여줌

19 오늘 꼭 기억할 것

시험 포인트
  1. 2가지 조건:
    • 자식 수 2, 3, 4 중 하나
    • 모든 리프가 같은 레벨
  2. 노드 종류: 2-노드(키 1·자식 2), 3-노드(키 2·자식 3), 4-노드(키 3·자식 4)
  3. search 시간복잡도: O(h) = O(log n)
    • 최선: log4n (모두 4-노드)
    • 최악: log2n (모두 2-노드)
    • 빅오 표기에서 로그 밑은 무시 → O(log n)
  4. Insert는 리프에만:
    • Split (top-down): 내려가는 길에 4-노드 만나면 미리 쪼갬
    • 가운데 키 → 부모로 올림, 나머지 → 좌/우 분리
    • Split 1회 = O(1), 전체 = O(h) = O(log n)
    • 높이 증가: 루트 split 시에만
  5. Delete 처리 순서:
    • 리프에 있고 노드가 3/4-노드면 → 그냥 지움
    • 내부 노드에 있으면 → successor(또는 predecessor)와 교체 후 리프에서 지움
    • 리프가 2-노드면 → fusion 필요
  6. Fusion (top-down):
    • 내려가는 길에 2-노드 만나면 미리 3/4-노드로 변환
    • 형제가 3-노드 이상이면 → redistribution (키 빌려옴)
    • 형제도 2-노드면 → merge (부모 키 1개와 합침)
    • Fusion 1회 = O(1), 전체 = O(h) = O(log n)
  7. 높이가 변하는 유일한 경로:
    • 증가: insert에서 루트 split 발생
    • 감소: delete에서 루트 merge 발생
  8. 3개 연산 모두 O(log n) — 균형 보장
  9. 레드블랙 트리와 1:1 변환:
    • 2-노드 → 1레벨 (black)
    • 3-노드 → 2레벨 (black + red 1개)
    • 4-노드 → 2레벨 (black + red 2개)
    • 두 자료구조는 본질적으로 같은 것
  10. 상계 (Upper Bound)와 하계 (Lower Bound):
    • 하계: a ≤ 성능 → 클수록 좋음
    • 상계: 비용 ≤ c → 작을수록 좋음
    • 트리에서 상계 = 높이 h
  11. 레드블랙 트리 높이 분석 개선:
    • 기존: hRB ≤ 2·log2n
    • 2-3-4 트리 매칭 이용: 2·log3n까지 가능 (보충 예정)
  12. 시험 안내: 코드 외울 필요 없음. 원리 이해 + 연산 시간 계산이 핵심
