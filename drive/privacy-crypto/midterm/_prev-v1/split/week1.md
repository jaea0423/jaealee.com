2. 개인정보 여부는 값의 형식이 아니라 **식별 가능성**으로 판단한다 — 생존성 · 개인 관련성 · 식별 가능성.
3. 보안 목표는 **CIA + 인증 · 부인방지 · 책임추적성**이고, 하나의 암호기술이 모든 목표를 주지 않으므로 **조합**해서 쓴다.

### [w1-s1-1] 과목 소개와 수업 목표 (교안 p.OT:4)

> **[교수님 말씀]**
> 
> 개인정보보호암호기술은 **2개의 축**으로 이루어져 있다.
> 
> - 개인정보를 **어떻게 보호할 것인가**
> - 그 보호를 **실제로 가능하게 만드는 암호기술**
> 
> 개인정보보호는 법과 제도의 영역이라고 생각하기 쉽지만, **법이 요구하는 안전조치를 실제 시스템 위에서 구현해 주는 것은 결국 암호기술**이다.
> 
> 이 과목은 암호학의 기본 원리를 제대로 이해하고, 그 원리를 개인정보의 **수집 · 저장 · 전송 · 파기** 과정에 적용하는 방법까지 연결해서 배우는 것을 목표로 한다.

## [1주차 04] 개인정보의 법적 정의와 판단 기준

### [w1-s4-1] 개인정보 보호법 제2조 제1호 (교안 p.개요:6)

> **[교안]** **법령 원문**
> 
> **"개인정보"란 살아 있는 개인에 관한 정보로서 다음 각 목의 어느 하나에 해당하는 정보를 말한다.**
> 
> 가. 성명, 주민등록번호 및 영상 등을 통하여 개인을 알아볼 수 있는 정보
> 
> **나. 해당 정보만으로는 특정 개인을 알아볼 수 없더라도 다른 정보와 쉽게 결합하여 알아볼 수 있는 정보. 이 경우 쉽게 결합할 수 있는지 여부는 다른 정보의 입수 가능성 등 개인을 알아보는 데 소요되는 시간 · 비용 · 기술 등을 합리적으로 고려하여야 한다.**
> 
> 다. 가목 또는 나목을 가명처리함으로써 원래의 상태로 복원하기 위한 추가 정보의 사용 · 결합 없이는 특정 개인을 알아볼 수 없는 정보 (= 가명정보)

**정의에서 읽어야 할 세 가지**

| 표현 | 의미 |
|---|---|
| 「살아 있는」 개인 | 사망자 정보는 원칙적으로 개인정보가 아님 (유족 관련성은 별도 판단) |
| 「개인에 관한」 정보 | 법인 · 단체의 정보는 개인정보가 아님 |
| 「쉽게 결합하여」 알아볼 수 있는 정보까지 포함 | 보호 범위가 넓게 설정됨 |

### [w1-s4-2] 개인정보 판단의 3가지 기준 (교안 p.개요:7)

| 기준 | 질문 | 세부 |
|---|---|---|
| **생존성** | 살아 있는 개인에 관한 정보인가? | ▪ 사망자 정보는 원칙적 제외<br>▪ 태아 · 사망자 정보는 별도 검토<br>▪ 법인 · 단체 정보는 해당 없음 |
| **개인 관련성** | 특정 개인에 관한 정보인가? | ▪ 신체 · 재산 · 사회적 지위 등<br>▪ 주관적 평가 · 판단 정보도 포함<br>▪ 통계값 · 집합 정보는 원칙적 제외 |
| **식별 가능성** | 특정 개인을 알아볼 수 있는가? | ▪ 그 자체로 식별 가능 (직접 식별자)<br>▪ 결합으로 식별 가능 (간접 식별자)<br>▪ 결합의 용이성: 입수 가능성 · 시간 · 비용 · 기술 고려 |

> **[교안 강조]**
> 
> **세 가지 기준을 모두 충족하면 개인정보 → 개인정보 보호법의 적용을 받는다.**

## [1주차 08] 개인정보 생명주기와 단계별 위협

### [w1-s8-1] 개인정보 생명주기와 단계별 위협 (교안 p.개요:15)

*[도식] 수집 → 저장 · 관리 → 이용 · 제공 → 파기, 박스 아래는 단계별 위협 (개요 p.15 도식)* — 도식 속 글자: 수집 / 동의 없는 수집 과도한 수집 출처 불명확 / 저장 · 관리 / 평문 저장 접근권한 과다 백업 미보호 / 이용 · 제공 / 목적 외 이용 제3자 무단 제공 위탁 관리 미흡 / 파기 / 보유기간 초과 불완전 삭제 백업본 잔존

**단계별 보호 조치**

| 단계 | 핵심 원칙 | 대표 보호 조치 |
|---|---|---|
| **수집** | 최소 수집 · 목적 명확화 · 동의 | 전송구간 암호화, 수집 항목 최소화, 동의 이력 관리 |
| **저장 · 관리** | 기밀성 확보 · 접근 최소화 | 저장 시 암호화, 비밀번호 일방향 해시, 접근권한 통제 |
| **이용 · 제공** | 목적 범위 내 이용 · 추적 가능성 | 가명처리, 접속기록 보관, 위탁 계약 · 점검 |
| **파기** | 지체 없는 · 복구 불가능한 파기 | 완전 삭제, 매체 폐기, 암호키 파기(크립토 셰딩) [보충: 영어 crypto-shredding은 보통 "크립토 슈레딩"으로 읽습니다. 교안 표기(셰딩)를 그대로 두되, 답안에는 영어를 같이 쓰는 편이 안전합니다.] |

> **[교안 강조]**
> 
> **개인정보는 한 시점이 아니라 전 생명주기에 걸쳐 보호되어야 하며, 각 단계마다 필요한 암호기술이 다르다.**


## [1주차 09] 정보보안의 기본 개념과 보안의 3대 요소(CIA)

### [w1-s9-1] 정보보안 (Information Security) (교안 p.개요:16)

- **정보를 여러 위협으로부터 보호하여 그 가치를 유지하는 활동** — 정보의 전체 라이프사이클(생성 · 처리 · 저장 · 전송 · 폐기)에 걸쳐 적용
- **보호 대상의 범위** — 디지털 데이터 : 파일, 데이터베이스, 로그, 통신 패킷 / 비(非)디지털 정보 : 인쇄 문서, 구두 전달 내용, 업무 지식

**보안을 구성하는 세 가지 축**

| 기술적 보안 | 관리적 보안 | 물리적 보안 |
|---|---|---|
| 암호화, 접근통제, 방화벽, 침입탐지, 로그 분석 등 | 정책 · 지침 수립, 권한 관리, 교육, 정기 점검 · 감사 등 | 출입통제, 전산실 보호, 저장매체 · 문서 관리, 폐기 절차 등 |

> **[교안 강조]**
> 
> **암호기술은 「기술적 보안」의 핵심 수단이지만, 세 축이 함께 갖추어질 때만 실제 보호 효과가 나타난다.**

### [w1-s9-2] 보안의 3대 요소 (CIA) (교안 p.개요:17)

*[도식] 가운데 정보보안, 세 꼭짓점에 기밀성 · 무결성 · 가용성 (개요 p.17 도식)* — 도식 속 글자: 정보보안 / 기밀성 Confidentiality / 무결성 Integrity / 가용성 Availability

| 요소 | 정의 | 깨졌을 때 | 대표 기술 |
|---|---|---|---|
| **기밀성** (Confidentiality) | 인가된 사용자만 정보에 접근할 수 있도록 보장 | 정보 노출 · 도청 | 암호화, 접근통제 |
| **무결성** (Integrity) | 정보가 인가되지 않은 방법으로 변경되지 않도록 보장 | 위 · 변조, 신뢰 상실 | 해시, MAC, 전자서명 |
| **가용성** (Availability) | 인가된 사용자가 필요할 때 정보를 사용할 수 있도록 보장 | 서비스 중단 | 이중화, 백업, DDoS 방어 |


## [1주차 10] 기밀성 · 무결성 · 가용성 자세히

### [w1-s10-1] 기밀성 (Confidentiality) (교안 p.개요:18)

**정의** — 인가받지 않은 개인 · 시스템이 정보의 내용을 알 수 없도록 보장하는 성질. 데이터가 유출되더라도 「읽을 수 없는」 상태를 유지하는 것이 목표.

**개인정보 보호에서의 의미**

- **고유식별정보 · 비밀번호 · 생체인식정보는 저장 · 전송 시 암호화가 요구됨**
- **접근권한을 업무상 필요한 최소 범위로 제한 (최소권한 원칙)**

*[도식] 평문 저장 → 암호화 저장 (개요 p.18 도식)* — 도식 속 글자: 평문 저장 "홍길동 / 900312-1……" / 암호화 저장 "9f2c a41b 77de …" / 유출되어도 키가 없으면 내용을 알 수 없음

| 위협 | 설명 | 대응 기술 |
|---|---|---|
| **도청 (Eavesdropping)** | 네트워크를 오가는 데이터를 몰래 관찰 | 전송 구간 암호화 (TLS) |
| **데이터베이스 탈취** | 저장된 데이터를 통째로 반출 | 저장 시 암호화, 키 분리 보관 |
| **권한 오남용** | 접근권한을 가진 자가 목적 외로 열람 | 최소권한, 접속기록 · 이상행위 탐지 |
| **트래픽 분석** | 내용이 아닌 통신 패턴에서 정보를 추론 | 패딩, 트래픽 은닉, 익명 통신 |

### [w1-s10-2] 무결성 (Integrity) (교안 p.개요:19)

**정의** — 정보가 인가되지 않은 방법으로 변경 · 삭제되지 않았음을 보장하는 성질. 「변경을 막는 것」보다 「변경 여부를 확인할 수 있는 것」이 실질적 목표.

**개인정보 보호에서의 의미**

- **개인정보의 정확성 · 최신성 유지는 정보주체의 권리와 직결됨**
- **접속기록 · 로그의 무결성이 깨지면 사고의 원인 추적 자체가 불가능해짐**

*[도식] 원본 → 해시값(지문) → 변조 탐지 (개요 p.19 도식)* — 도식 속 글자: 원본 문서 "이체 금액 100만원" / 해시값 (지문) H = a3f1…9c2 / 한 글자만 바뀌어도 해시값이 완전히 달라짐 → 변조 탐지

| 위협 | 설명 | 대응 기술 |
|---|---|---|
| **메시지 변조** | 전송 중인 데이터의 내용을 바꿔치기 | 해시 함수, 메시지 인증 코드(MAC) |
| **데이터 위조** | 존재하지 않던 데이터를 만들어 삽입 | 전자서명, 인증서 |
| **재전송 (Replay)** | 정상 메시지를 가로챈 뒤 그대로 다시 전송 | 난스(nonce), 타임스탬프, 순서번호 |
| **로그 조작** | 침입 흔적을 지우기 위해 기록을 수정 | 로그 서명, 무결성 검증, 분리 보관 |

### [w1-s10-3] 가용성 (Availability) (교안 p.개요:20)

**정의** — 인가된 사용자가 필요한 시점에 정보와 서비스를 사용할 수 있도록 보장하는 성질. 보안이 지나치게 강화되어 정당한 사용자마저 접근하지 못하면 가용성 훼손.

**개인정보 보호에서의 의미**

- **정보주체의 열람 · 정정 · 삭제 요구는 서비스가 살아 있어야 행사 가능**
- **암호화 키를 분실하면 데이터가 영구 복구 불가 → 키 관리는 가용성 문제이기도 함**

| 위협 | 설명 | 대응 방안 |
|---|---|---|
| **서비스 거부 공격 (DoS · DDoS)** | 대량의 요청으로 시스템 자원을 고갈 | 트래픽 필터링, CDN, 자동 확장 |
| **랜섬웨어** | 데이터를 암호화하여 사용 불가 상태로 만듦 | 오프라인 백업, 복구 훈련, 접근통제 |
| **시스템 · 하드웨어 장애** | 서버 · 디스크 · 네트워크 고장 | 이중화, 클러스터링, 무정지 설계 |
| **재해 · 정전 · 화재** | 데이터센터 물리적 손상 | 재해복구(DR) 센터, 지리적 분산 |
| **키 분실 · 키 손상** | 복호화 키를 잃어 데이터 복구 불가 | 키 백업 · 에스크로, 키 관리 시스템 |

> **[교안 강조]**
> 
> **기밀성 · 무결성 · 가용성은 서로 상충할 수 있다 → 보안 설계는 세 요소 사이의 균형을 찾는 일**


## [1주차 11] 확장 보안 요소와 보안 위협의 유형

### [w1-s11-1] 확장 보안 요소 (교안 p.개요:21)

| 요소 | 정의 | 세부 |
|---|---|---|
| **인증** Authentication | **통신 상대나 정보의 출처가 주장하는 바와 일치함을 확인하는 성질** | ▪ 사용자 인증 : 비밀번호, OTP, 생체인증<br>▪ 메시지 인증 : MAC, 전자서명<br>▪ 개체 인증 : 챌린지–응답 프로토콜 |
| **부인방지** Non-repudiation | **어떤 행위를 한 주체가 나중에 그 사실을 부인할 수 없도록 하는 성질** | ▪ 송신 부인방지 : 보내지 않았다고 못 함<br>▪ 수신 부인방지 : 받지 않았다고 못 함<br>▪ 핵심 기술 : 전자서명 + 인증서 |
| **책임추적성** Accountability | **시스템에서 일어난 행위를 특정 주체까지 되짚어 갈 수 있는 성질** | ▪ 접속기록(로그) 보관 및 보호<br>▪ 계정 공유 금지 · 1인 1계정 원칙<br>▪ 개인정보 보호법상 접속기록 보관 의무 |

> **[교안 강조]**
> 
> **기밀성 · 무결성 · 가용성 + 인증 · 부인방지 · 책임추적성 = 실제 시스템이 요구하는 보안 요구사항의 집합**

### [w1-s11-2] 보안 위협의 4가지 유형 (교안 p.개요:22)

*[도식] S = 송신자, R = 수신자, E = 제3자(공격자). 교안은 가로채기 · 변조 · 위조를 같은 모양(경로 + E 점선)으로 그렸고, 여기서는 점선 화살표 방향으로 차이를 표시함* — 도식 속 글자: 정상 흐름 / S / R / 송신자 → 수신자로 정보가 온전하게 전달됨 / (보안 목표 유지) / 차단 (Interruption) / S / R / 정보의 전달 자체가 끊어짐 / 가용성 훼손 / 가로채기 (Interception) / S / R / E / 제3자가 몰래 정보를 엿봄 (전달은 정상) / 기밀성 훼손 / 변조 (Modification) / S / R / E / 제3자가 정보를 바꾼 뒤 전달함 / 무결성 훼손 / 위조 (Fabrication) / S / R / E / 제3자가 송신자인 척 가짜 정보를 만들어 보냄 / 인증 · 무결성 훼손

> **[교안 강조]**
> 
> **차단 → 가용성 / 가로채기 → 기밀성 / 변조 → 무결성 / 위조 → 인증 · 무결성** (위협과 보안 목표는 1:1로 대응)

> **[작성자 주의 (교안·말씀 차이 · 개정 등)]** **교안 문장 안의 모순**
> 
> 같은 줄에서 **위조는 인증 · 무결성 두 목표**에 대응하므로 "1:1 대응"은 정확하지 않습니다. 객관식에서는 "차단 → 가용성, 가로채기 → 기밀성, 변조 → 무결성, **위조 → 인증(· 무결성)**"으로 외우세요.

### [w1-s11-3] 소극적 공격과 적극적 공격 (교안 p.개요:23)

| 구분 | 소극적 공격 (Passive Attack) | 적극적 공격 (Active Attack) |
|---|---|---|
| **행위** | 정보를 관찰 · 수집하기만 함 | 정보를 변경 · 삭제 · 생성함 |
| **대표 유형** | 도청(스니핑), 트래픽 분석 | 신분위장, 재전송, 메시지 변조, 서비스 거부 |
| **침해 대상** | 기밀성 | 무결성 · 가용성 · 인증 |
| **탐지** | **매우 어려움 (흔적이 남지 않음)** | 상대적으로 쉬움 (변화가 관찰됨) |
| **예방** | 가능 (암호화로 무력화) | **완전 예방 어려움** |
| **대응 전략** | **예방에 중점 — 암호화** | **탐지 · 복구에 중점 — 인증 · 로그 · 백업** |

**왜 이 구분이 중요한가**

- **소극적 공격은 「막을 수 없지만 무의미하게 만들 수 있다」** — 도청 자체를 차단하기는 어려우나, 암호화하면 엿들어도 의미를 알 수 없음
- **적극적 공격은 「완전히 막을 수 없으므로 빠르게 발견하고 되돌려야 한다」** — 무결성 검증, 접속기록, 백업 · 복구 체계가 함께 필요


## [1주차 12] 왜 암호기술인가 · 암호의 기본 모델과 공격자

### [w1-s12-1] 왜 암호기술이 필요한가 (교안 p.개요:24)

|  | 이유 | 설명 |
|---|---|---|
| 1 | **경계 방어만으로는 부족하다** | 방화벽 · 접근통제는 「들어오지 못하게」 막지만, 뚫린 뒤에는 아무것도 지켜 주지 못한다 |
| 2 | **암호화는 최후의 방어선이다** | 데이터가 유출되어도 키가 없으면 읽을 수 없다 → 사고를 「피해」로 만들지 않는다 |
| 3 | **법이 요구하는 의무이다** | 고유식별정보 · 비밀번호 · 생체인식정보의 암호화는 법령상 안전조치 의무 |
| 4 | **활용과 보호를 동시에 가능하게 한다** | 가명처리 · 동형암호 등은 데이터를 쓰면서도 개인을 드러내지 않게 해 준다 |

> **[교안 강조]**
> 
> **「침해는 언젠가 일어난다」를 전제로 설계하는 것 = 암호기술을 개인정보 보호의 기본값으로 두는 것**

### [w1-s12-2] 암호의 기본 용어와 모델 (교안 p.개요:25)

*[도식] 평문 M → 암호화 E(키 K) → 암호문 C → 복호화 D(키 K') → 평문 M (개요 p.25 도식)* — 도식 속 글자: 평문 M Plaintext / 암호화 E Encryption / 암호문 C Ciphertext / 복호화 D Decryption / 키 K (Key) / 키 K' / 복호화하면 다시 평문 M / C = E_K(M) / M = D_K'(C)

| 용어 | 설명 | 개인정보 보호에서의 예 |
|---|---|---|
| **평문 (Plaintext)** | 보호하려는 원래의 데이터 | 주민등록번호, 계좌번호, 진료기록 |
| **암호문 (Ciphertext)** | 암호화되어 의미를 알 수 없게 된 데이터 | DB에 저장된 암호화 컬럼 값 |
| **암호화 (Encryption)** | 키를 이용해 평문을 암호문으로 바꾸는 과정 | DB 저장 시 · 네트워크 전송 시 수행 |
| **복호화 (Decryption)** | 키를 이용해 암호문을 평문으로 되돌리는 과정 | 권한 있는 업무 처리 시에만 수행 |
| **키 (Key)** | 암호화 · 복호화를 제어하는 비밀 값 | 별도의 안전한 저장소에서 분리 관리 |

### [w1-s12-3] 암호 시스템과 공격자 모델 (교안 p.개요:26)

*[도식] 송신자 Alice → 공개 채널 → 수신자 Bob, 공격자 Eve가 채널을 관찰 · 개입 (개요 p.26 도식)* — 도식 속 글자: 송신자 Alice / 암호문 C 전송 (공개 채널) / 수신자 Bob / 공격자 Eve / 채널 관찰 · 개입

> **[교안 주의]** **케르크호프스의 원리 (Kerckhoffs' Principle)**
> 
> **암호 시스템의 안전성은 알고리즘의 비밀이 아니라 오직 「키의 비밀」에 의존해야 한다.**
> 
> - 알고리즘은 공개되어 검증받는 편이 오히려 안전 (공개 검증 → 취약점 조기 발견)
> - "보안을 숨김으로 달성한다(security by obscurity)"는 접근은 실패한다

**공격자에 대한 가정**

- **알고리즘의 전체 구조를 알고 있다고 가정**
- **통신 채널을 관찰 · 변조할 수 있다고 가정**
- **현실적으로 충분한 계산 자원을 가지고 있다고 가정 → 「계산적으로 불가능」하게 만드는 것이 목표**


## [1주차 13] 암호기술의 분류와 보안 목표의 대응

### [w1-s13-1] 암호기술의 분류 (교안 p.개요:27)

| 분류 | 핵심 | 대표 알고리즘 | 특징 |
|---|---|---|---|
| **대칭키 암호** | **암호화 키 = 복호화 키** | AES, ARIA, SEED, ChaCha20 | ▪ 빠르고 대용량 처리에 적합<br>▪ 키 공유 · 관리가 어려움 |
| **공개키 암호** | **공개키로 암호화, 개인키로 복호화** | RSA, ECC, ElGamal | ▪ 키 공유 문제를 해결<br>▪ 대칭키보다 매우 느림 |
| **해시 함수** | **임의 길이 → 고정 길이 (일방향)** | SHA-256, SHA-3, LSH | ▪ 역산 불가 · 충돌 저항성<br>▪ 무결성 · 비밀번호 저장 |
| **메시지 인증 코드** | **해시 + 비밀키** [보충: HMAC 기준의 설명. CMAC · GMAC은 블록 암호 기반이라 일반 정의는 "데이터 + 비밀키 → 확인값"(4주차 p.28)] | HMAC, CMAC, GMAC | ▪ 무결성 + 송신자 인증<br>▪ 부인방지는 제공하지 못함 |
| **전자서명** | **개인키로 서명, 공개키로 검증** | RSA-PSS, ECDSA, EdDSA | ▪ 무결성 + 인증 + 부인방지<br>▪ 인증서(PKI)와 함께 사용 |

### [w1-s13-2] 보안 목표와 암호기술의 대응 (교안 p.개요:28)

| 보안 목표 | 대칭키 암호 | 공개키 암호 | 해시 함수 | MAC | 전자서명 |
|---|---|---|---|---|---|
| **기밀성** | ● | ● | – | – | – |
| **무결성** | – | – | ● | ● | ● |
| **인증** | △ | △ | – | ● | ● |
| **부인방지** | – | – | – | – | ● |
| **키 교환** | – | ● | – | – | – |

● 제공 △ 부분적 · 조건부 제공 – 제공하지 않음

**읽는 법**

- **하나의 기술이 모든 보안 목표를 제공하지는 않는다 → 조합해서 사용**
- 예) 기밀성 + 무결성 + 인증이 동시에 필요하면 「대칭키 암호 + MAC」 또는 인증암호(AEAD) 사용
- 예) 기밀성 + 부인방지가 필요하면 「공개키 암호 + 전자서명」 조합
- **부인방지는 오직 전자서명만 제공 → 서명자만이 개인키를 가지고 있기 때문**

> **[작성자 주의 (교안·말씀 차이 · 개정 등)]** **4주차 표와 값이 다름 — 시험은 4주차 표 기준** 〔시험·중요 신호〕
> 
> 4주차 교안 p.29의 같은 표는 더 세분화되어 있습니다: **해시 함수의 무결성 ● → △**(키가 없어 단독으로는 제한적), **대칭키 · 공개키 암호의 무결성 – → △**(암호화만으로는 무결성 보장 안 됨), 공개키 암호의 인증 △ → –. 교수님 설명도 4주차 쪽과 같으므로 표를 묻는 문제는 4주차 p.29로 답하세요. "무결성을 위한 대표 기술 = 해시 · MAC · 전자서명"이라는 문장 자체는 그대로 맞습니다.

> **[보충 (교수님 설명 아님)]** **자료구조와 연결 — 해시 함수가 두 번 나오는 이유 — 교수님 설명 아님**
> 
> 자료구조의 해시 테이블에서 쓰는 해시 함수는 **빠르고 고르게 흩어지는 것**이 목표라서 입력을 거꾸로 찾아내기 어렵지 않아도 됩니다. 암호학적 해시 함수는 여기에 더해 **출력으로 입력을 되찾을 수 없고(일방향), 같은 출력을 내는 두 입력을 찾기 어려워야(충돌 저항성)** 합니다. 이름은 같아도 요구 조건이 다르므로, 비밀번호 저장에는 반드시 암호학적 해시(SHA-2 · SHA-3 · LSH 등)에 **솔트**를 더해 쓰고, 실무에서는 일부러 느리게 만든 비밀번호 전용 방식(PBKDF2 · bcrypt · Argon2)을 권장합니다.


## [1주차 14] 생명주기별 암호기술 적용과 법 · 제도적 근거

### [w1-s14-1] 개인정보 생명주기와 암호기술 적용 (교안 p.개요:29)

| 단계 | 보호 요구 | 적용 암호기술 | 구체적 예 |
|---|---|---|---|
| **수집** | 전송 중 노출 방지 | 공개키 암호 + 대칭키 암호 (TLS) | 회원가입 · 결제 화면의 HTTPS 통신 |
| **저장 · 관리** | 유출 시 판독 불가 | 대칭키 암호 (AES 등) | 주민등록번호 · 계좌번호 컬럼 암호화 |
| **저장 · 관리** | 복호화 자체가 불필요 | 해시 함수 + 솔트 | 비밀번호 일방향 저장 (복원 불가) |
| **이용 · 제공** | 변조 · 위조 탐지 | MAC, 전자서명 | API 응답 서명, 전자문서 서명 |
| **이용 · 제공** | 식별 없이 분석 | 가명처리, 동형암호, MPC | 통계 · AI 학습용 데이터 활용 |
| **이용 · 제공** | 행위 추적 가능성 | 해시 · 서명 기반 로그 무결성 | 접속기록 위 · 변조 방지 |
| **파기** | 복구 불가능한 삭제 | 암호키 파기 (Crypto-shredding) | 키만 안전 파기 → 데이터 복원 불가 |

> **[교안 강조]**
> 
> **동일한 데이터라도 「어느 단계에 있느냐」에 따라 필요한 암호기술이 달라진다.**

> **[교안 주의]** **비밀번호는 「암호화」가 아니라 「해시」로 저장**
> 
> 서비스 제공자조차 원래 값을 알 필요가 없기 때문.

### [w1-s14-2] 암호화의 법 · 제도적 근거 (교안 p.개요:30)

> **[교안]** **개인정보 보호법 제29조 (안전조치의무)**
> 
> 개인정보처리자는 개인정보가 분실 · 도난 · 유출 · 위조 · 변조 또는 훼손되지 아니하도록 내부 관리계획 수립, 접속기록의 보관 등 대통령령으로 정하는 바에 따라 안전성 확보에 필요한 기술적 · 관리적 및 물리적 조치를 하여야 한다.

**개인정보의 안전성 확보조치 기준 — 암호화 요구 사항**

| 구분 | 대상 정보 | 요구되는 조치 |
|---|---|---|
| **전송 시** | 고유식별정보, 비밀번호, 생체인식정보 | 정보통신망 송신 · 보조저장매체 전달 시 암호화 |

| **저장 시** | 고유식별정보, 생체인식정보 | 암호화하여 저장 |
| **저장 시** | 인터넷 구간 · DMZ에 저장하는 고유식별정보 | 반드시 암호화하여 저장 |
| **키 관리** | 암호화에 사용되는 키 | 안전한 보관 절차 수립 · 시행 (데이터와 분리) |

> **[보충 (교수님 설명 아님)]** **이 표는 개요 수준 — 정확한 조건은 3주차 제7조 — 교수님 설명 아님**
> 
> 현행 고시 제7조는 이렇게 나뉩니다: ① 인증정보(비밀번호 · 생체인식정보 등)는 저장 · 송수신(내부망 포함) 모두 암호화, 비밀번호는 일방향 · ② 이용자의 고유식별정보 · 카드 · 계좌번호 · 생체인식정보 7종은 암호화 저장 · ③ 이용자가 아닌 정보주체의 고유식별정보는 인터넷망 · DMZ면 암호화, 내부망이면 **주민등록번호만 무조건**이고 나머지는 영향평가 · 위험도 분석에 따라 · ④ 인터넷망 구간으로 보내는 개인정보는 종류와 관계없이 암호화. "고유식별정보는 항상 암호화" 같은 O/X는 3주차 기준으로 판단하세요. 또 안내서가 사용 금지로 든 것은 **3DES(TDEA) · MD5 · SHA-1**입니다(3주차 p.25, 단일 DES는 당연히 금지).

- **암호화는 「권장」이 아니라 「의무」 — 미이행 시 사고가 없어도 제재 대상이 될 수 있음**
- **알고리즘은 안전성이 인정된 표준(AES, SHA-2 등) 사용 — 취약해진 MD5 · SHA-1 · DES 사용은 미이행으로 평가**

### [w1-s14-3] 암호화는 어디에 적용되는가 (교안 p.개요:31)

*[도식] 단말 ↔ 서버 = 전송 중 암호화, 서버 ↔ DB = 저장 시 암호화 (개요 p.31 도식)* — 도식 속 글자: 이용자 단말 (브라우저 · 앱) / 전송 중 암호화 / 서비스 서버 (애플리케이션) / 저장 시 암호화 / 데이터베이스 · 저장소 / 서버에 도착 · 메모리에서 처리하는 「처리 중(in use)」 구간은 여전히 평문

| 구분 | 전송 중 암호화 (in transit) | 저장 시 암호화 (at rest) |
|---|---|---|
| **보호 대상 위협** | 도청 · 중간자 공격 · 변조 | DB 탈취 · 백업 유출 · 매체 분실 |
| **대표 기술** | TLS (공개키로 키 교환 → 대칭키로 통신) | AES 등 대칭키 암호, 컬럼 · 파일 · 디스크 암호화 |
| **적용 지점** | 단말 ↔ 서버, 서버 ↔ 서버 | DB 컬럼, 파일 시스템, 백업 매체 |
| **한계** | 서버에 도착한 뒤에는 평문이 됨 | 메모리에서 처리할 때는 평문이 됨 |

- **두 지점을 모두 암호화해도 「처리 중(in use)」 구간은 여전히 평문 → 남는 위험** — 이 빈틈을 메우려는 시도가 동형암호 · 안전한 다자간 연산 · 신뢰실행환경(TEE)


## [1주차 15] 개인정보보호 강화기술(PET)과 최신 암호기술

### [w1-s15-1] 기존 암호화의 딜레마 (교안 p.개요:32)

**암호화하면 안전하지만 「쓸 수 없고」, 복호화하면 쓸 수 있지만 「위험하다」** — 데이터 활용(통계 · AI 학습 · 연구)과 개인정보 보호가 충돌하는 지점.

**식별성을 낮추는 접근 : 가명처리와 익명처리**

| 구분 | 원본 정보 | 가명정보 | 익명정보 |
|---|---|---|---|
| **식별 가능성** | 직접 식별 가능 | 추가 정보 있으면 식별 가능 | 복원 불가 · 식별 불가 |
| **법적 지위** | **개인정보** | **개인정보 (규제 완화 적용)** | **개인정보 아님** |
| **활용 범위** | 동의받은 목적 내 | 통계 · 과학적 연구 · 공익적 기록보존 | 제한 없음 |
| **데이터 유용성** | 높음 | 중간 | 낮음 |
| **예시** | 홍길동, 900312-1…… | A0173, 1990년생, 남 | 1990년대생 남성 1,240명 |

> **[교안 강조]**
> 
> **보호 수준을 높일수록 데이터 유용성은 떨어진다 → 「재식별 위험」과 「유용성」의 균형 문제**

### [w1-s15-2] 개인정보를 지키는 최신 암호기술 (교안 p.개요:33)

| 기술 | 핵심 | 예시 |
|---|---|---|
| **동형암호** (Homomorphic Encryption) | **암호문 상태로 연산이 가능한 암호** | Enc(a) ⊕ Enc(b) = Enc(a+b)<br>복호화 없이 통계 · 학습 수행 |
| **안전한 다자간 연산** (MPC) | **각자 데이터를 공개하지 않고 함께 계산** | 여러 병원이 원본을 공유하지 않고 공동 통계 산출 |
| **영지식증명** (Zero-Knowledge Proof) | **정보를 드러내지 않고 사실만 증명** | 생년월일을 밝히지 않고 "19세 이상"만 증명 |
| **차분 프라이버시** (Differential Privacy) | **결과에 통제된 잡음을 더해 개인 기여를 은닉** | 통계 결과로부터 특정 개인의 포함 여부를 알 수 없게 함 |

> **[교안 강조]**
> 
> **공통 목표 : 「데이터를 쓰면서도 개인을 드러내지 않는다」 — 보호와 활용의 양립**
