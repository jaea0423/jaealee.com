02글쓰기의 목표 (Goals of writing)

왜 쓰는지 기억하라(Remember why you write) — 독자에게 알리기 위해서입니다(Inform readers).

글누구를 무엇으로 설득하나판단 기준
논문(Paper)심사자에게 결과가 가치 있음을 설득관련성, 중요성, 독창성, 정확성, 가독성(relevance, significance, originality, correctness, readability)
학위논문(Thesis)심사위원에게 내 역량을 설득주제 분야 전문성, 방법을 능숙하게 쓰는가, 전문가로서의 기술(expertise, competent use of methods, professional skills)
슬라이드 강조 (빨간색)

쓰는 동안 이것을 계속 염두에 두라(Keep this in mind while writing)

리뷰 보고서와 이어지는 점

논문의 판단 기준 다섯 개 중 significance, originality, correctness는 리뷰 보고서의 검토 기준과 이름이 같습니다. 논문 저자는 이 기준으로 설득하려 하고, 리뷰어는 같은 기준으로 그 설득을 점검하는 셈입니다.

03보고서 구조 잡기 (Structuring your work)

연구 보고서를 쓰는 첫 단계는 기본 구조를 계획하는 것입니다(The first step to writing a research report is planning its basic structure).

#연구 보고서의 일반 구조 (General structure of research reports)
1제목, 저자, 소속 (Title, authors, affiliations)
2초록 (Abstract)
3서론 (Introduction)
4연구 본론 — 세부, 방법론, 결과 (The research: details, methodology, results)
5결론 (Conclusions)
6참고문헌 (References)

→ 우리가 채워야 하는 것은 4번 "The research"입니다(we need to fill in "The research"). 04~07절이 그 방법입니다.

Note

내가 어떻게 그 통찰에 이르렀는지를 시간순·인과순으로 서술하는 것은 연구 보고서에 맞지 않는다(A chronological/causal description of how you arrived at your insights is not appropriate for a research report)

06-1과 이어지는 점

06-1에서는 같은 구조를 7부분(관련 연구가 따로 있음)으로 배웠습니다. 이번 슬라이드는 관련 연구를 빼고 6부분으로 적었고, 관련 연구의 위치는 09절에서 따로 다룹니다.

04구조 ① 연구 순서 (Structuring principles: Research sequence)

가장 단순한 방법은 연구 과정을 그대로 보고서 구조로 바꾸는 것입니다(The simplest approach is to turn the research process into a report structure).

연구 순서 (Sequence of research)괄호 속 내용더 나눌 수 있는 예
문제 정의(Problem definition)배경, 사전 지식(background, preliminaries)—
제안 해법(Proposed solution)추측, 가설, 설계(conjecture, hypothesis, design)(1) 핵심 알고리즘 (2) 구현 기법
평가(Evaluation)증명, 실험(proof, experiment)(1) 요구사항 분석 (2) 이론적 분석 (3) 실증 평가

→ 많은 논문과 짧은 학위논문에 맞는 범용 구조입니다(Good general-purpose structure for many papers and shorter theses).

예시 — EvalPlus (Is Your Code Generated by ChatGPT Really Correct?)

LLM이 생성한 코드를 자동으로 평가하는 실증 연구 파이프라인을 설계한 논문입니다(Liu, Xia, Wang, Zhang — UIUC·Nanjing). 학회·연도는 슬라이드에 없습니다.

논문 목차연구 순서에서의 역할
Introduction (background, preliminaries)문제 정의
Approach — Automated Test Input Generation / Test-Suite Reduction / Program Input Contracts제안 해법 (3개로 나눔)
Evaluation평가
Related Work → Conclusion—

슬라이드에 함께 실린 논문의 Figure 1은 ChatGPT가 만든 틀린 코드 예시입니다(HumanEval #58).

pythonChatGPT가 생성한 코드 (슬라이드 Figure 1)
def common(l1: list, l2: list):
    """Return sorted unique common elements for two lists"""   # 요구사항: 정렬된 결과
    common_elements = list(set(l1).intersection(set(l2)))     # 공통 원소 (중복 제거)
    common_elements.sort()                                     # 여기서는 정렬됨
    return list(set(common_elements))                          # ← 버그: set으로 다시 바꾸면 순서가 보장되지 않음
슬라이드의 입력 · 출력
입력 (l1, l2)출력판정
[4,3,2,8], [] — HumanEval 입력[]맞음
[5,3,2,8], [3,2] — HumanEval 입력[2,3]맞음
[4,3,2,8], [3,2,4] — HumanEval 입력[2,3,4]맞음
[6,8,1], [6,8,1] — HumanEval⁺ 입력[8,1,6]틀림 — 정렬 안 됨

코드 주석은 제가 붙였습니다. 슬라이드는 docstring의 "sorted"와 마지막 줄 set(...)에 분홍색 표시를 해서 정렬 후 다시 set으로 바꿔 순서가 깨지는 버그를 가리킵니다. 기존 테스트 3개는 통과했는데, 새 입력 하나가 버그를 잡아낸 것이 이 논문의 문제 제기입니다.

팀 주제와 이어지는 점

"AI가 만든 코드가 테스트를 통과해도 정말 맞는가"는 우리 팀 주제(AI 코딩 도구와 초보자)와 맞닿아 있습니다. CHI '23 논문에서도 학습자의 49%가 생성 코드를 수정 없이 제출했습니다.

HumanEval — 교수님이 설명하신 내용 아님

HumanEval은 OpenAI가 2021년 공개한 Python 코드 생성 벤치마크로, 함수 설명(docstring)과 테스트로 이루어진 문제 164개입니다. HumanEval⁺는 이 논문이 테스트를 대폭 늘려 만든 확장판입니다. 06-2의 "벤치마크 중심 연구" 문제와 같은 맥락입니다.

05구조 ② 특수 사례 먼저 (Special case first)

복잡한 해법은 단순한 경우부터 보여 주는 것이 좋을 때가 있습니다(Complicated solutions are sometimes best represented by starting with a simple case).

순서내용
1공통 배경과 정의 (Common background & definition)
2더 단순한 특수 사례 — 정의, 해법, 평가
3완전한 일반 사례 — 정의, 해법, 평가
  • 이론적 평가가 특히 이 분할의 덕을 본다 — 단순한 경우를 분석하며 필요한 방법을 소개하고, 일반 경우에서는 그 방법을 다시 설명하지 않고 쓴다
  • 반대로 실증 평가는 모든 것을 설명한 뒤에 두는 편이 나을 수 있다
  • → 한 번에 아이디어 하나에 집중하게 해 주는 유용한 방식

예시 — Program Synthesis for Non-linear Real Arithmetic: Going Beyond Realizability

Akshay, Chakraborty, Govind, Joshi (IIT Bombay 등). 슬라이드 표기는 "Generating program code from program specifications (IJCAR 2026)"입니다.

논문 목차특수 사례 먼저에서의 역할
Introduction / Preliminaries and Problem Statement공통 배경과 정의
Hardness Results and Theoretical Characterizations문제의 어려움(이론)
Algorithmic Procedures for Solving RPSQ — ① Complete Synthesis for Single-Output Specifications특수 사례(출력이 하나인 경우)
　〃 — ② Synthesis for Full NRA일반 사례
Implementation and Experiments → Conclusion실증 평가는 맨 뒤

오른쪽 열은 슬라이드의 파란색 강조 두 줄을 05절 표에 짝지은 정리입니다. 초록 요지: 비선형 실수 산술(NRA) 명세로부터, 답이 있으면 답을 내고 없으면 없다고 보고하는 프로그램을 합성하는 문제.

06구조 ③ 예시 먼저 (Example first / Guiding example)

복잡한 해법을 설명하는 또 다른 방법은 예시부터 시작하는 것입니다(Another way of explaining a complex solution is to start with an example).

순서내용
1공통 배경과 정의
2풀어 본 예시 / 중요한 사용 사례 (Worked example / important use case)
3완전한 해법(과 평가)

→ 예시가 뒤에 올 기술적 세부를 분명히 하고 동기를 부여할 수 있습니다(Example can clarify and motivate technical details to come).

예시 — Reward-Guided Synthesis of Intelligent Agents with Control Structures (PLDI 2024)

Cui, Wang, Qiu, Zhu (Rutgers). 보상 기반 프로그램 합성(ReGuS)으로 로봇 제어 과제를 푸는 논문입니다.

논문 목차예시 먼저에서의 역할
1. Introduction배경
2. Overview — Program and Domain-Specific Language / The Synthesis Procedure (including examples)예시로 먼저 보여 주기
3. Problem formulation → 4. Reward-guided program synthesis완전한 해법
5. Experiments → 6. Limitations → 7. Related work → 8. Conclusion평가와 마무리

07구조 ④ 개요 먼저 (Overview first)

구성 요소가 많은 시스템은 개요부터 보여 주는 것이 가장 좋을 수 있습니다(Systems with many components might be best described by giving an overview first).

순서내용
1공통 배경과 정의
2해법의 개요 (Overview of solution)
3구성 요소별 설명과 각각의 평가
4전체 시스템의 통합 평가

→ 응용 지향 연구(그리고 도구 논문)에 알맞습니다(Appropriate for application-oriented research (and also for tool papers)).

예시 — UTFix: Change Aware Unit Test Repairing using LLM (OOPSLA 2025)

Rahman 외 (UT Austin, AWS, Meta). 코드가 바뀌어 낡은 단위 테스트를 LLM으로 고치는 기법입니다. 슬라이드 표기는 "Automatic test case repair using change-intention"입니다.

논문 목차개요 먼저에서의 역할

구조는 내용만큼 보고서의 맥락에 달려 있습니다(The structure depends on the report's context as much as on its contents).

10쓰기 시작 · 시간 계획 (Managing the write-up)

강조 박스 — 시작하기 (Getting started)

보고서 쓰기는 예상보다 오래 걸린다. 일반 지침: 가능한 한 빨리 시작하라!

  • 연구를 시작할 때 프로젝트 폴더를 만든다(메모·논문 등을 한곳에)
  • 거기에 문서를 일찍 만든다 — 빈 페이지라도

무엇부터 쓰나 (What to start with)

일찍 쓸 수 있는 것나중에 쓰는 게 나은 것

증명과 정의는 종이에서 발전시킨다 — 이론 연구는 글로 이루어진다. 화면에서 하면 피드백 받기에 좋다—

11막혔을 때 (Getting stuck)

글쓰기에서 막히는 것, 즉 글을 쓰기가 매우 어렵거나 불가능하게 느껴지는 것은 흔한 일입니다. 흔한 이유 네 가지가 있고, 과제는 그것들을 구별하는 것입니다 — "보통은 알 것이다. 스스로를 속이지만 마라"(you'll usually know - just don't cheat yourself).

원인증상해결해결이 아닌 것
쓸 내용 부족필요한 지식이 없거나, 그것을 글로 옮길 계획이 없다아직 이 부분을 쓰기 이를 수 있다 — 연구를 계획하라, 연구를 더 하라, 남의 의견을 구하라, 영감을 주는 일(운동·대화·명상·산책·독서)에 적당한 시간을 써 기분을 바꿔라더 작업할 필요 없는 일반적인 부분 다듬기에 시간 쓰기(정면 과제 회피)
두려움(완벽주의)무엇을 써도 부족하게 느껴진다. "올바른" 방식으로 시작하는 법을 모르겠다뭐라도 써라 — 문체·언어 상관없이 요점을 빠르게, 또는 아주 짧고 단순한 문장으로. 두려움·긴장 해소(명상·산책·운동·차·휴식). 수면 패턴·건강 확인미루기·압박 키우기 — 온라인 미디어·게임·TV로 생각 잠재우기, "유용한" 일(집안일, 실험 코드 개선 같은 사소한 연구 일)로 바쁘기, 스스로를 더 몰아붙이기
우울, 번아웃 등아무것도 할 기운이 없음, 자존감·자신감 저하, 절망·무력감·극심한 슬픔·불안, 일·취미·친구·가족을 돌보지 않음도움을 구하라(친구 또는 전문가)아무것도 하지 않기
게으름·동기 부족슬라이드는 원인 목록에만 적고, 따로 증상·해결 슬라이드는 없습니다

12함께 쓰기 (Working with others)

공동 저자가 있다면 협업 방식을 분명히 정하라!(If you have co-authors, clarify what your collaboration model will be!)

흔한 방식내용평가 (슬라이드)
돌아가며 책임(Rotating responsibility)저자들이 번갈아 부분을 맡아 작업결과가 가장 좋다
부분별 책임 분담(Divide responsibility for parts)누가 어느 절을 쓸지 정함더 빠르지만 일관성이 깨질 수 있다
비대칭 역할(Asymmetric roles)모든 공동 작업자가 쓰지는 않음큰 팀에서 효율적. 일관성이 깨질 수 있고, 불공정할 수 있다
받아들일 수 없는 것 (Not acceptable)
  • 선물 저자 / 무임승차(Gift authorship / free rider) — 일을 하지 않은 "공동 저자"가 포함되는 것
  • 가벼운 검토만으로는 저자 자격이 정당화되지 않는다(light reviewing does not justify authorship)
팀 서베이 보고서와 이어지는 점

팀 최종 보고서(11/15)는 각자 리뷰한 논문을 모으는 구조라 기본이 부분별 책임 분담입니다. 슬라이드의 단점(일관성 깨짐)을 줄이려면 Editor 역할(재아 님)이 전체를 한 번 통일하는 단계가 필요합니다. 06-2의 "프랑켄슈타인 보고서" 위험 요인(팀 조율·마감)과도 같은 이야기입니다.

13이야기 계획 (Planning the story / narrative)

연구 보고서에는 명확하고 논리적인 구조가 필수입니다(A clear and logical structure is essential to research report).

단위규칙슬라이드 예
절(section)절 하나에 주제 하나(빨간색) — 초안 구조를 따르고, 새것과 알려진 것을 구분—
절각 부분의 길이가 적절하고 나머지와 균형이 맞아야 한다고유한 기여가 전체 길이의 절반 이상이어야 한다

문단쓰면서 문단마다 제목(headline)을 생각한다. 그 제목을 자리 표시·할 일로 써도 된다아래 BugLocator 서론

14독자를 놀라게 하지 마라 (No surprises!)

강조 박스 — 과학 글쓰기의 주요 원칙 (Main principle of scientific writing)

독자를 놀라게 하지 마라(Don't surprise your readers)

논리 구조가 독자에게 뻔히 보여야 합니다(The logical structure must be made obvious to the reader).

  • 연구 보고서는 소설이 아니다
  • 무엇을 어디서 찾을지 분명하면 효율적으로 읽을 수 있다
  • 앞쪽 참조(forward-reference)를 피하라 — 아직 다루지 않은 내용에 기대지 마라
    • 개념이나 단어를 정의하기 전에 쓰지 마라

예 — 용어를 먼저 정의하고 그림으로 설명하기

슬라이드의 논문 캡처(제목 없음)는 3 PROBLEM DESCRIPTION에서 Real time task, Execution time, Priority, WCET, Deadline, Arrival time 등을 먼저 정의하고, 그다음 그림으로 마감 시간 초과(deadline miss)를 설명합니다.

그림 속 용어 — 교수님이 설명하신 내용 아님

WCET는 Worst-Case Execution Time(최악 실행 시간), 작업이 가장 오래 걸릴 때의 실행 시간입니다. 도착 시간(arrival time)은 작업이 실행 가능해지는 시점, 마감(deadline)은 그 전에 끝나야 하는 시점입니다. τ3의 두 번째 작업은 9에 도착해 12까지 끝나야 했는데 13~14에 실행되어 마감을 넘겼습니다.

실천 방법 (Practical approaches)

  • 분명한 제목을 쓴다
  • 발표 계획을 계속 밝힌다(Continuously explicate your presentation plan)
  • 서론과 각 절 첫머리에 "스포일러"와 미리 보기를 넣는다
  • 서론 끝에 절·장 구조의 개요를 준다
  • 지금 무엇을 하려는지 설명한다
  • 문단과 문장을 연결한다 — 대조는 "but", "however", "nonetheless", 결과는 "therefore", "hence", "in consequence". 너무 많이 쓰지는 마라
예시 박스 — EvalPlus 논문 2장 Approach 발췌 (파란색 = 각 절 첫머리의 개요 문장)

2 Approach — Figure 2 shows the overview of EvalPlus. …
2.1 — Test input generation is consist of two main components: Seed initialization via ChatGPT and and type-aware input mutation. …
2.3 — The goal of evaluating code synthesis is to check whether the synthesized code accurately reflects the desired user intent. …

각 절이 무엇을 할지 먼저 말하고 시작합니다. 발췌 원문의 "is consist of"(→ consists of)와 "and and"는 원문 그대로입니다.

접속부사 없이 문장 잇기 (Connecting sentences without conjunctive adverbs)

원래 문단 (접속부사 사용, 빨간색)고친 문단 (앞 문장을 이어받기, 파란색)
Currently, the most popular and effective methods in test selection are primarily based on the uncertainty of the soft-max layer outputs. However, when a model exhibits high confidence in an incorrect prediction, these uncertainty-based methods often fail to detect such faults.Most test selection methods rely on the uncertainty estimated from soft-max layer outputs. Such uncertainty-based methods struggle to detect errors when the model is highly confident in an incorrect prediction.

고친 문단은 "Currently", "However" 없이, 앞 문장의 "methods rely on the uncertainty"를 다음 문장 주어 "Such uncertainty-based methods"로 이어받아 연결합니다. 문장도 더 짧아졌습니다.

리뷰 보고서와 이어지는 점

리뷰 초안을 영어로 쓸 때 이 슬라이드를 점검표로 쓸 수 있습니다 — Detailed comments의 각 소제목 첫 문장을 그 항목의 결론(스포일러)으로 시작하고, However/Therefore를 문단마다 반복하지 않기.

15인용의 목적과 방법 (Citations)

인용의 주된 목적 (Main purposes of citing)

  • 주장을 뒷받침한다(Provide support for claims)
  • 최신 연구에 대해 내 연구의 위치를 잡는다(Position own work with respect to the state of the art)
  • 더 읽을거리를 가리킨다(Point to material for further reading)

인용은 균형 있게 (The choice of citations must be balanced)

  • 흔한 개념은 인용하지 마라 — 예: 의사코드를 실었다고 의사코드를 설명하는 교과서를 인용할 필요는 없다
  • 이름을 흘리거나 목록을 부풀리려고 인용하지 마라(Don't cite to drop names or pad the literature list)
  • 자기 인용은 이전 전문성을 보여 주는 데 유용하지만 지나치면 안 된다
06-1과 이어지는 점

06-1에서 "나쁜 관련 연구 절은 심사자 비위를 맞추려는 생각 없는 이름 나열"이라고 배운 것과 같은 규칙입니다.

본문에서 인용을 가리키는 방식 (How to cite)

영숫자(Alpha-numeric)[Kim22], [ICN23]—
각주 방식(Footnote-style)41—

인용 키는 괄호 속 말처럼 다룬다 (Citation keys are treated as parenthetical remarks)

인용 키를 지워도 문장이 성립해야 합니다. 키를 문장 성분(주어 등)으로 쓰지 마세요.

나쁜 예 (빨간색)고친 예 (파란색)
"The authors of [1] introduced Alternating Turing Machines.""Chandra and Stockmeyer introduced Alternating Turing machines [1]."
"As shown by (Cook 1971), SAT is NP-complete.""As shown by Cook (1971), SAT is NP-complete." — 더 짧은 키에 주의
"SAT is NP-complete (Cook 1971)."
LaTeX 수업·리뷰 보고서와 이어지는 점

IEEEtran + \cite는 번호 키 방식입니다. 리뷰 보고서에서 "[1] shows that…"이 아니라 "Bassner et al. [1] show that…"처럼 저자 이름을 문장에 쓰고 키는 뒤에 붙여야 합니다.

16참고문헌 목록 · 무엇을 인용할까 (Reference lists)

인용한 문헌은 모두 참고문헌 목록에 자세히 보여 줍니다. 지침: 사람은 무엇을 인용했는지 바로 알고 찾을 수 있어야 하고, 기계는 인용을 자기 데이터베이스와 모호함 없이 맞출 수 있어야 합니다.

필수 정보 (Essential information)내용
Who?모든 저자 또는 편집자 — 목록이 아주 길지 않다면 모두 넣는다
What?저작물 제목 (온라인 자료는 웹 페이지 제목)
Where?출판 매체 또는 다른 출판 방식
When?출판 연도 (선택: 월), 웹 페이지는 접속 날짜

있으면 좋은 정보: DOI(많은 출판물의 고유 식별자), URL(비공식·찾기 어려운 출판물의 위치), 웹 페이지 최종 수정일, 출판사·출판 기관.

04-2·06-1과 이어지는 점

Who/What/Where/When은 06-1 "거르는 법"의 핵심 정보 표와 같은 네 칸입니다. 읽을 때 걸러 내는 기준이 쓸 때 반드시 적어야 하는 정보이기도 합니다.

무엇을 인용할 수 있나 / 해야 하나

구분슬라이드
인용할 수 있는 것다른 독자(적어도 일부)가 합리적으로 참조하고 접근할 수 있는 모든 것 — 웹 페이지, 학위논문, 데이터셋(DOI가 있으면 이상적), TV 프로그램, 공개 강연(어떤 URL에 녹화본이 있으면 이상적) 등
주의해서출판되지 않은 원고 — 어떻게 접근할 수 있는지 밝히거나, 내용에 기대지 말고 저자에게 공을 돌리는 용도로만
인용할 수 없는 것개인적인 대화
인용해야 하는 것신뢰할 수 있는 고품질 연구 — 연구 품질 판단과 같은 지침을 쓴다(예: 저널 논문 > 워크숍 논문)
원출처가 나중의 요약보다 낫다 — 예외: 배경 읽기에는 역사적 원본보다 교과서가 낫다
보존되는(archival) 출판물이 웹 페이지보다 낫다
리뷰 보고서와 이어지는 점

리뷰의 "지금도 유효한가"에 쓰려던 How AI Impacts Skill Formation은 arXiv 프리프린트(동료 심사 전)입니다. 슬라이드 기준으로는 "주의해서" 쪽에 가깝고, Bastani et al. (PNAS 2025) 같은 저널 논문을 주 근거로 두는 편이 맞습니다.

18용어 정리

연구 순서 구조research sequence

문제 정의 → 제안 해법 → 평가 순서로 본론을 짜는 범용 구조.

특수 사례 먼저special case first

단순한 경우를 먼저 풀고 일반 경우로 넓히는 구조. 이론적 평가에 유리.

예시 먼저guiding example

풀어 본 예시·사용 사례로 시작해 완전한 해법으로 가는 구조.

개요 먼저overview first

해법 개요 → 구성 요소별 설명·평가 → 통합 평가. 시스템·도구 논문에 맞음.

부록appendix

읽는 데 필수가 아닌 보조 자료를 두는 곳. 핵심 가정·주장은 넣지 않음.

선물 저자gift authorship

일하지 않은 사람을 저자로 넣는 것. 받아들일 수 없음.

앞쪽 참조forward reference

아직 정의·설명하지 않은 개념이나 내용에 기대는 것. 피해야 함.

스포일러·미리 보기spoilers and previews

서론과 각 절 첫머리에서 무엇을 할지 먼저 말해 주는 문장.

접속부사conjunctive adverb

however, therefore처럼 문장을 잇는 부사. 너무 많이 쓰지 않음.

번호 키 · 하버드 방식numerical keys · Harvard style

[1] / (Kim 2022) 형태의 인용 표기. 컴퓨터과학에서 가장 흔한 두 가지.

DOIDigital Object Identifier

출판물마다 붙는 고유 식별자.

보존 출판물archival publication

학술지·학회 논문집처럼 영구 보존되는 출판물. 웹 페이지보다 인용에 적합.

19확인 필요

1. 07-1(10/15 목)·05-1(10/1 목) — 해결

두 회차 모두 실습 시간(정리할 자료 없음)으로 확인되어 기록용 페이지를 만들었습니다 — 07-1, 05-1.

2. 슬라이드 쪽번호 "(1/2)" — 확인만

"Planning the story (narrative)" 첫 장은 "(1/2)"인데 이어지는 장은 "(2/4)", "(3/4)", "(4/4)"입니다. 내용 누락은 없어 보입니다.

3. 그림 라벨 — 확인만

14절 타임라인에서 τ3 첫 작업의 실행 라벨이 슬라이드에는 "e3,2"로 적혀 있습니다. 두 번째 작업과 겹치므로 e3,1의 오기로 보고 그림에는 e3,1로 그렸습니다.

4. 예시 논문 제목 표기 — 확인만

슬라이드의 예시 제목이 실제 논문 제목과 다릅니다: "Reward-guided robot task procedure Synthesis of Intelligent Agents" → 실제 Reward-Guided Synthesis of Intelligent Agents with Control Structures, "Automatic test case repair using change-intention" → 실제 UTFix. 교수님이 내용을 풀어 쓴 제목으로 보입니다. NRA 논문의 "IJCAR 2026"은 확인하지 못했습니다.

5. 슬라이드 원문 오타 — 확인만

① p.21 "to provided" → to provide ② p.23 "Plan you research" → your, "mediation" → meditation ③ p.24 "mediate" → meditate ④ p.31 "challange", "appraoches"(2회), "Retrival", "large-scales" ⑤ p.36 "Havard style" → Harvard ⑥ p.37 "for every references" → every reference. 본문에는 의도된 뜻으로 옮겼습니다.

7주차 2차시 단어장

전공영어 필수 단어 — 보고서 쓰기

이번 차시 범위에서 보고서 구조·쓰기 과정·인용을 말할 때 다시 만날 단어만 골랐습니다.

  • chronological/ˌkrɑːnəˈlɑːdʒɪkl/adj.

    시간순의 — 일어난 차례대로 늘어놓은

    A chronological story of your work is not a good report.연구를 시간순으로 늘어놓은 이야기는 좋은 보고서가 아니다.

  • preliminaries/prɪˈlɪmɪneriz/n.

    사전 지식 — 본론 전에 알아야 할 기본 정의와 배경

    The introduction gives the background and preliminaries.서론은 배경과 사전 지식을 준다.

  • conjecture/kənˈdʒektʃər/n.

    추측 — 아직 증명되지 않은 주장

    The proposed solution starts from a conjecture.제안 해법은 하나의 추측에서 시작한다.

  • empirical/ɪmˈpɪrɪkl/adj.

    실증적인 — 실험·관찰 데이터에 근거한

    Write the empirical evaluation after you have the results.실증 평가 절은 결과가 나온 뒤에 써라.

  • auxiliary/ɔːɡˈzɪliəri/adj.

    보조의 — 주된 것을 돕는

    Appendices are for auxiliary material.부록은 보조 자료를 위한 것이다.

  • procrastination/proʊˌkræstɪˈneɪʃn/n.

    미루기 — 해야 할 일을 계속 뒤로 미루는 것

    Procrastination is not a solution to fear.미루기는 두려움의 해결책이 아니다.

  • perfectionism/pərˈfekʃənɪzəm/n.

    완벽주의 — 완벽하지 않으면 시작·마무리를 못 하는 태도

    Perfectionism can stop you from writing anything.완벽주의 때문에 아무것도 못 쓸 수 있다.

  • incoherence/ˌɪnkoʊˈhɪrəns/n.

    비일관성 — 앞뒤가 맞지 않고 하나로 이어지지 않음

    Dividing sections among authors might lead to incoherence.저자들이 절을 나눠 쓰면 일관성이 깨질 수 있다.

  • narrative/ˈnærətɪv/n.

    이야기 흐름 — 내용을 잇는 서술의 줄거리

    Plan the narrative before you write.쓰기 전에 이야기 흐름을 계획하라.

  • explicate/ˈeksplɪkeɪt/v.

    밝혀 설명하다 — 숨은 계획이나 뜻을 분명히 말하다

    Continuously explicate your presentation plan.발표 계획을 계속 분명히 밝혀라.

  • conjunctive/kənˈdʒʌŋktɪv/adj.

    접속의 — 문장·말을 이어 주는 (conjunctive adverb: 접속부사)

    Do not use too many conjunctive adverbs like however.however 같은 접속부사를 너무 많이 쓰지 마라.

  • parenthetical/ˌpærənˈθetɪkl/adj.

    괄호 속 말의 — 빼도 문장이 성립하는 덧붙인 말의

    Citation keys are treated as parenthetical remarks.인용 키는 괄호 속 말처럼 다룬다.

  • bibliography/ˌbɪbliˈɑːɡrəfi/n.

    참고문헌 목록 — 인용한 문헌을 모은 목록

    Every cited work appears in the bibliography.인용한 모든 문헌은 참고문헌 목록에 나온다.

  • archival/ɑːrˈkaɪvl/adj.

    보존되는 — 기록으로 오래 남겨지는

    Archival publications are better than web pages.보존되는 출판물이 웹 페이지보다 낫다.

  • unambiguously/ˌʌnæmˈbɪɡjuəsli/adv.

    모호함 없이 — 다르게 해석될 여지 없이

    Machines must match citations unambiguously.기계는 인용을 모호함 없이 맞출 수 있어야 한다.
