# DineONE 구조 정리

2026-11-11 기준으로 지금까지 정한 내용입니다. 이 시안은 `jaealee.com/dineone/` 에 있습니다.

## 1. 이름

- 영문 **DineONE**. 한글 표기 **다인원**은 당분간 쓰지 않습니다(11-11). 화면·제목·아이콘 설명 모두 DineONE만 씁니다.
- 원래 뜻: Dine(식사) + ONE(하나로 묶음). 한국어로는 '여러 사람'으로도 들림.
- 상표 조회(KIPRIS, 11-11):
  - '다인원'은 0건.
  - DINEONE은 2008년 음식점업(43류) 1건이 있지만 소멸.
  - 해외에 같은 이름은 없음.
- 글자만으로는 식별력이 약할 수 있어 **심볼과 글자를 묶은 결합 로고로 출원**. 출원 전에 변리사 검토를 받음.
- '원다인'은 쓰지 않음. 미국 OneDine(식당 기술 회사)과 겹침.

## 2. 도메인과 주소

| 용도 | 운영 | 개발 | 이 시안 |
|---|---|---|---|
| 기업 홈페이지 | `dineone.co.kr` | `dineone.dev` | `dineone/` |
| 가게 홈페이지 | 가게 자체 도메인 → 없으면 `가게.dineone.co.kr` | `dineone.dev/@가게` | `dineone/store/` |
| 사장님·직원 | `partner.dineone.co.kr` | `partner.dineone.dev` | `dineone/partner/` |
| 매장 기기 (웨이팅·계산대·TV) | `kiosk.dineone.co.kr` | `kiosk.dineone.dev` | `dineone/kiosk/` |
| 다인원 본사 | `admin.dineone.co.kr` | `admin.dineone.dev` | `dineone/admin/` |

- 가게 홈페이지는 **가게 자체 도메인이 주인공**입니다.
  - 다인원 표시는 맨 아래 작게만 둡니다. 외주로 싸게 만든 홈페이지처럼 보이지 않게 하기 위함입니다.
  - 도메인 명의는 사장님으로 합니다.
- 가게 영문 이름에 쓰지 못하게 막을 말: `www partner kiosk admin api app dev test mail help status`
- 도메인은 가비아에서 삽니다. Namecheap은 .co.kr을 팔지 않습니다.
  - 도메인만 사고, SSL·호스팅 같은 추가 상품은 사지 않습니다.
  - 네임서버는 Cloudflare로 옮깁니다.
  - `.dev`는 https로만 열리지만 Cloudflare가 인증서를 무료로 자동 발급합니다.

## 3. 맡는 곳

**Cloudflare**
- DNS, 화면 올리기, 와일드카드 서브도메인, 가게 자체 도메인 연결, SSL
- 유료 API 비밀값 보관 (화면 코드에는 절대 넣지 않음)
- 영상 저장 (R2)

**Supabase** (서울 지역)
- DB, 로그인, 행 단위 권한(RLS), 사진·파일 저장, 실시간 반영
- 프로젝트는 `dineone-prod`, `dineone-dev` 두 개
- 운영은 실제 가게가 붙을 때 유료로 올림 (무료는 일주일 안 쓰면 잠김)

**GitHub**
- 비공개 저장소 `dineone`
- `main` 브랜치 → 운영, `dev` 브랜치 → 개발

한옥반점이 지금 쓰는 방식(서브도메인마다 GitHub 저장소 하나)은 가게가 늘면 감당할 수 없습니다. 그래서 다인원은 프로그램 하나가 모든 주소를 받는 구조로 갑니다.

## 4. 저장소 구조 (실서비스)

```
dineone/
  apps/      www/ store/ partner/ kiosk/ admin/
  modules/   예약·웨이팅·장부·포인트·TV … (새 기능은 여기 추가)
  shared/    공통 디자인 부품, 자료 함수
  supabase/  migrations/(DB 변경 기록) seed.sql(개발용 더미)
  docs/
```

## 5. 처음부터 지킬 것

- 모든 표에 **가게 번호(store_id)** 칸을 둡니다.
- 가게 식별은 바뀌지 않는 내부 번호와 바꿀 수 있는 영문 이름을 따로 둡니다.
- 권한은 사람 × 가게 × 역할(사장·매니저·직원)로 정합니다.
- 공간은 **가게 → 구역(홀·룸) → 테이블** 구조로 둡니다.
  - 홀만 있는 가게는 구역이 하나입니다.
  - 화면은 하나로 두고, 구역이 하나면 구역 선택이 보이지 않습니다.
- 기능은 가게마다 켜고 끕니다. 새 기능은 시범 가게에서 먼저 켭니다.
- DB는 칸을 더하기만 하고 지우거나 이름을 바꾸지 않습니다.
- DB 변경은 개발에 먼저 적용하고, 확인한 뒤 운영에 적용합니다.
- 개발 DB에 실제 손님 정보를 넣지 않습니다.
- 기록은 지우지 않고 취소 표시를 남깁니다. 장부·포인트·예약 모두 해당합니다.
- 관리·기기 화면은 검색에서 뺍니다(noindex). 보호는 로그인과 RLS가 맡습니다.

## 6. 디자인 통일 정도

| 화면 | 통일 정도 |
|---|---|
| 관리·기기 | 거의 완전히 통일. 가게 로고와 색만 다르게 |
| 매장 TV | 정해 둔 틀 몇 개 중에서 고르고, 가게 색과 영상을 넣음 |
| 손님 홈페이지 | 부품은 공통, 고르기·순서·색·글꼴·사진은 가게별. 특별한 페이지는 따로 만들 수 있게 열어 둠 |

## 7. 매장 기기

- 직원 로그인 없이 **기기 등록 코드**로 가게에 묶습니다.
- 매장 TV:
  - 광고 영상, 부르는 웨이팅 번호, 오늘 예약을 보여 줍니다. 예약 이름은 `김*수`처럼 가리고 전화번호는 표시하지 않습니다.
  - 영상은 기기에 저장해 두고 끊김 없이 재생합니다.
  - 기기는 안드로이드 TV 박스나 미니 PC에서 크롬 전체화면을 권장합니다.

## 8. 포인트

- **적립**
  - 전화번호로 적립합니다. 처음 적립할 때 이름을 받으며, 성이나 별명도 됩니다.
  - 직원별 로그인은 쓰지 않습니다. 카운터 직원이 수시로 바뀌기 때문입니다.
  - 적립 한도는 두지 않습니다.
- **사용**
  - 손님이 이름과 전화번호를 둘 다 말해야 합니다.
  - 인증번호나 금액별 PIN은 쓰지 않습니다.
- 적립한 포인트는 **다음 날부터** 쓸 수 있습니다.
- **마감 정산 화면**에서 그날 실수를 바로잡습니다.
  - 같은 번호 두 번, 큰 금액, 한 번호에 몰린 적립을 표시만 하고 막지는 않습니다.
  - 포스 하루 매출과 나란히 비교합니다.
- 적립 기록에 들어온 방식(직원 입력 / 영수증 스캔 / 포스 연동)을 남기는 칸을 처음부터 둡니다.
- **포스 연동은 미룹니다.** 포스 회사와 모델은 지금 물어 둡니다.
- 장부 결제를 적립할지는 가게에 확인합니다.
  - 충전할 때와 사용할 때 둘 다 적립하면 같은 돈에 두 번 적립되므로 하나만 고릅니다.
  - 회사 장부는 '적립 안 함'이나 '충전 보너스'를 권합니다.
- 유효기간을 둡니다. 쌓인 포인트는 가게의 부채가 되기 때문입니다. 1년을 권합니다.

## 9. 정산이라는 말

정산은 아래 셋으로 나눠서 씁니다.

1. 다인원이 가게에 청구하는 이용료
2. 가게 안의 기록 정리: 장부와 포인트 통계
3. 온라인 예약금 같은 카드 결제

3번에서 손님 돈이 다인원 계좌를 거치면 전자금융업 문제가 생길 수 있습니다. 그래서 **PG 계약은 가게 명의로** 하고, 다인원은 화면만 연결합니다.

## 11. 예상 대기 시간 (쌓인 기록으로 계산)

- 처음에는 단순 계산으로 시작합니다: 앞 팀 수 × 한 팀당 평균 회전 시간 ÷ 테이블 수.
- 웨이팅마다 아래를 기록합니다.
  - 접수 시각, 인원, 호출 시각, **입장 시각**, 취소·불참 여부
  - 요일, 시간대, 공휴일 여부
  - 그때의 앞 팀 수와 빈 테이블 수
- **입장 시각은 직원이 '입장' 버튼을 눌러야 남습니다.** 이 버튼을 누르는 습관이 예측 정확도를 좌우하므로, 버튼 하나로 끝나게 만듭니다.
- 4~8주 정도 쌓이면 "같은 요일·시간대·앞 팀 수일 때 실제로 몇 분 걸렸는지"로 예상합니다.
- 숫자 하나 대신 **범위(예: 15~25분)**로 보여 줍니다.
- 가게가 늘면 비슷한 가게끼리의 기록으로 첫날부터 예측할 수 있습니다. 이것이 다인원만의 강점이 됩니다.

## 12. 기록(로그)

세 종류로 나눕니다.

| 종류 | 무엇을 | 어디에 | 누가 보나 |
|---|---|---|---|
| **업무 기록** | 예약·웨이팅·장부·포인트·설정이 바뀔 때마다: 언제, 어느 가게, 누가/어느 기기, 무엇을, 바뀌기 전→후 | Supabase `activity_log` 표 | 사장님은 우리 가게만, 본사는 전체(가게별로 걸러 보기) |
| **오류 기록** | 화면 오류, 서버 응답 실패, 느린 요청. 가게·기기 이름을 붙여서 | Sentry(무료 범위) + Cloudflare 로그 | 본사 |
| **접속·보안 기록** | 로그인, 로그인 실패, 권한 없는 접근 시도, 기기 등록·해제 | Supabase 로그인 기록 + `activity_log` | 본사, 필요하면 사장님 |

- 업무 기록은 **DB 트리거로 자동으로 남깁니다.** 화면 코드에서 빠뜨려도 DB가 알아서 남깁니다.
- 기록은 **더하기만 됩니다.** 고치거나 지울 수 없게 권한으로 막습니다. 본사도 마찬가지입니다.
- 모든 기록에 가게 번호가 붙습니다. '가게별 기록'은 가게 번호로 거른 것이고, '전체 기록'은 거르지 않은 것입니다.
- 기록 속 전화번호는 가려서 남깁니다(010-****-1201). 개인정보 보관 기간이 지나면 기록 속 이름도 가립니다.
- 장부·포인트처럼 돈과 관련된 기록은 오래 보관합니다(5년 기준으로 잡고 세무사 확인).
- 화면:
  - 사장님 화면에 '기록' 탭을 둡니다. 예: "18:42 카운터 아이패드 — 010-****-1201 포인트 4,300 적립"
  - 본사 화면에서는 전체 기록을 보고, 이상 징후는 알림으로 받습니다.

## 13. 서비스가 멈출 때 대비

멈추는 이유별로 대비가 다릅니다.

| 무엇이 멈추나 | 대비 |
|---|---|
| **가게 인터넷** | 매장 기기는 '끊겨도 돌아가게' 만듭니다. 오늘 예약·웨이팅을 기기에 저장해 두고, 끊긴 동안 받은 접수·적립은 기기에 쌓았다가 다시 연결되면 올립니다. 웨이팅 번호는 기기마다 겹치지 않게 나눕니다. TV 영상은 기기에 저장해 두고 계속 재생합니다. 비상시에는 사장님 휴대폰 핫스팟으로 연결합니다(안내서에 적어 둠) |
| **다인원 서버 (Supabase·Cloudflare)** | 짧은 장애는 위의 '끊겨도 돌아가는' 기기가 버팁니다. 손님 화면에는 "잠시 후 다시" 안내를 띄웁니다. 운영 DB는 유료로 올려 매일 백업하고, 특정 시점으로 되돌리는 기능을 켭니다 |
| **우리 실수 (잘못된 배포)** | 개발에서 먼저 확인합니다. 문제가 생기면 버튼 하나로 직전 버전으로 되돌립니다. 기능별 스위치로 문제 기능만 끕니다 |
| **자료 사고 (잘못 지움)** | 기록은 지우지 않고 취소 표시만 남깁니다. 백업에서 되살립니다 |
| **모든 게 안 될 때** | **매일 오픈 전에 오늘 예약 목록을 사장님 휴대폰으로 보내 둡니다** (PDF 또는 메시지). 최악의 경우에도 종이처럼 쓸 수 있습니다 |

- **백업의 백업:** Supabase 자체 백업 외에, 매일 밤 전체 자료를 별도 저장소(Cloudflare R2)에 따로 내보냅니다. 한 회사가 통째로 멈춰도 자료는 남습니다.
- **복구 연습:** 한 달에 한 번 백업을 개발 DB에 실제로 되살려 봅니다. 연습하지 않은 백업은 없는 것과 같습니다.
- **감시:** 1~5분마다 주요 주소와 DB가 살아 있는지 확인하는 외부 감시를 둡니다. 멈추면 운영자 휴대폰(텔레그램)으로 바로 알림이 갑니다.
- **기기 상태:** 각 매장 기기가 마지막으로 연결된 시각을 본사 화면에서 봅니다. 오래 끊긴 기기는 먼저 연락합니다.
- **연락 체계:** 장애가 생기면 가게에 알리는 문구와 순서를 미리 정해 둡니다. 상태 안내 페이지도 하나 둡니다.

**처음에 반드시 할 것 (나중으로 미루면 안 되는 것)**
1. 업무 기록 트리거와 '지울 수 없는 기록'
2. 운영 DB 매일 백업 + 별도 저장소 백업
3. 매장 기기의 '끊겨도 돌아가는' 저장
4. 외부 감시와 휴대폰 알림

## 14. 운영(.co.kr)과 개발(.dev) 경계

목표는 **개발에 할 일을 실수로 운영에 하는 일이 구조적으로 일어나지 않게** 하는 것입니다.
사람의 주의력에 기대지 않고, 잘못된 방향으로는 아예 갈 수 없게 막습니다.

### 원칙: 기본값은 언제나 개발

- 내 컴퓨터, 터미널, AI 작업자(Claude 등)가 기본으로 연결되는 곳은 **항상 개발**입니다.
- 운영에 닿는 길은 **딱 하나**, `main` 브랜치에 합쳐질 때 자동 배포(GitHub Actions)뿐입니다.

### 장치

| 장치 | 내용 |
|---|---|
| **운영 열쇠는 내 컴퓨터에 없음** | 운영 DB 비밀번호와 운영 Cloudflare 배포 권한은 GitHub의 운영용 비밀값(Environment `production`)에만 둡니다. 내 컴퓨터의 `.env`에는 개발 값만 있습니다. 그래서 실수로 운영에 명령을 보내려 해도 열쇠가 없어 실패합니다 |
| **운영 배포는 승인 버튼을 거침** | GitHub `production` 환경에 '승인 필요'를 켭니다. `main`에 합쳐져도 운영자가 버튼을 눌러야 배포됩니다 |
| **main 보호** | `main`에 직접 올리기와 강제 푸시를 금지합니다. `dev`에서 확인한 뒤 PR로만 합칩니다 |
| **DB 변경은 개발 → 운영 순서로만** | 변경 파일(`supabase/migrations/`)은 개발에 자동 적용됩니다. 운영 적용은 배포 승인과 함께만 일어납니다. 운영 DB에 손으로 SQL을 치지 않습니다 |
| **주소와 DB가 어긋나면 멈춤** | 화면이 켜질 때 자기 주소(`.dev`/`.co.kr`)와 연결된 DB(dev/prod)가 짝이 맞는지 확인합니다. 어긋나면 아예 뜨지 않고 "환경 불일치" 화면을 띄웁니다. 개발 화면이 운영 DB에 쓰는 일이 원천적으로 막힙니다 |
| **눈에 띄게 다름** | 개발 화면 맨 위에 늘 노란 'DEV' 띠를 두고, 파비콘도 다른 색을 씁니다. 브라우저 탭 제목 앞에 `[DEV]`를 붙입니다 |
| **이름부터 다름** | Supabase는 `dineone-prod` / `dineone-dev`, Cloudflare 프로젝트도 `-prod` / `-dev`, 비밀값 이름도 `PROD_` / `DEV_`로 시작합니다 |
| **계정 분리** | 운영 Supabase는 별도 조직에 두고, 평소 로그인하는 계정에는 개발 조직만 보이게 합니다(가능하면) |
| **운영은 읽기 전용으로 들여다봄** | 운영 문제를 조사할 때는 읽기 전용 계정만 씁니다. 고치는 건 개발에서 재현한 뒤 배포로만 합니다 |
| **되돌릴 수 있음** | 그래도 무언가 잘못 나가면 직전 배포로 되돌리고, DB는 특정 시점으로 되살립니다(13장) |

### AI 작업자 규칙

- 운영 주소, 운영 DB, `production` 환경에 영향을 주는 일(배포 승인, 운영 SQL, 운영 비밀값 변경)은 **사용자가 그 작업을 콕 집어 승인했을 때만** 합니다. 작업마다 따로 승인을 받고, 한 번 받은 승인이 다음 작업으로 이어지지 않습니다.
- 확인이 애매하면 개발에서 합니다.

## 15. 손님 알림

- 손님 알림은 **문자만** 씁니다. 카카오 알림톡은 쓰지 않습니다(11-11 결정, 확인표에서도 묻지 않음).
- 대상: 예약 확정·변경, 웨이팅 접수·호출, 포인트 적립, 장부 사용 내역(담당자).
- 문자는 건당 비용이 들어서, 발송 건수를 가게별로 기록에 남겨 청구 근거로 씁니다.
- **발신번호는 사업자(와이비테크랩) 대표번호 하나**로 모든 가게의 문자를 보냅니다(11-11 결정).
  - 가게마다 발신번호를 등록하는 서류(이용증명원·위임장)를 받지 않아도 됩니다.
  - 손님이 모르는 번호로 보지 않게 문자 맨 앞에 **[가게 이름]**을 붙이고, 끝에 가게 전화번호를 넣습니다.
  - 손님이 이 번호로 되걸거나 답장할 수 있으니, 대표번호에 "가게 문의는 가게 번호로" 안내 멘트를 둡니다.
  - 단문(한글 45자)에 맞추려면 가게 이름은 짧은 표기를 따로 둡니다. 예: [짚불태백].
