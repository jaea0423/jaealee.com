# DineONE DB 설계 (초안 v0)

2026-11-12 첫 초안입니다(같은 날 개인정보 동의·지우기 추가). SQL은 [dineone-db-draft.sql](dineone-db-draft.sql) 한 파일에 있습니다.

- **아직 어디에도 적용하지 않았습니다.**
  - 실서비스 저장소(`dineone`)가 생기면 `supabase/migrations/0001_init.sql`로 옮깁니다.
  - 그다음 `dineone-dev`에 먼저 적용합니다. 운영 적용은 구조 정리 14장을 따릅니다.
- 시안(`dining/zipbulgwanggyo/manage/store.js`)의 자료 모양을 그대로 옮겼습니다. 화면을 바꿀 때 이름이 어긋나지 않습니다.
- 내 컴퓨터의 Postgres(PGlite)에서 Supabase 로그인을 흉내 내 아래 검사를 모두 통과했습니다. 실제 Supabase에서는 한 번 더 확인합니다.

## 0. dev에 올리고 검사하는 방법 (11-12)

1. Supabase 대시보드 → `dineone-dev` 프로젝트 → **SQL Editor** → New query
2. [dineone-db-draft.sql](dineone-db-draft.sql) 전체를 붙여 넣고 **Run**
   - 처음 한 번만 실행합니다. 두 번 돌리면 '이미 있음' 오류가 납니다.
   - 다시 하려면 프로젝트를 새로 만들거나, 나중에 정식 migration으로 관리합니다.
3. 새 query에 [dineone-db-check.sql](dineone-db-check.sql) 전체를 붙여 넣고 **Run**
   - 맨 아래 표의 '통과'가 27개 모두 true여야 합니다.
   - 검사용 가게·사람·기기는 끝에서 스스로 지웁니다. 여러 번 돌려도 됩니다.
   - **운영(dineone-prod)에서는 돌리지 않습니다.**
- 프로젝트 설정: 'Automatically expose new tables' 끔, 'Enable automatic RLS' 켬(구조 정리 19장). 그래서 표 권한은 SQL 16장에 직접 적었습니다.
- 내 컴퓨터(PGlite)에서 Supabase와 같은 조건으로 두 파일을 미리 돌려 27개 모두 통과했습니다.

## 1. 큰 원칙

| 원칙 | 어떻게 |
|---|---|
| 가게끼리 섞이지 않음 | 모든 표에 `store_id`. 권한(RLS)이 자기 가게 줄만 보여 줌 |
| 손님은 가게마다 따로 | 같은 사람이 두 가게에 가도 손님 기록은 둘. 가게끼리 손님 정보를 공유하지 않음 |
| 지우지 않음 | 장부·포인트·예약은 지우기 권한 자체가 없음. 취소는 `voided_at`·상태로 |
| 기록은 DB가 남김 | 표가 바뀔 때마다 트리거가 `activity_log`에 자동으로 한 줄(누가/어느 기기, 전·후). 전화번호는 `010****1201`로 가림 |
| 기록은 못 고침 | `activity_log`는 본사·서버 열쇠도 고치거나 지울 수 없음 |
| 기기는 함수로만 | 매장 기기는 표를 직접 읽지 못하고 정해진 함수만 부름. 적립 태블릿이 손님 전화번호 목록을 통째로 받아 갈 수 없음 |
| 손님 화면은 서버를 거침 | 홈페이지 예약·원격 웨이팅은 Cloudflare 서버 함수가 확인한 뒤 DB에 씀. 손님 브라우저는 DB에 직접 닿지 않음 |
| 영업일 | 새벽 손님이 전날 영업으로 잡히게 가게마다 경계 시각(기본 05:00)을 둠 |

## 2. 표 목록

| 묶음 | 표 | 내용 |
|---|---|---|
| 가게 | `stores` | 이름, 문자용 짧은 이름(8자 이하), 전화, 상태(시범/운영/중지/폐업), 영업일 경계 |
| | `reserved_slugs` | 가게 영문 이름으로 못 쓰는 말(www, partner, kiosk, admin …) |
| | `store_domains` | 서브도메인과 가게 자체 도메인 |
| | `store_settings` | **확인표 답 = 설정값.** 시안의 `DEFAULT_CFG`와 같은 이름(`tables`, `dwellLunch`, `pointRate` …) |
| | `store_features` | 기능 켜고 끄기(예약, 웨이팅, 원격 웨이팅, 장부, 포인트, TV, 문자) |
| 사람 | `profiles` · `store_staff` · `platform_admins` | 사람 × 가게 × 역할(사장·매니저·직원). 본사는 관리자·읽기 전용 |
| 기기 | `devices` · `device_codes` | 기기 등록 코드로 가게에 묶음. 해제하면 바로 아무것도 못 함. 마지막 연결 시각. 끊겼을 때 쓸 웨이팅 번호 구간 |
| 공간 | `zones` · `store_tables` | 가게 → 구역 → 테이블. 좌석 수, 온라인 예약용 여부, 붙일 수 있는 테이블 |
| 손님 | `customers` · `consents` | 전화번호(숫자만), 이름(성·별명 가능), 홍보 동의 상태, 마지막 이용 시각. 동의는 바뀔 때마다 문구 버전과 함께 한 줄씩 더함 |
| 예약 | `reservations` | 날짜·시각·인원·테이블, 상태(요청/확정/착석/완료/노쇼/취소), 들어온 곳 |
| 웨이팅 | `waitlist` · `wait_counters` | 번호, 인원, 우선(예약 손님), 상태, **접수·호출·입장 시각**, 접수 때 앞 팀 수와 빈 테이블 수(예상 대기 계산용) |
| 장부 | `ledger_accounts` · `ledger_tx` · `ledger_balances`(뷰) | 거래처, 충전·사용, 쓴 사람, 취소. 마이너스 한도는 경고용 |
| 포인트 | `point_tx` · `point_state()` | 적립·사용·조정, 들어온 방식(계산대/직원/영수증/포스), 본인 확인 방식 |
| 마감 | `day_closings` | 그날 포스 매출, 마감 시각 |
| 문자 | `sms_messages` · `sms_credit_tx` · `sms_wallets`(뷰) | 보낸 문자, 바이트, 단문/장문, 크레딧, 원가. 크레딧 통장 |
| 이용료 | `subscriptions` · `payments` | 요금, 파트너가, 월 포함 크레딧, 자동 충전 규칙, 비상 크레딧, 결제 기록 |
| 기록 | `activity_log` | 업무 기록 (구조 정리 12장) |

## 3. 누가 무엇을 볼 수 있나 (RLS)

| | 직원 | 매니저 | 사장 | 매장 기기 | 본사 | 손님 화면 |
|---|---|---|---|---|---|---|
| 예약·웨이팅·장부·포인트·손님 | 읽기·쓰기 | 읽기·쓰기 | 읽기·쓰기 | 함수로만 | 읽기 | 서버 거쳐서 |
| 지우기 | ✕ | ✕ | ✕ | ✕ | ✕ | ✕ |
| 설정 | 읽기 | 고치기 | 고치기 | 읽기 | 읽기 | ✕ |
| 업무 기록·문자 내역·크레딧 | ✕ | 읽기 | 읽기 | ✕ | 읽기 | ✕ |
| 이용료·결제 | ✕ | ✕ | 읽기 | ✕ | 읽기 | ✕ |
| 직원 추가 | ✕ | ✕ | ○ | ✕ | ✕ | ✕ |

- **기기 등록**: 기기마다 Supabase 익명 로그인 계정을 하나 만들고, 등록 코드를 넣으면 `devices`에 묶입니다. 그래서 기기 비밀번호나 직원 로그인이 필요 없습니다.
- **기기용 함수** (지금 초안에 있는 것)
  - `kiosk_wait_join(인원, 전화)`: 입구 웨이팅 접수 → 번호와 앞 팀 수
  - `kiosk_earn(전화, 결제금액, 이름, 개인정보 동의, 홍보 동의)`: 계산대 적립. 처음이면 **필수 동의가 있어야** 회원을 만들고 동의 기록을 남김. 최소 금액보다 적으면 막음
  - `tv_board()`: 부르는 번호, 대기 팀, 곧 오는 예약(이름 `김*수`, 전화번호 없음)
- **나중에 더할 기기 함수**: 포인트 사용(이름+전화 확인), 웨이팅 취소, 손님 휴대폰의 내 순서 보기.

## 4. 계산 규칙 (시안과 같음)

- **포인트** `point_state(손님)`
  - 적립은 묶음으로 보고, 먼저 쌓인 것부터 씁니다(FIFO).
  - 유효기간(`pointExpireDays`, 기본 365일)이 지난 묶음은 소멸합니다.
  - 오늘 적립한 것은 다음 날부터 씁니다(`pointNextDay`).
  - 결과: 전체, 지금 쓸 수 있는 것, 오늘 적립분, 30일 안에 소멸, 소멸된 것, 다음 소멸일.
- **웨이팅 번호** `next_wait_no(가게)`
  - 영업일마다 1번부터 셉니다. 두 기기가 동시에 눌러도 겹치지 않습니다.
  - 가게 인터넷이 끊겼을 때 기기가 쓸 번호 구간은 `devices.wait_no_from`에 둡니다(구조 정리 13장).
- **문자 크레딧**
  - 크레딧 통장(`sms_credit_tx`)에 더하기와 빼기를 한 줄씩 남기고, 잔액은 합계로 계산합니다.
  - 월 포함·직접 충전·비상(웨이팅 호출 전용)을 칸으로 나눕니다.
  - 실제 발송, 크레딧 차감, 자동 충전은 서버만 합니다. 화면은 읽기만 합니다.
- **보관 기간 지난 개인정보 지우기** `purge_personal_data()`: 매일 새벽 서버가 부름. 기간은 [개인정보: 동의와 처리방침](dineone-privacy.md) 2장
  - 웨이팅 번호는 다음 날, 예약 요청사항·알레르기는 방문 30일 뒤, 손님 번호·이름은 마지막 이용 3년 뒤, 보낸 문자는 6개월 뒤 번호를 가리고 내용을 비움
  - 예약·포인트·장부 내역 자체는 남고, 누구인지만 알 수 없게 됨
- **카드 정보**: 카드번호와 정기결제 열쇠(빌링키)는 DB에 두지 않습니다. PG사와 비밀값 보관소에만 두고, DB에는 열쇠 이름만 남깁니다.

## 6. 다음에 할 것

1. 실서비스 저장소와 `dineone-dev`를 만들고 이 초안을 적용합니다. 실제 Supabase에서 같은 검사를 다시 합니다.
2. 서버 함수(Cloudflare Workers)를 만듭니다.
   - 홈페이지 예약(노쇼 제한 포함)
   - 원격 웨이팅
   - 문자 발송: 바이트 세기, 크레딧 차감, 실패하면 크레딧 돌려주기
   - 자동 충전
   - 매일 밤 백업
3. 개발용 더미 자료(`seed.sql`)를 시안의 더미와 같게 만듭니다.
4. 시안 화면이 `localStorage` 대신 이 DB를 쓰게 바꿉니다. 바꾸는 곳은 `store.js` 한 파일입니다.
